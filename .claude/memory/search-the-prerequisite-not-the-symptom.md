A request framed as *"X works in 2-D, make it work everywhere"* gets filed against the **symptom** words
("letter swap parity"). That search misses the issue that builds the thing X sits ON, which is filed
against the **capability** words.

2026-09-21, #1303: filed "analytic has no rename, so letter switching has nothing to attach to" after
searching `rename letter swap parity`. **#1154 — "a point's letter cannot be changed — port 2-D's rename
family" — was open, `P2`, and had carried `auto-ok` since 2026-09-16.** Found only afterwards, in the
`gh issue list --label auto-ok` output while verifying an arming.

Two costs, and the second is the real one:

- the new issue duplicated the prerequisite's scope (they were in fact complementary — #1154 explicitly
  scopes OUT the taken-letter case, which is exactly what the new one adds);
- **the new issue's plan contradicted a standing operator ruling.** #1154 had already ruled the entry
  surface — rename lives in the #1048 measure menu — on the argument that a menu entry *composes a typed
  sentence*, so it is not a second grammar. I had recommended "typed only, no menu" on precisely the
  objection that ruling already answers, and the operator did not catch it because he was answering a
  question about propagation and was never shown the five-day-old ruling.

**How to apply:** before filing any port/parity/"same on all tools" issue, run a second search on the
CAPABILITY in the target tree ("rename", "name a point", "click to name") and on `--label auto-ok`, not
only on the symptom. An armed issue in the same family is a plan with rulings already inside it; read
them before writing a competing plan. **A silent operator is not agreement** — he cannot correct a
contradiction with a ruling he is not shown, so the burden is on the search.

**Why:** a session's fresh recommendation carries no weight against a recorded ruling, but it reads
identically in the issue body — and once armed, an autonomous round builds the contradiction.
