## ADR-001 — Rebuild the engine as a constructive / dependency-graph model

**Status:** Accepted (2026-06-10)

**Context.** The original engine was a *shape-template matcher*: it recognized "this is a square / triangle" and placed vertices analytically. It dead-ended — it could not represent free points, points-on-objects ("G on AD"), arbitrary accumulating constraints, or enumerate alternative configurations. These are the three features most central to the product vision.

**Decision.** Rebuild as a **constructive / dependency-graph engine** (GeoGebra-style in spirit): every object is defined in terms of earlier ones; positions are computed by topological evaluation. Considered and rejected: a **numerical residual solver** (general, but less stable, figures jump, alternatives are fuzzy, failures hard to explain).

**Consequences.** Points-on-objects and free points become first-class (DOF model). Alternatives fall out of intersection branch choices. Stability becomes structural (persistent DOF/branch indices) rather than heuristic. Over-constraint detection becomes general. The old template/triangle/quad solver is discarded.

## ADR-002 — Input via parser-first, LLM-fallback behind a narrow boundary

**Status:** Accepted (2026-06-10)

**Context.** The product must be free to distribute, work offline, and not depend on a paid service for the common case. The old design called the LLM first with a regex fallback and shipped the API key in the browser.

**Decision.** Define a single `utterance → command[]` boundary. A **deterministic grammar parser runs first** (free, offline) and handles common phrasings; only inputs it can't handle **escalate to the Claude API**. The engine is agnostic to which path produced the commands.

**Consequences.** ~70–90% of inputs are expected to be handled locally at zero cost and zero latency. The LLM becomes optional and swappable. Requires building and maintaining a real grammar (risk R2 in the design doc).

## ADR-003 — LLM = Haiku 4.5; key behind a gated proxy; bounded cost

**Status:** Accepted (2026-06-10)

**Context.** Operator (David) is first-time with API billing, wants to give the tool away, and "has no motivation" to absorb open-ended cost. A browser-embedded key is both a cost and a security liability.

**Decision.** For the fallback, use **`claude-haiku-4-5`** (sufficient for short structured geometry parsing; ~10× cheaper than Opus/Fable, which add no quality on this task). The key lives **only in a server-side proxy**; the proxy is gated (per-class code) and rate-limited. Enforce a prepaid credit ceiling, a Console monthly spend limit, usage alerts, low `max_tokens`, and a lean prompt. A claude.ai **subscription cannot** power a distributed app's API calls — confirmed; not an option.

**Consequences.** Realistic exposure for a small utility is a few dollars/month and structurally incapable of surprising the operator. Requires running a small proxy (serverless is fine). Dev cost is negligible; use a separate dev key with its own cap.

## ADR-004 — Render with hand-rolled SVG (not JSXGraph, not Mafs)

**Status:** Accepted (2026-06-10)

**Context.** The engine is now the single source of truth, so the render layer only needs to *draw* its output. JSXGraph's value was its geometry *logic*, which is being replaced; its imperative API forced the old `BoardReconciler` sync layer. Mafs (a React math-viz lib) was considered.

**Decision.** Render with **hand-rolled SVG via React**, declaratively from engine output. Mafs rejected because it targets function-graphing — the geometry-specific visuals a construction tool needs (angle arcs, right-angle marks, equal-side ticks, dashed cevians, labels) aren't built-ins, so they'd be hand-drawn anyway; Mafs would only cover grid + pan/zoom (a small one-time chunk) at the cost of an external dependency.

**Consequences.** No imperative reconciler. Full control over geometry visuals. The renderer consumes engine output only, so it stays **swappable** — this decision is low-stakes and reversible without touching the engine.

## ADR-009 — Redefining an existing object is a conflict, not a silent no-op

**Status:** Accepted (2026-06-10) · **Amended by [ADR-011](#adr-011--re-placing-a-free-point-is-a-move) (free points are an exception — re-placing one is a move).**

**Context.** Idempotency (FR-EN-9) was implemented by `addObj` skipping any object whose id already exists. That conflated two different cases: re-issuing the *identical* definition (a legitimate no-op) and issuing a *different* definition for an existing id (a contradiction). The latter was silently dropped — surfaced when a demo "triangle" reused the square's `A/B/C`: declaring `C` as "5 from A and 5 from B" while `C` was already the square's derived corner was ignored, yet the step still reported success. An accepted ✓ for an impossible fact is both wrong and misleading.

**Decision.** A command may **introduce** new objects but may not **redefine** an existing one. The pipeline (`applyStep`) calls `commandConflict(prev, cmd)` before mutating: it produces the command's canonical objects (against an empty construction) and, for any id already present, compares structurally — identical ⇒ idempotent no-op (accepted), different ⇒ rejected with "'X' is already defined…", keeping the prior figure (same path as over-constraint, FR-EN-8). `addObj`'s skip-if-present remains, but it is now only ever reached for genuine duplicates because conflicts are caught upstream. Considered and rejected: treating a redefinition as an in-place *move* — that conflates declaration with dragging (a Phase-8 interaction), and makes the build-by-facts flow unpredictable.

**Consequences.** Contradictory redefinitions are now caught as a distinct, explained failure class. Demo quick-facts are additionally gated in the UI so an inapplicable command can't be issued in the first place (defence in depth; the engine guard is the real safety net). Covered by engine tests (conflict rejected + prior kept; pure-add and identical re-issue still pass).

## ADR-010 — Facts are individually selectable/deselectable/deletable; the figure is derived by replay

**Status:** Accepted (2026-06-10)

**Context.** A student needs to revisit a fact they entered — fix a mistake, or experiment with the impact of removing it. The Phase-3 store kept the *accumulated construction* as its source of truth, which can represent "all facts so far" but not "this fact exists but is currently off," and offers no handle on an individual earlier fact.

**Decision.** Make the **ordered list of facts the source of truth**; derive the figure by **replaying the enabled facts** through the engine (`replay`). Each fact carries an `enabled` flag. Three operations: **select** (highlight the objects the fact introduced, on the canvas — UI-only, not undoable), **deselect/select** (toggle `enabled`; the figure re-derives), **delete** (remove the fact). When a deselected/deleted fact is depended on by a later fact, the dependent **auto-drops** (it fails to apply during replay and is flagged inactive) and is **restored** when the dependency returns — chosen over *blocking* the action or *cascading* deletes, because it best serves "experiment and see the impact" and loses nothing (reversible). Branch choices for alternatives live in the fact's command, so cycling = editing that fact and re-deriving. Undo/redo tracks the fact list (toggle/add/delete/cycle are all fact edits); selection is excluded from history via `partialize` + an `equality` guard so highlighting doesn't pollute undo.

**Consequences.** Deselect is trivially reversible; delete is clean; the model is closer to the constructive ideal (a program of construction steps, not a baked figure). Positions stay derived (not stored), so undo can't desync coordinates from facts. Slightly more compute (replay on every change) — negligible at v1 sizes; can be memoized/incrementalised later if needed. This generalises naturally to future reordering/editing of facts.

## ADR-011 — Re-placing a free point is a move

**Status:** Accepted (2026-06-10) · amends [ADR-009](#adr-009--redefining-an-existing-object-is-a-conflict-not-a-silent-no-op)

**Context.** ADR-009 treated *any* re-declaration of an existing id as a conflict, explicitly rejecting the "in-place move" reading. In use that surprised: a `square ABCD` places `B` at the default `(5,0)`; typing `point B at (6,0)` was rejected as "B is already defined," even though B is a **free** point and relocating it is geometrically fine (the square just resizes — `C`,`D` are derived from `A`,`B`). The user asked "what prevents B being at (6,0)?" — and the honest answer was "only our guard, not geometry."

**Decision.** A **free point** (and only a free point) may be re-placed: re-issuing `free-point` for an existing free point **updates its coordinates** — a *move* — provided the resulting figure stays valid (`evaluate` still succeeds; an over-constraint or broken dependency rejects and keeps the prior figure). Re-declaring a **derived / on-object / intersection** point as something different remains a conflict (ADR-009 stands for those): those points are *defined* by other objects, so "moving" them is meaningless. In the store, a reposition **updates the existing free-point fact in place** rather than stacking rows, and is undoable/deletable like any fact (deleting the move reverts to the original definition). This is distinct from, and complementary to, **drag** (Phase 8): drag is a pointer gesture on the canvas; this is the typed/command path to the same end.

**Consequences.** Typed repositioning works and reads naturally; the build-by-facts flow stays predictable because only free points (the things that genuinely have positional freedom) can move. When constraint-driven solving lands ([ADR-012](#adr-012--constraints-may-solve-a-free-dof-constructively-phase-5)), a move that would violate a constraint is rejected by the same `evaluate` gate. Covered by engine + store tests (move resizes the square and stays valid; derived points still conflict; deleting the move reverts).

## ADR-012 — Constraints may solve a free DOF constructively (Phase 5)

**Status:** Accepted (2026-06-10) · **implementation generalised by [ADR-014](#adr-014--constraint-driven-solving-is-one-generic-mechanism-not-a-point-kind-per-combination)** (2026-06-11) — an angle that references a point-on-segment (as its vertex *or* a ray endpoint) now solves the parameter `t` (deterministic scan + bisection, branch-indexed, reverts on delete via replay). Remaining cases (on-segment as a *ray*, free-point DOFs, distance/parallel/perpendicular drivers) still to come, on the ADR-014 mechanism.

**Context.** Phase 1 implemented the angle constraint as a satisfiability **check** only: the referenced points are already determined, so a constraint can only confirm or contradict. This collides with the vision (FR-EN-3/-4/-5: distance, angle, right-angle, parallel, perpendicular, equal-segments are meant to *shape* the figure). Concretely: with a square `TYUI` and `G` on `IU` at the default midpoint, `angle UGY = 50°` is rejected (the figure says 63.4°) — even though `G` has one free parameter and sliding it to `t≈0.16` would make the angle exactly 50°. The engine never looked, because it doesn't *solve* constraints.

**Decision.** When a constraint references a point that still has a **free degree of freedom** (a point-on-object's parameter `t`, or a free point), the engine will **solve that DOF** so the constraint is satisfied — keeping within the constructive model rather than adding a general solver. Approach: targeted, **deterministic** solves — analytic where possible, otherwise bounded 1-D root-finding over the parameter range — applied as a construction step that sets the DOF. Multiple solutions (e.g. two `t` values giving the same angle) become **alternatives** (branch indices, like intersections — [ADR-001](#adr-001--rebuild-the-engine-as-a-constructive--dependency-graph-model)/FR-ALT). **Over-constraint detection still fires** when *nothing* is free to absorb the constraint (the current behaviour, for fully-determined references). Explicitly **rejected**: a general numeric residual solver over arbitrary constraint sets — that reintroduces the instability / figure-jumping / fuzzy-alternatives that ADR-001 chose the constructive model to avoid. This widens in lock-step with the rest of Phase 5.

**Consequences.** Constraints become *constructive* (they place geometry), matching how students think ("make this angle 50°") and how GeoGebra-style tools behave. Determinism and structural stability are preserved because each solve is local, bounded, and branch-indexed. Requires deciding, per constraint type, which DOF it consumes and how to enumerate solution branches — designed construct-by-construct in Phase 5. Until then, constraints over fully-determined points remain checks (today's behaviour), and the angle-on-a-free-`t` case is **not yet** supported.

## ADR-013 — Shapes build on existing points (composition)

**Status:** Accepted (2026-06-10) · **amended 2026-06-11** — a composed shape's *new* vertices are now fitted to the reused ones (see the amendment at the end of this entry).

**Context.** A student built `parallelogram ABCD`, then `square ADFG` — a square on the existing side A–D. It was rejected: "'D' is already defined." The `square`/`quad`/`parallelogram` commands create *all* their corners fresh (base vertices as free points), so they couldn't attach to points that already exist. But building a shape on an existing edge (a square on a triangle's side, etc.) is a routine, legitimate construction — the rejection was a gap, not a real contradiction.

**Decision.** A shape command **builds on existing points**: its **base corners reference whatever point already carries that id** (any kind — free, derived, on-object, intersection), creating a free point only for ids that don't yet exist. The default coordinates a shape assigns a *new* base vertex are an initializer, not a definition, so a base corner **never conflicts**. The shape's own **derived** corners are still new and **still conflict** if their id already exists as something different (ADR-009 holds for them). Mechanically: `applyCommand` already reuses existing points (`addObj` skips existing ids); `commandConflict` now exempts a shape's produced *free-point* (base) objects, while keeping the strict rule for derived corners and for the standalone `free-point` *move* (ADR-011). The shared edge is one segment (undirected id), and each shape keeps its own polygon.

**Consequences.** Figures **compose** — squares/triangles/quads can be built on the sides of existing shapes, and a base corner that is a derived point (e.g. a parallelogram's 4th vertex) keeps updating, so the attached shape follows. There are two squares on a given edge (one per side); the engine picks one deterministically (CCW) — making the other an *alternative* is future work. Covered by tests (square on a parallelogram edge is a valid square reusing A,D; a shape whose **derived** corner would redefine an existing point still conflicts).

**Amendment (2026-06-11) — a composed shape's new vertices are fitted to the reused ones.** The original implementation reused existing base corners but gave each *new* free vertex its absolute template default, independent of where the reused corners actually are. That collapsed any shape with a **free** non-base vertex when built on an existing edge: e.g. `triangle ABC` then `parallelogram ABDF` reused A,B at (0,0),(6,0) but placed the free third vertex D at the template default (7,0) — on line AB — so D,F landed on that line and the parallelogram degenerated to a segment. (Square/rectangle/rhombus dodged this because their non-base vertices are *derived* from the base edge, which is also why no test caught it.)

**Fix.** A shape now fits its canonical template onto its existing base vertices ("anchors") via a **similarity transform** (rotate + uniform scale + translate), computed in `apply.ts` (`fitTemplate`/`placeBase`) from the anchors' *evaluated* positions (threaded into `applyCommand` as `pos`): 0 anchors → identity (standalone, unchanged); 1 → translation; ≥2 → the farthest-apart anchor pair fixes the frame. New free vertices are placed through that transform; reused vertices are left untouched, so the shape shares the existing edge and is a non-degenerate instance of its template regardless of where that edge sits (including reused **derived** endpoints, since the fit reads computed positions). **Testing gap closed:** `phase5-composition.test.ts` now builds *every* shape both standalone and on an existing edge, asserting its defining property purely from (x,y) — the case-cross (free non-base vertex) × (built on existing points) that previously had no coverage at all.

**Amendment 2 (2026-06-11) — the shared edge need not be named first (order-independence).** The fit above places *new* vertices, but a shape can reuse an existing point only at a *free base* slot — derived corners still conflict (above). Base slots are fixed positions in the vertex tuple (e.g. a square's free base is positions 0–1, derived 2–3), so reuse only worked when the shared edge happened to be named first. `trapezoid ABCD` then `square RTCD` (a square on side DC, naming the new corners R,T first) put the existing C,D on the square's *derived* slots and was rejected — "C is already defined" — even though it's a routine construction. **Fix:** `normalizeShapeComposition` (apply.ts) cyclically **rotates the vertex tuple** so existing points land on free slots, not derived ones, before both the conflict check and the build. A polygon is a cycle, so a rotation is the *same* shape with a different start vertex (`square RTCD` → base `CDRT`); it prefers the as-typed order and rotates only when it strictly reduces derived-slot clashes. When no rotation can free an existing point from a derived slot — a *diagonal* pair, or all vertices already declared — it remains a genuine conflict (ADR-009 holds). This also means an existing point named where a derived corner would sit is reinterpreted as a *base* corner (reused), consistent with "base corners reference whatever point already carries that id." Covered by tests (square RTCD builds on the trapezoid's DC; CDRT and RTCD give the same square; a diagonal pair and an all-four redeclaration still conflict).

## ADR-014 — Constraint-driven solving is one generic mechanism, not a point kind per combination

**Status:** Accepted (2026-06-11) · refines [ADR-012](#adr-012--constraints-may-solve-a-free-dof-constructively-phase-5)

**Context.** The first ADR-012 slice absorbed a driving constraint into a bespoke point kind: an on-segment point whose angle is set became `on-seg-angle`, with its own type, evaluator case, and solver call. That shape doesn't scale — it enumerates the cross-product of (DOF carriers: on-segment, on-circle, free point…) × (constraint types: angle, distance, parallel, perpendicular…), one hand-built kind per combination, each with its own evaluation and branch-count logic. The slice also chose the driven DOF by looking **only at the constraint's vertex**, so an angle whose *ray endpoint* carried the freedom (e.g. "∠GBA = 37°" with G on AD — vertex B determined) was wrongly treated as a check and rejected, even though sliding G satisfies it. That broke the product's defining interaction.

**Decision.** Factor constraint-driven solving into three orthogonal parts (`src/engine/solve.ts`):

1. **Carriers stay generic.** A driven on-segment point becomes `on-segment-solved` — segment + the embedded `Constraint` + a branch index. One kind per *carrier*, regardless of which constraint drives it.
2. **Constraints contribute residuals.** Each constraint type defines `constraintRefs` (which points it references), `residual` (a scalar, 0 ⇔ satisfied), and `describeConstraint` (for error messages). A new constraint type is a new `case` in these three functions — not a new point kind, evaluator rule, or solver.
3. **One solver.** `solveParam` (geometry.ts) finds all roots of any residual over the carrier's parameter range by deterministic grid scan + bisection; the roots are the solution **branches** (alternatives, as in ADR-001/012). No root ⇒ "cannot place …" and the prior figure is kept.

**DOF selection considers every referenced point**, not just the vertex: the first reference (vertex, then ray1, then ray2 — deterministic) that still has a free DOF is driven; if none has, the constraint is a check (over-constraint detection, unchanged). A point already solved by an earlier constraint has no DOF left and counts as determined, so a second constraint on it correctly over-constrains.

This stays inside ADR-001/012's guardrails: each solve is local (one parameter), bounded, deterministic, and branch-indexed — it is *not* the rejected global residual solver.

**Consequences.** Phase 5d widens by adding residual cases (distance, parallel, perpendicular) and carrier kinds (on-circle, on-ray) independently — linear work, not multiplicative. The defining interaction works in both directions (angle at a driven vertex *and* angle to a driven ray point). A constraint that is *insensitive* to the available DOF (e.g. ∠GAB with G on AD: the angle is 90° for every t) is now rejected with the honest geometric answer — "cannot place G so that ∠GAB = 37°" — rather than a generic over-constraint message. Free-point (2-DOF) drivers remain future work and will need a 2-residual/2-DOF solve or a partial-determination model. The vision docs' example was corrected to the satisfiable "∠GBA = 37°".

## ADR-015 — A fact can be edited in place

**Status:** Accepted (2026-06-11) · generalises [ADR-011](#adr-011--re-placing-a-free-point-is-a-move)

**Context.** A student who typed "point E on AD at 20%" and later wants 40% had no way to change it. Re-typing was rejected as a redefinition conflict (ADR-009: E already exists as `on-segment t=0.2`, the new one is `t=0.4` → "already defined"); delete-then-re-add dropped E's dependents and re-appended E *after* them, breaking replay order. The only in-place edit was the free-point *move* (ADR-011). Yet editing an earlier fact is exactly what the incremental, fact-list model should make easy — ADR-010 already anticipated "reordering/editing of facts."

**Decision.** Add a store `update(factId, cmd, utterance)` that **replaces a fact's command at its existing list position**. The figure re-derives by replay (ADR-010). The UI exposes this as an **edit (✎) button** on each fact row, alongside ✓/×; clicking it opens the row as an inline text field pre-filled with the fact's phrasing, which is re-parsed on confirm (the same parser as the main input) and written back with `update`. Because the edited fact is applied at its own slot — *before* any dependent — the edited id is not yet present in the construction at that point, so `commandConflict` never fires: a parameter change just re-derives downstream, and a structurally incompatible change makes dependents **auto-drop reversibly** (ADR-010), rather than erroring. This means the edit is general (any fact, any field — ratio, angle value, coordinates, even kind/parents), not only a continuous-parameter tweak. The edit is one fact-list mutation, so it is **undoable** like any other (zundo). Re-typing a *new* line for an existing id remains a conflict (ADR-009 stands) — editing is the explicit, in-place path.

**Consequences.** "Change E to 40%" works: click ✎, fix the number, confirm. The replay/derived-figure model (ADR-010) carried almost all of this — `update` is a few lines and needed no engine change. Inline editing is per-row and single-active. Not yet built (deliberately deferred): drag-to-reorder facts (also enabled by the model) and dragging a point as the geometric form of the same edit (Phase 8). Covered by store tests (ratio edit re-derives without conflict; a dependent follows; the edit undoes).

## ADR-016 — Segment crossings are a click-to-create affordance, never auto-created

**Status:** Accepted (2026-06-11)

**Context.** When two drawn segments visibly cross — e.g. a parallelogram's diagonals AC and BD — the crossing is often a meaningful point (here, the centre where the diagonals bisect). Should the app mark it automatically? Auto-creating it is tempting but wrong for this engine: (1) it reintroduces *figure recognition / inference*, exactly what the constructive rebuild rejected (ADR-001) — every object should exist because it was declared; (2) N segments give O(N²) crossings, most incidental → clutter and fragile "interesting?" heuristics; (3) the figure is **dynamic** — free points move and alternatives cycle — so an auto-point (no DOF, no identity, a side effect of two segments' current positions) would blink in/out or jump, violating the stability guarantee; (4) a useful point needs a name the student will reference, and auto-labels (P1, P2) collide with their scheme; (5) noticing the diagonals meet and choosing to name the point is part of the geometric reasoning.

**Decision.** Crossings are a **suggestion**, promoted only by the student. The explicit construct stays the default (`line-line-intersection`, already parseable both directions). On top of it, the renderer detects interior crossings of *declared* segments (`findSegmentCrossings`, pure) and draws a **faint hollow dot** that brightens on hover; **clicking it creates a real, named `line-line-intersection` point** (the host picks the first free capital letter and runs it through the normal command path, so it's an ordinary editable/deletable/undoable fact). A crossing at a shared vertex isn't offered; once named, the dot disappears (an existing point now sits there). Detection lives behind an optional `onPickIntersection` prop, so the renderer stays a swappable, side-effect-free consumer (ADR-004) — it emits a pick intent; the host owns creation. **Theorem detection (Phase 6) does not need the point marked** — a predicate can compute the crossing internally to state "the diagonals bisect each other" without putting an object on the canvas.

**Consequences.** Marking an intersection costs one click instead of a sentence, while the model stays constructive and stable — nothing appears unbidden, and every marked point is a normal declared object. Rejected alternatives: auto-mark all crossings (clutter, instability, naming collisions); a typed-only path (kept, but high-friction for discovery). Future: the same hover/click affordance could offer midpoints, feet of perpendiculars, or tangent points as those constructs land. Covered by render tests (the AC×BD centre is offered once; adjacent/parallel segments offer nothing; a named crossing stops being offered).

## ADR-017 — Two distinct points may never share a location; a composed shape flips to avoid it

**Status:** Accepted (2026-06-11)

**Context.** A parallelogram `ABCD` and a square `CDFG` sit on opposite sides of edge CD; a third shape `parallelogram CDTY` built on CD placed its new vertices T,Y *exactly* on A,B — the default fit (ADR-013) reconstructed the first parallelogram on top of itself. Two distinct labels at one location is a degenerate, broken-looking figure. The operator's rule: **never position two nodes on top of each other — that is an error** — but here the shape had room to go elsewhere (the other side, or a different size), so it should be *placed*, not rejected.

**Decision.** Two layers. (1) **Invariant:** `evaluate` now fails any figure where two distinct points coincide (within `LEN_EPS`), flagged `coincide: true`; the step keeps the prior figure and explains ("T and A would be at the same point") — same contract as over-constraint. This holds for *every* construct, not just shapes. (2) **Auto-avoidance for composition:** when a shape built on exactly two existing points would coincide, `applyStep` retries once with `mirrorComposition` — the shape's *new free* vertices reflected across the edge through its two reused points, putting it on the open side (derived corners recompute from the reflected frees). If the mirror is clean it's used silently; if it still coincides (or the shape has no free vertex to flip — e.g. a second square on the same edge, whose far corners are fixed by the edge), the coincidence error stands. The default side is always preferred; the flip only fires on a collision.

**Consequences.** `parallelogram CDTY` now lands on the empty side, T,Y distinct from A,B, still a valid parallelogram. The invariant turns every silent overlap into an honest, explained failure that preserves the prior figure. Coincidence detection is O(P²) per evaluate — negligible at v1 figure sizes. Not done (bounded scope): trying *different proportions* to dodge a collision. The deeper generalisation is **[ADR-018](#adr-018--alternatives-are-samples-of-the-figures-residual-freedom)** — the colliding default is just one sample of an underdetermined shape; cycling should explore the freedom.

**Amendment (2026-06-11) — composition prefers the side *away* from existing geometry, and any shape can flip.** Two upgrades made textbook-clean defaults possible. (1) The derived corner kinds (`derived`/`perp-offset`/`rotated`) gained a `flip` flag that mirrors them to the other side of the base edge *without changing vertex labels* — so square/rectangle/rhombus (whose corners are derived, not free) can now flip too, not just the free-vertex shapes. `mirrorComposition` reflects new free vertices **and** toggles `flip` on new derived corners, mirroring the whole shape. (2) `applyStep` (`chooseComposition`) now evaluates *both* the default placement and the mirror and picks the valid one whose body sits on the side of the edge **away** from existing geometry — not only when the default coincides, but whenever the default would land on the occupied side. So a square built on a parallelogram's edge flips to the empty side instead of overlapping it; two squares on one edge land on opposite sides; a third (both sides full) still errors by the coincidence invariant. This decouples composition aesthetics from template tuning, which let the standalone templates be normalised to a clean **base-on-the-x-axis, built-upward** orientation (parallelogram/trapezoid were previously drawn base-at-top; the general quad had a tilted base) — the textbook look the operator asked for. Covered by engine tests (square flips to the empty side; second square goes to the opposite side; both-sides-full errors; templates upright).

## ADR-018 — Alternatives are samples of the figure's residual freedom

**Status:** Accepted (2026-06-11) · **Stage 1 built (2026-06-11)** · **Stages 2 & 3 built (2026-06-15)** · generalises [ADR-001](#adr-001--rebuild-the-engine-as-a-constructive--dependency-graph-model)/FR-ALT, reframes [ADR-017](#adr-017--two-distinct-points-may-never-share-a-location-a-composed-shape-flips-to-avoid-it)

**Stage 1 (built, 2026-06-11).** `FreePoint.pinned` distinguishes a point the *student* fixed (explicit "point A at (x,y)" → pinned) from one the *engine* defaulted (a shape's base vertex, a segment/circle's auto-created point → not pinned). `applySeed(construction, seed)` (`sample.ts`, pure + deterministic via mulberry32) perturbs only the non-pinned free points — a seeded rotation of the free cluster + independent per-point jitter — so the figure is re-drawn while every shape stays structurally valid (derived points recompute from their moved parents; a square is still a square). The store holds a `seed` (UI-only, not in undo history); `replay(facts, seed)` applies it; `resample()` advances to the next seed that evaluates (skipping degenerate draws); the "show another configuration" button calls `cycleAlt` when a discrete branch is selected, else `resample()`. `freeDofs()` lists the remaining free points. Tests in `phase-sample.test.ts`.

**Stages 2 & 3 (built, 2026-06-15).** **Stage 2 — constraints prune the sampled DOFs.** A fully-consumed *parametric* DOF carries a `solve` directive (on-segment/on-circle/on-line `t`/θ/offset, or a shape scalar) — `applySeed`/`freeDofs` skip it (perturbing it is a no-op; the constraint determines it 1-to-1). A **free vertex** the solver drives (ADR-030) is different: it keeps residual freedom, so it stays samplable (re-solving from a perturbed start yields a different valid drawing). **Stage 3 — a visible "degrees of freedom remaining" cue.** App shows `freeDofCount(construction)` beside "show another configuration": *"Degrees of freedom: N"* while underdetermined (blue), *"✓ fully determined"* at 0 (green) — the convergence made literal.

**Correction (2026-06-16) — the DOF count is `raw − constraints`, not "exclude every `solve`-marked object".** The first Stage-2/3 cut counted a `solve`-marked free *vertex* as 0 DOF. That's wrong: one scalar constraint (`CD ⟂ AB`) marks **all** referenced free vertices with `solve` for the joint solve, but removes only **one** DOF — so a figure of two segments + one ⟂ (8 raw DOF) was reported "fully determined" (0) when it has 7. Fixed: `freeDofCount` = Σ`rawMovableDof` (free point 2, parametric/shape scalar 1, derived/pinned 0) − Σ`dofRemoved(constraint)` (an equality 1, a `coincide` 2, an ORDER/inequality 0 — ADR-039), gathering constraints from **both** the checked list and the `solve` directives (a *driven* constraint lives only in `solve`), deduped by identity. And `applySeed`/`freeDofs` no longer exclude a `solve`-marked free *vertex* (only fully-consumed parametric/scalar carriers), so such a figure is still resamplable. Lone square = 4, pinned = 0, parallelogram + `|AB|=|AC|` = 5 (6−1), the two-segments-⟂ figure = 7. +tests incl. the reported `set-perpendicular`-over-four-vertices case.

**Context.** "Show another configuration" today cycles only **discrete** branch indices — which side a circle∩circle or angle solution sits on. But the product's defining interaction (vision §core, FR-EN "rarely fully determined", FR-ALT) is broader and *continuous*: an underdetermined figure has residual degrees of freedom, and the student should **see** that freedom and watch it shrink as facts accumulate, until exactly one figure remains. A parallelogram on an edge with an unspecified third vertex can be *anywhere*. The collision incident (ADR-017) made this concrete — operator's framing: *"the shape could be anywhere; the student should see a different valid drawing each time they cycle — a random size/rotation — until they add enough information to narrow it to one solution. Lots of freedom early is correct."* So a colliding default isn't a special error; it's one unlucky sample of a shape that could be drawn elsewhere.

**Decision.** Treat alternatives as **samples of the figure's residual freedom**, not only discrete branches. "Show another configuration" re-samples the **free** degrees of freedom — free points the student did *not* pin, a shape's engine-chosen (unspecified) vertices, and global placement/orientation — deterministically from a configuration seed, while keeping every *stated* fact satisfied (constraints solved, derived relations held, discrete branches honoured). As constraints accumulate (Phase 5d), free DOFs are consumed, so successive samples vary *less*, converging to a single rigid figure when fully determined — the convergence is itself the lesson. Discrete-branch cycling becomes the 0-dimensional special case of the same mechanism.

This requires a **pinned-vs-free distinction on points** that the engine currently lacks: a point the student fixed (`point A at (0,0)`) is *pinned* and never varies; a point the engine defaulted (a shape's unspecified base vertex) is *free* and is what cycling re-samples. Only free DOFs move.

**Consequences.** This is the product's core made literal — the student perceives "not yet determined" by watching the figure wander, and "determined" when it stops. Collisions (ADR-017) stop being a special case: the engine samples a non-colliding configuration and the student can cycle to others; the ADR-017 mirror is just the simplest, first sampler. **Staged:** Stage 1 — the pinned/free distinction + a seeded sampler so cycling re-draws an underdetermined figure (free points/vertices + orientation); Stage 2 — Phase-5d constraints prune the sampled DOFs automatically; Stage 3 — a visible "degrees of freedom remaining" cue. **All three are now built** (Stage 1: 2026-06-11; Stages 2 & 3: 2026-06-15 — see the status note above).

## ADR-019 — Lines are constructive scaffolding (an `(anchor, dir)` object), not drawn geometry

**Status:** Accepted (2026-06-11) · Phase 5b · extends [ADR-001](#adr-001--rebuild-the-engine-as-a-constructive--dependency-graph-model)

**Context.** Phase 5b needs angle bisectors, perpendiculars, and their crossings (corpus Q2: E = bisector(∠BAC) ∩ bisector(∠BCA), F = AE ∩ BC; Q3: F = foot of ⟂ from C to AD; Q4: D = bisector(∠BAC) ∩ bisector(∠ABC)). A bisector is a ray whose direction is *derived* from an angle — it isn't defined by two existing points, so the existing `line-line-intersection` (which takes four point ids) can't express "where two bisectors meet." The question was how to represent a derived line. Options: (a) a first-class **Line object** with several constructors; (b) a derived **direction point** on the bisector plus the existing 4-point intersection; (c) push it into constraint-solving (5d). (b) clutters the canvas with an auxiliary labelled point; (c) is a 2-DOF simultaneous solve, heavier than needed for a one-shot construction.

**Decision.** Introduce a first-class **`Line`** object (`types.ts`) carrying a `LineSpec` — `through` (two points), `bisector` (internal bisector of ∠p-vertex-q), `perpendicular`, or `parallel` (to a line, through a point). A line has **no coordinates**: the evaluator resolves each to an `(anchor, dir)` pair (`resolveLine`), in the *same* topological sweep as points (a line needs its points; a `line-intersection` point needs its lines — they interleave to a fixed point). New point kinds consume lines/points directly: `line-intersection` (two `Line` ids), `foot` (⟂ foot onto line a→b), `midpoint`. A new line kind is one `resolveLine` case; a new derived point is one `tryEval` case — neither needs a new top-level type. **Lines are scaffolding and are never rendered** — `scene.ts` ignores `kind:'line'`; only the *segments* the student names (e.g. `segment AE`, `segment CF`) are drawn. So a bisector contributes a crossing point and the segments around it, with no stray auxiliary dot. The existing 4-point `line-line-intersection` stays for through∩through (e.g. F = AE ∩ BC), so the new `line-intersection` (two Line ids) is used only when a line is *derived* (bisector∩bisector). `right-triangle ABC` is a shape with the right angle at the **last** id: A and C are free legs, B is a derived `perp-offset` perpendicular to CA at C, so ∠C stays 90° as A or C moves (consistent with how other shapes fix a default size).

**Consequences.** Q2/Q3/Q4 reproduce from typed He/En utterances (`phase5b.test.ts`, 11 tests). The renderer was untouched (the gate is structural). A *single* bisector fact ("AD bisects ∠BAC") and the `parallel`/`perpendicular` **constraint** phrasings ("BC ∥ AD") deliberately stay out of grammar — they shape an underdetermined figure and belong to Phase 5d, not construction; only the **meet of two bisectors** (fully determined) is wired now. The `parallel` line kind exists in the engine (cheap) ahead of its first parser use (Phase 5c, Q6). Drawing a line itself (clipped to the viewport, e.g. "draw the bisector") is deferred until a question needs a bare line shown.

## ADR-020 — Circles are first-class drawn objects; circle-dependent points resolve in the same sweep

**Status:** Accepted (2026-06-11) · Phase 5c · extends [ADR-019](#adr-019--lines-are-constructive-scaffolding-an-anchor-dir-object-not-drawn-geometry)

**Context.** Phase 5c reproduces the three circle problems (Q5: a triangle inscribed in a circle + the midpoint of arc BC; Q6: a chord and a diameter crossing, plus a parallel line ∩ the circle; Q7: an inscribed triangle, the tangent at a vertex, and an angle bisector meeting a side). This is the first phase that must **draw** a curve — Phase 2 deferred circles. Open questions: how to model a circle and a point *on* it, how a circle composes with the existing point/line dependency graph, and how the tangent (a line whose direction comes from a circle) fits ADR-019's line model.

**Decision.** A **`Circle`** is a top-level object (like `Line`) carrying a centre point id and a `RadiusSpec` (`length` — a fixed value, or `through` — the distance to a point on it). Unlike a line, a circle **is rendered** (an unfilled outline, drawn before segments so chords sit on top; `scenePositions` adds the circle's extent to the fit so it is never clipped). The evaluator resolves circles, lines, and points in **one interleaved fixed-point sweep**: a circle needs its centre; a tangent line needs its circle; an on-circle / line∩circle point needs its circle (and line) — so the sweep already handled lines+points (ADR-019) and now adds circles. New circle-dependent point kinds, each one `tryEval` case: **`on-circle`** (1 DOF — an angle θ; a lone "A on circle O" auto-spreads by a golden angle so inscribed vertices never coincide), **`antipode`** (a diameter's far end, 2·centre − of), **`arc-midpoint`** (the normalized sum of the two radius directions; `branch` flips to the other arc), and **`line-circle`** (0/1/2 solutions, `branch` selects). The **tangent** is one more `LineSpec` (`{via:'tangent', circle, at}`) resolving to (`at`, ⟂ to the radius there) — so a tangent is an ordinary scaffolding line (ADR-019) that happens to read a circle. An inscribed polygon is *not* a new primitive: it is `circle` + N `on-circle` points + the existing `triangle`/`quadrilateral` shape reused on those points (composition, ADR-013). A `circle`'s centre and a `segment`'s endpoints are created if missing (like a shape's base) so "circle centered at O radius 5" and bare segments work standalone.

**Consequences.** Q5, Q6, Q7 reproduce from typed He/En utterances (`phase5c.corpus.test.ts`, 6 tests) on top of circle-primitive unit tests (`phase5c.test.ts`, 8) — the full v1 construct vocabulary is now covered (Q1–Q7). 173 tests green, build clean. The corpus figures are valid drawings of the givens **up to free configuration** (e.g. the two chords of Q6 cross at a generic interior point, not the specific "C is the midpoint of OB" the algebra fixes — solving stays a non-goal, ADR/Vision). A tangent's `line∩circle` legitimately equals the point of tangency, so materializing that point trips the coincidence guard (ADR-017) — a minor, honest limitation (you already have the point). A circle through *three* points (circumscribed / circumcentre) is a different construct and stays out of grammar for now. Drawing a bare line (a tangent or bisector as a visible line, clipped to the viewport) remains deferred (ADR-019).

## ADR-021 — The constraint family is one generic mechanism (distance, equal, parallel, perpendicular)

**Status:** Accepted (2026-06-11) · Phase 5d · extends [ADR-014](#adr-014--constraint-driven-solving-is-one-generic-mechanism-not-a-point-kind-per-combination)

**Context.** Phase 5d finishes the constraint phrasings 5b/5c deliberately left out of grammar: `AB = 6` (fix a length), `AB = CD` (equal segments), `AB ∥ CD`, `AB ⟂ CD`. ADR-014 already built the generic mechanism for `angle` (a constraint is `constraintRefs` + `residual` + `describeConstraint`, solved over a 1-DOF on-segment carrier by `solveParam`). The question was only whether new constraints fit it without new machinery.

**Decision.** Each new constraint is **three small cases** in `solve.ts` (refs / residual / describe) plus a `residualTolerance` case — nothing else. `apply.ts` gains a single generic `driveOrCheck(con)`: if any referenced point is a plain on-segment point it is upgraded to an `on-segment-solved` carrier the constraint *places* (the same path angle used); otherwise the constraint is pushed as a *check* and `evaluate` flags it as over-constrained if its residual exceeds tolerance. `evaluate`'s constraint loop is now fully generic (`residual`/`residualTolerance`/`describeConstraint`), no longer angle-specific. Residuals are signed so `solveParam` can bracket a root: distance/equal use the length difference; parallel/perpendicular use the **unit** cross / dot (∈ [−1,1]) so the scale is bounded and the sign flips through the solution. Parser adds `AB = 6` / `AB = CD` / `AB ∥ CD` / `AB ⟂ CD` (He/En); the unnamed-foot phrasing "perpendicular from A to BC" stays out of grammar (it is the foot construct, not the ⟂ constraint).

**Consequences.** A constraint that references a sliding point *shapes* the figure (e.g. an on-segment E slides until `EB = 3`, or until `AE ⟂ AB`); over fully-determined points it is an honest over-constraint check that keeps the prior figure. Tests in `phase5d-constraints.test.ts`. **Fixed in passing:** `solveParam` missed a root that landed *exactly* on a grid sample (a symmetric configuration where the residual is exactly 0 at t = 0.5) — it now records exact-zero samples as roots, not just strict sign changes. Still 1-DOF only: a constraint driving a *free* point (2 DOF) leaves residual freedom and is Stage 2 of [ADR-018](#adr-018--alternatives-are-samples-of-the-figures-residual-freedom); a single angle bisector (a 1-DOF on-ray placement) is likewise deferred.

## ADR-022 — Lines can be drawn (visible flag), and two circles can cross

**Status:** Accepted (2026-06-12) · extends [ADR-019](#adr-019--lines-are-constructive-scaffolding-an-anchor-dir-object-not-drawn-geometry)/[ADR-020](#adr-020--circles-are-first-class-drawn-objects-circle-dependent-points-resolve-in-the-same-sweep)

**Context.** ADR-019 made `Line` objects pure scaffolding — never rendered — because their value was the *crossing* they produce. But that left the **tangent** (and bisector, perpendicular, parallel) with no way to be *seen*: a student typing "tangent at A" got either nothing (no standalone rule) or, at best, an invisible line whose only trace was a point. Real geometry work needs to draw a tangent, an angle bisector, a perpendicular through a point. Separately, the engine could intersect a line with a circle but **not two circle objects** with each other (only the radius-based `point-by-distances`).

**Decision.** A `Line` gains an optional **`visible`** flag. Lines created as scaffolding inside a compound (the bisector inside "where two bisectors meet", the tangent inside "tangent ∩ AB") stay invisible (flag absent); lines the student asks to *draw* set `visible: true`. The renderer resolves visible lines to `(anchor, dir)` (`scene.ts` `lineGeometry`, mirroring the engine's `resolveLine` — lines are a rendering concern, ADR-004) and draws each as a **dashed line clipped to the viewport** (an infinite line rendered as a long segment through its anchor; the SVG viewport clips it), behind the segments. New **standalone parser rules** emit visible lines: `bisector of angle ABC` (distinct from "AD bisects ∠BAC", which would *place a point* — still deferred), `tangent to circle O at A`, `line through P perpendicular to AB`, `line through P parallel to AB`. A new **`circle-circle`** point kind (and `circle-circle-intersection` command + parser "G is the intersection of circle O and circle P") crosses two circle objects via the existing `circleCircleIntersect`, 0/1/2 branches, cyclable like the other branch points.

**Consequences.** "We don't have משיק" is fixed — a tangent (and bisector / perpendicular / parallel) now draws. Two circles and their intersection are first-class. Tests: `src/render/__tests__/lines-circles.test.tsx` + a `circle-circle` campaign family (357 committed cases; 70k+ stress sweep clean). **Still deferred:** an **implicit circle** so `משיק ב-A` / `מיתר AB` attach to the on-screen circle without naming it (ambiguous once two circles exist — needs canvas context passed to the parser); a single bisector that *places a point* on the ray (1-DOF, ADR-018 territory); right-angle / tick / arc marks.

## ADR-023 — Phase 7: the LLM fallback normalises freeform input into canonical commands, behind a server proxy

**Status:** Accepted (2026-06-12) · Phase 7 · realises [ADR-002](#adr-002) (parser-first, LLM fallback)

**Context.** The deterministic grammar (`parse.ts`) covers the engine's vocabulary but is, by design, narrow — it absorbs structural variation (word order, synonyms, He/En) and returns `not-handled` for anything else. That `not-handled` boundary was always the planned escalation point to Claude. The operator confirmed students find exact phrasing hard ("very hard to *program* the data entry") and chose to build Phase 7 now. Two questions: what does the LLM emit, and how does the key stay safe.

**Decision.** **What it emits:** not raw engine command JSON (easy to get subtly wrong, and it could drift past what the engine supports), but the app's own **canonical command phrasings** — the exact lines the deterministic parser already understands. The model does natural-language *normalisation* (decompose, translate He↔En, resolve "the circle" against the on-canvas objects passed as context); the client then **re-parses each returned line with the tested `parse()`**, so only valid, in-vocabulary commands ever reach the store. The model's allowed vocabulary IS the supported `COMMAND_CATALOG`, embedded in the system prompt, so it can never invent unsupported constructs. The call uses **`claude-haiku-4-5`** (cheap, sufficient for bounded structured parsing) with **forced tool use** (`tool_choice: {type:'tool', name:'emit_steps'}` → `{ steps: string[] }`) and low `max_tokens`. **Where the key lives:** only in a **server-side proxy** — a Vite dev-server plugin (`server/llmProxy.ts`) serving `POST /api/parse`, reading `ANTHROPIC_API_KEY` from `.env.local`/shell via `loadEnv` (never a `VITE_` var, never the browser). The SDK is dynamically imported at request time. Cost controls: a request-size cap, a per-IP rate limit, Haiku + low `max_tokens` + a lean prompt, and (operator-side) a Console prepaid cap + spend limit. The pure core (`src/parser/llmShared.ts`: tool def, request builder, `extractSteps`) has no SDK/engine import so it loads in both the proxy and tests. The client (`src/parser/llm.ts`) only `fetch`es the proxy.

**Consequences.** A student can type "draw a circle with a triangle inside it" and get `circle …` + `triangle … inscribed …`; the engine never knows the LLM produced it. Tests (`llm.test.ts`, LLM mocked — no live calls): request shape (Haiku + forced tool), `extractSteps`, the dispatch (re-parse keeps only steps that parse, drops hallucinated phrasing, returns null when nothing's usable), and a **guard that no shipped `src/` file imports the SDK or reads the key** (which caught and removed two vestiges of the abandoned browser-key approach: `src/env.d.ts`'s `VITE_ANTHROPIC_API_KEY` and the old `.env.example`). 561 tests green, client bundle key-free. **Deferred:** a production deployment of the proxy (a serverless function wrapping the same handler) — the dev plugin proves the UX; prod hosting is a follow-up. The LLM is still bounded by the parser's vocabulary (it normalises, it doesn't extend the engine) — genuinely novel constructs still need engine work first.

## ADR-024 — A shape rule that can't account for a modifier escalates, never half-parses

**Status:** Accepted (2026-06-13) · refines [ADR-002](#adr-002) / the parser misparse-defense

**Context.** The deterministic grammar is deliberately forgiving: a shape rule matches its keyword and pulls the vertex labels via `labelRun`, ignoring word order and filler. But that same "ignore the rest" is dangerous when the rest carries **meaning** — `משולש ABC חסום במעגל` ("triangle ABC inscribed in a circle") matched `triangle ABC` and silently dropped `חסום במעגל`, drawing a bare triangle. A half-parse is worse than a miss: a miss escalates to the LLM (ADR-023), a half-parse draws a *wrong figure* and the student never finds out. The operator asked to cover the combination space systematically.

**Decision.** Two parts. (1) **Auto-create where the intent is unambiguous:** "inscribed in a circle" needn't name the centre — `inscribedPolygon` now creates a circle with a fresh centre label when none is given (the triangle/quad case). (2) **A general anti-half-parse guard on the shape rules:** after a shape extracts its keyword + labels, if a `SHAPE_LEFTOVER` token survives — a geometry-significant word/operator the shape itself can't express (a circle, a constraint `=`/`⟂`/`∥`, a special line, a second construct like `segment`/`point`, an inscription, an angle; He + En, plural-tolerant, word-bounded so it never matches inside "rectangle"/"triangle") — the rule returns `'stop'`, aborting the parse so the input escalates to the LLM instead of being half-parsed. A *right* triangle inscribed in a circle (engine can't build it — the hypotenuse must be a diameter) defers out of `inscribedPolygon` so the guard escalates it rather than drawing a generic inscribed triangle.

**Consequences.** `square ABCD with AB = 6`, `triangle ABC with angle BAC = 37`, `square ABCD and segment AC`, `rectangle ABCD with diagonals`, etc. now **escalate** (the LLM decomposes them, or the student sees "couldn't read that") — none silently draw a wrong figure. Clean canonical forms, order/spacing/filler variants, and the inscribed triangle/quad (named or unnamed centre) still parse. Pinned by `parser-coverage.test.ts` — a *parses-to-X* vs *escalates* matrix, both locales — the explicit contract for the boundary. The guard is intentionally conservative (it errs toward escalating a genuinely-compound utterance); the LLM fallback is what makes that cheap. *(Superseded in part by [ADR-025](#adr-025): several cases this ADR escalated — inscribed cyclic quads, inscribed right triangle, the circumcircle, and the special-line constructs — are now genuinely constructible and **parse**, because the engine widened to build them.)*

## ADR-025 — Widen the engine to build the cases ADR-024 was escalating (cyclic quads, right-tri inscribed, circumcircle, special lines)

**Status:** Accepted (2026-06-13) · extends [ADR-024](#adr-024) / the corpus-driven Phase 5

**Context.** ADR-024 made the parser *escalate* anything the engine couldn't build, which was honest but left real, common, curriculum constructs going to the LLM (or drawing only part, then reporting "couldn't draw this part"). The operator pushed back on one specifically — "an isosceles trapezoid *can* be inscribed" — and then: "fix this right triangle issue and any other such issues." The throughline: several escalating cases were not *unbuildable*, only *unbuilt*. The mechanical reason each refused was incidental, not fundamental.

**Decision.** Build them, in engine + parser lock-step:
- **Inscribed cyclic quads** (square/rectangle/rhombus/isosceles-trapezoid): place the 4 vertices *on the circle* at fixed angles (`INSCRIBED_ANGLES`) instead of using the off-circle `trapezoid`/`rectangle` derivations. The shape comes from the angles; the edges just connect them.
- **Right triangle inscribed** (Thales): vertices at 180°/0°/90° — A,B antipodal (hypotenuse = diameter), C the right angle on the circle.
- **Circumcircle** (`circle through A B C`): a new 0-DOF `circumcenter` point kind (engine) + a `circumcircle` command (circumcentre + circle-through-A); auto-creates the 3 points if new.
- **Special lines** as compositions of existing primitives, no new engine kind: `median` = opposite-side `midpoint` + `segment`; `height`/`altitude` and the bare-foot `perpendicular from A to BC` = `foot` + `segment`; `perpendicular bisector` = `midpoint` + a visible `perpendicular-line`; `AD bisects ∠BAC` = `bisector` ∩ opposite-side `line-through` → places D, + `segment` (the angle-bisector foot — fully determined, so no 1-DOF placement needed, sidestepping ADR-018). The Hebrew special-line rules run *before* the shape rules (their names embed משולש in `במשולש`, which the `triangle` rule would otherwise grab and stop on).

**Consequences.** `right triangle ABC inscribed`, `circle through A B C` / `מעגל חוסם את ABC`, `median/height/perpendicular-bisector from …`, `AD bisects ∠BAC`, and `triangle ABC with a height/median from A` (the compound, handled directly) all **parse and build** — moved from escalate → parses in `parser-coverage.test.ts`, with geometry lock-in tests (on-circle + right angle; equidistance; midpoint; foot ⟂; bisected angle). The catalog flips them to `supported`, so the help panel **and** the LLM system prompt (built from supported entries) learn them automatically. What still escalates is now only genuine **compounds** (a shape carrying a constraint, two constructs in one breath) — the LLM's job. 662 tests green, build clean.

## ADR-026 — Proportion constraint (|AB| = k·|CD|), and the half-parse it exposed

**Status:** Accepted (2026-06-13) · extends [ADR-021](#adr-021)/[ADR-014](#adr-014) (the constraint family / generic mechanism)

**Context.** Operator asked where proportions like `AB = 2·AD` are handled. Answer: nowhere — the constraint vocabulary had only `angle`, `distance` (`AB = 6`), `equal` (`AB = CD`, the ratio-1 case), `parallel`, `perpendicular`. Worse, `AB = 2 AD` (and `AB = 2*AD` / `AB = 2·AD`) **half-parsed**: `distanceConstraint` matched `AB = 2` and silently dropped `AD`, drawing a wrong figure (|AB| set to 2 instead of |AB| = 2·|AD|) — the misparse failure [ADR-024](#adr-024) guards against on shape rules, but the constraint rules had no such guard.

**Decision.** Add a `ratio` constraint, `|AB| = k·|CD|`, through the generic mechanism ([ADR-014](#adr-014)) — a residual `dist(a,b) − k·dist(c,d)`, refs `[a,b,c,d]`, the standard tolerance/description, and a `set-ratio` command that calls the same `driveOrCheck`. No new point kind, evaluator rule, or solver: it *drives* a 1-DOF on-segment carrier when one is referenced (e.g. `AE = 2 EB` places E at the 2:1 point) and is an over-constraint *check* otherwise. A `ratioConstraint` parser rule (`m·AB = n·CD` with at least one coefficient → k = n/m; plus Hebrew `AB פי 2 מ-AD`) runs **before** `equalSegments`/`distanceConstraint`, so the coefficient-free `AB = CD` still routes to `equal` and `AB = 6` to `distance`, while `AB = 2 AD` no longer half-parses.

**Consequences.** `AB = 2 AD`, `2AB = 3CD`, `AB = 2·AD`, `AB = 2AD`, `AB = 2*AD`, and `AB פי 2 מ-AD` parse to `set-ratio` and build (the proportion drives a sliding point, else is checked); pinned in `parser-coverage.test.ts` and a driven-DOF test in `phase5d-constraints.test.ts`. Catalog gains `AB = 2 AD` (so the help panel and the LLM prompt learn it). 676 tests green, build clean. Still deferred: textual coefficients (`AB is twice AD`) and the implicit-circle-style reference — left to the LLM.

## ADR-027 — "circle inscribed in a triangle" is the incircle, not a misparse of "triangle inscribed in a circle"

**Status:** Accepted (2026-06-13) · extends [ADR-024](#adr-024)/[ADR-025](#adr-025)

**Context.** Operator hit a crash: `circle … inscribed in triangle ABC` (the LLM's normalisation of an incircle request, complete with a placeholder `radius r`) produced a degenerate figure — "A and I would be at the same point". Cause: `inscribedPolygon` keys only on "inscribed" + a polygon word, so it grabbed a *circle*-inscribed-in-*triangle* phrase and built the wrong thing (a new centre at the origin + vertices forced onto it), colliding with an existing vertex. The two readings of "inscribed" are opposite constructs: **polygon inscribed in a circle** (vertices on the circle) vs **circle inscribed in a polygon** = the **incircle** (tangent to the sides, centred at the incenter).

**Decision.** (1) **Discriminate by order** — the inscribed subject comes first, so a circle word *before* the polygon word (`circle … inscribed in triangle`, `מעגל חסום במשולש`) is the incircle; `inscribedPolygon` bails on that case. (2) **Build the incircle** from existing primitives (no new engine kind): two angle `bisector`s → their `line-intersection` (the incenter I) → the `foot` from I to a side (the tangency point, = the inradius) → a `circle-through` that foot. A new `incircle` rule (`circle inscribed in triangle ABC` / `incircle of …` / `מעגל חסום במשולש`) runs before `inscribedPolygon`.

**Consequences.** The crash phrasing now builds a correct incircle (verified tangent to all three sides — the incenter is equidistant from them), while `triangle inscribed in a circle` still routes to polygon-in-circle. Realises the incenter/incircle of theorems 80–81 (pedagogy §4). Catalog + LLM prompt learn `circle inscribed in triangle ABC`; coverage matrix + a tangency lock-in test pin both directions. v1 covers the *triangle* incircle; a polygon incircle (tangential quad, theorem 88) stays deferred. 681 tests green, build clean.

## ADR-028 — A second statement that *places* an existing point drives a free DOF (accumulating constraints adapt the figure)

**Status:** Accepted (2026-06-13) · realises the core of [Vision §core interaction](01-vision.md) · extends [ADR-014](#adr-014), **amends [ADR-001](#adr-001)**

**Context.** The defining interaction of the product is that *facts accumulate and the figure adapts* — "G slides along AD until the angle holds." A real corpus case broke it: `C = AB∩DE` (a derived intersection), then `C is the midpoint of OB`. The second fact isn't a *redefinition* of C — it's a **constraint** that should move the free chord DE so its crossing with the diameter lands on the midpoint. The engine rejected it ("C is already defined"). The operator: *"this is the core element. this must work."*

**Decision.** A second statement that **places an already-built point P** is reinterpreted, in `applyStep`, as a coincidence: keep P, add the new placement as a HIDDEN target `~P` (`~`-prefixed id, not rendered), add a `coincide(P, ~P)` constraint, and mark a free **1-DOF ancestor** of P (an on-circle/on-segment point, found by walking P's dependency graph back to the most-recently-added parametric point) as *solved* to satisfy it. At evaluation, that DOF is driven: vary it over its range, re-evaluate the whole figure each trial (the constraint references *downstream* points), and find where the coincidence residual reaches zero. Because a coincidence distance is non-negative, the root finder is a **local-minimum finder** (a touch of zero, not a sign change), refined by ternary search; multiple minima are the solution **branches**.

**Why this does *not* re-open [ADR-001](#adr-001)'s "no numerical solver".** ADR-001 rejected a *general* residual solver over *all* DOFs (unstable, fuzzy alternatives, opaque failures). This is the **deterministic 1-DOF driver** of [ADR-014](#adr-014) generalised: **one** constraint drives **one** DOF, deterministically, with enumerable roots and honest failure (no root ⇒ the over-constraint is reported, the prior figure kept). The constructive backbone and the discrete intersection branches are untouched — only the *single* driven parameter is solved, by re-evaluating the existing constructive engine.

**Implementation (additive — no existing path changed).** `evaluate` = `resolveDriven` ∘ `evaluateCore`, where `evaluateCore` is the prior `evaluate` verbatim (so all prior tests are unaffected when no DOF is driven). New: a `coincide` constraint (`solve.ts`), a `solve?: SolveDirective` on on-circle/on-segment points, hidden `~`-prefixed helper points the renderer skips, and a coincidence-check exemption for coincide pairs (their meeting is the goal). The driven trial evaluates with constraint checks **off** (it's searching for where they pass).

**Consequences.** `C = AB∩DE` + `C is the midpoint of OB` now **repositions the chord** so C is the midpoint *and* still on AB and on DE (verified, 4 lock-in tests); the fixed structure (circle, diameter) doesn't move, D/E stay on the circle; with **no** free DOF upstream it stays an honest over-constraint, not a silent wrong figure. (Also fixed a latent bug the case exposed: the English `midpoint of OB` read "of" as the labels O,F.) 685 tests green. **Limitations / next:** drives a single 1-DOF carrier (not a 2-DOF free point, not simultaneous multi-constraint systems); picks the most-recently-added carrier; the alternative roots aren't yet cycleable from the UI. A general multi-DOF solve is future work, but the common bagrut pattern (one accumulating fact pins one DOF) now works. (See Amendment 2 for recruiting MORE DOFs when one isn't enough.)

**Amendment 2 (2026-06-13).** When a constraint's DIRECT carrier can't satisfy it alone — "cannot place F on segment AB so that |DE|=|DF|", F stuck on the segment while |DE| is the far tangent length — `applyStep` no longer gives up. It RECRUITS the free DOFs the constraint transitively depends on (the inscribed triangle's free vertices, found by walking the dependency graph) and turns them, plus the stuck carrier, into joint carriers for that constraint, then runs the coupled solver — i.e. it *reconfigures the figure* to find a satisfying placement ("find a possible case and do it"). Verified: DE=DF holds (|DE|=|DF|), F stays on segment AB, A,B,D stay on the circle. Purely additive — recruitment only fires after the normal solve fails, so every passing case is unchanged (712 tests green).

**Amendment (2026-06-13, same day).** Extended to drive an **on-circle** DOF (not just on-segment) and to solve **coupled** constraints. `driveOrCheck` now marks a free on-circle ref as the carrier when no on-segment one exists (so `|ED| = 7` repositions a chord endpoint). When two-or-more carriers are coupled — e.g. `C = midpoint of OB` drives one chord endpoint while `|ED| = 7` drives the other, and the length depends on where the first lands — `resolveDriven` solves them **jointly**: coordinate descent (grid `argMin` per DOF, so every branch is considered) for a global start, then **Nelder–Mead** to converge out of the narrow trough coordinate descent stalls in, minimising the summed squared residual; an unreachable target still leaves the honest over-constraint. A single DOF keeps the deterministic `drivenRoots` + branch-index path (alternatives). Verified: a chord constrained to pass through the midpoint of OB *and* be length 7 satisfies both with D,E on the circle (689 tests green). Still open: 2-DOF free points as carriers; UI-cycling the alternative joint solutions.

## ADR-029 — Implicit circle reference: the parser resolves "the circle" to the figure's one circle

**Status:** Accepted (2026-06-13) · realises the implicit-reference item deferred in [ADR-022](#adr-022)

**Context.** The deterministic parser is context-free — it only knew a circle if the utterance *named* it ("circle O"). But once a circle exists, students naturally refer to it without naming: `המשיק בנקודה D והמשך AB נפגשים בנקודה E` ("the tangent at D and the extension of AB meet at E"). With no named circle the tangent rule bailed → the input escalated to the LLM, which decomposed it **and invented an extra point F** (representing "the extension of AB" as a point) — confusing the student, who never wrote F. This recurred across several circle constructs (a tangent, a chord, a radius set, "the circle").

**Decision.** Give `parse` an optional **`ParseContext`** carrying the centre letters of circles already in the figure; the App passes them from the current construction. A `resolveCenter(s, ctx)` helper returns the named centre, or — when none is named and there's **exactly one** circle — that circle's centre (0 or 2+ ⇒ null, so it stays ambiguous and escalates rather than guessing). The circle-dependent rules (tangent∩line, chord, diameter, arc-midpoint, parallel∩circle, the drawn tangent) use it. The `tangentLineIntersection` rule was also rewritten to read **both** phrasings (result-first and meet-at-end) and to treat "the extension of AB" / "המשך AB" as just the line AB. The LLM system prompt gained a rule: **only introduce points the student names** (don't invent intermediate points) — so the residual LLM path stops adding phantom F's too.

**Consequences.** The reported case now parses **deterministically** (offline, no LLM, no F) to a tangent ∩ AB = E; `chord AB` / `diameter DE` resolve the one circle; a named circle still works; with **0 or 2+** circles an unnamed reference escalates instead of misparsing. The change is backward-compatible — `parse(s)` (no context) behaves exactly as before, so all prior tests pass. 711 tests green. Still context-free: `point-on-circle` ("A on the circle") and inscribed shapes don't yet consult the implicit circle.

## ADR-030 — A constraint drives a FREE vertex (2 DOF); regular shapes stay rigid

**Status:** Accepted (2026-06-13) · realises the "2-DOF free point as carrier" item left open by [ADR-028](#adr-028); refines [FR-EN-11](02-requirements.md)

**Context.** ADR-028 made an accumulating constraint *reshape* the figure by driving a 1-DOF parametric carrier (on-segment `t`, on-circle `theta`), and Amendment 2 recruited such DOFs from ancestors. But a constraint on a shape whose referenced vertices are **free points** (2 DOF each) — e.g. `מקבילית ABCD` then the diagonal `AC` then `|AB| = |AC|`, where a parallelogram's A,B,C are free — had no parametric DOF to drive, so it fell through to a pure over-constraint *check* and was wrongly rejected as impossible, even though a parallelogram with side = diagonal plainly exists.

**Decision.** Extend the driven-DOF mechanism to free vertices. (1) `FreePoint` gains an optional `solve?: SolveDirective` (the free-point analogue of the parametric one). (2) `driveOrCheck`, after finding no on-segment/on-circle carrier, drives a **free, non-pinned, non-rigid** referenced vertex — the most-recently-added one, so earlier/base vertices stay put. (3) `resolveDriven` routes free carriers to a new `resolveFreeDriven`: it minimises Σ residual² + λ·Σ‖p−p₀‖² (a tiny regulariser that picks the configuration **nearest** the current one — a single equation leaves a solution manifold) by Nelder–Mead seeded at the current positions with a figure-scaled simplex step and a few cardinal restarts, then **polishes** with the regulariser dropped so the result lands exactly on the constraint (tolerance 1e-6). (4) A **degeneracy guard**: the solution is accepted only if it satisfies every constraint AND no two referenced points collapsed together (`degenerateSpread`); otherwise the original figure is kept so the honest "over-constrained … cannot hold" check fires (a parallel/ratio constraint a figure can't meet is otherwise "satisfied" by shrinking a segment to ~0).

**Rigid shapes.** A **square** is fully committed (equal sides, right angles), so a constraint contradicting it is a genuine over-constraint, not a reshape. Its base vertices are tagged `rigid` (via `placeBase`) and the driver skips them — `|AB| = 7`, `|AB| = 2|BC|`, `AB ∥ BC` on a square all stay honest over-constraints. **Generic** shapes (parallelogram, quadrilateral, triangle, trapezoid) and the semi-regular rectangle/rhombus leave their vertices drivable, so e.g. sizing them with a distance constraint reshapes rather than rejects.

**Consequences.** `|AB| = |AC|` on a parallelogram now reshapes it (base AB fixed, C moved onto the |AB|-radius circle, D re-derived; verified |AB| = |AC| and D = A + C − B). The square stays rigid (3 prior over-constraint tests still pass, now via the `rigid` tag). Purely additive — free-point driving only fires when no parametric carrier exists and the vertex is non-rigid, so every prior case is unchanged. 715 tests green. **Limitations / next:** free-point driving picks one vertex and regularises to the nearest solution (no UI cycling of the continuous alternative family yet); an explicit shape *dimension* (`square side 5`) isn't yet a first-class constraint, so rectangle/rhombus sizing is allowed but not range-checked; mixing free-point and parametric carriers in one solve isn't exercised.

## ADR-031 — Symbolic measures: named variables that set a relation, plus on-figure measure labels

**Status:** Accepted (2026-06-14) · builds on the proportion of [ADR-021](#adr-021)/`set-ratio` and the driving of [ADR-028](#adr-028)/[ADR-030](#adr-030); realises [FR-RN-2](02-requirements.md) and adds [FR-IN-6](02-requirements.md)

**Context.** Bagrut givens are overwhelmingly *relational*: "AB = 3x", "DF = x", "∠ABC = 2α", "∠DEF = α". They set a relation between measures **without fixing a number** — the figure is drawable (it scales freely), the relation is reused as more givens arrive, and the *student* solves for the unknown (the tool never does). The engine could already express a *direct* proportion (`AB = 3 DF` → `set-ratio`), but had no notion of a named unknown shared across statements, so the natural phrasing failed to parse. Separately, textbooks **print the measure on the figure** ("3x" along a side, "37°" at an angle); the app rendered no measure labels at all (FR-RN-2, a Must, was unimplemented).

**Decision.** Add a **variable layer** on the existing compiler-style pipeline, and **render measure labels**.

*Conventions (settled with David).* A variable is one **lowercase** letter — **latin for lengths** (`x, y`), **Greek for angles** (`α, β, γ`); points stay uppercase, so a variable and a point never collide. Labels are **on by default** with one global hide toggle. Once a variable gets a value, the label shows the **resolved number** (`3x` → "12"), not the expression. Greek letters are hard to type, so the input has small **α/β/γ/δ/θ insert buttons**.

*Architecture — a middle-end.* The parser stays a context-free front-end but may now emit a few **store-level `SymbolicCommand`s** the engine doesn't understand — `measure-length`, `measure-angle`, `set-var` (`AnyCommand = Command | SymbolicCommand`). The store's `replay` builds a **symbol table** over the enabled facts and **lowers** (`src/engine/lower.ts`) each symbolic command into ordinary engine commands: the *first* binding of a variable is the free **representative** (no constraint — the figure scales), each later one links to it as a `set-ratio` (lengths) or the new **`angle-ratio`** constraint (angles), and a known value resolves every binding to an absolute `set-distance`/`set-angle`. `replay` also produces a **label map** (`Derived.labels`); numeric measures (`AB = 5`) keep their existing `set-distance`/`set-angle` output and are labelled from those constraints — so FR-RN-2 falls out with no parser-test churn. The renderer gains a `SceneMeasure` primitive (length at the segment midpoint nudged outward, angle at the vertex along the interior bisector), drawn upright like vertex labels and gated on a `showMeasures` flag.

*One engine addition.* A new `AngleRatioConstraint` (`∠1 = k·∠2`) + `set-angle-ratio` command, wired through `solve.ts` (refs/residual/tolerance/describe) and `driveOrCheck`, so it drives a free DOF on the same ADR-028/030 machinery. To let two angle constraints that share all their vertices (e.g. two angles of a triangle, once a value is given) be solved *jointly*, `driveOrCheck`'s free-vertex pick now *prefers* an un-referenced vertex but falls back to any free one — so the second constraint gets a distinct carrier and `resolveDriven`'s coupled solver satisfies both, instead of the second finding everything "pinned" and failing as a check.

**Consequences.** `AB = 3x` + `DF = x` holds `|AB| = 3|DF|` as the figure flexes; `x = 4` makes them 12 and 4; `∠ABC = 2α` + `∠ACB = α` holds the 2:1 angle relation and `α = 30` resolves to 60°/30°; a numeric `AB = 5` shows "5". Labels render on the figure (blue, upright, toggle to hide). Purely additive to the engine (symbolic commands lower to existing constraints; `build()` lowers internally so all prior call sites are unchanged). 732 tests green (14 new store tests for the relations/resolution/labels, 1 render test). **Limitations / next:** a variable links measures of one kind (a length variable and an angle variable are independent — by design); multi-term expressions (`AB = 2x + 1`) and cross-kind algebra aren't supported; the joint multi-constraint solve is heuristic (works for the common triangle/quad cases, not guaranteed for arbitrary tangled systems); right-angle/tick/arc *marks* are still pending.

**Amendment 1 (2026-06-14) — symbolic roots & powers, ∠/° glyphs, two-row symbol toolbar.** Bagrut lengths are often radical or squared (`AD = 12√x`, `AB = x²`). `MeasureExpr`'s symbolic variant gains an optional **`pow?`** exponent (absent/1 = linear, **½ = √**, **2 = x²**, n = `xⁿ`). Two parser rules — `measureSqrt` (`√`/`\sqrt{…}`/`sqrt(…)`) and `measurePower` (`x²`/`x³`/`x^n`) — run *before* the numeric rules, since otherwise `distanceConstraint`/`measureLength` half-parsed `AD = 12√x` → `set-distance 12` (dropping the radical and over-constraining a determined segment — the bug that prompted this) and `AB = x²` → a bare `x`. A **variable** base is symbolic (`coef·base^pow`, resolves when the var is given: `x=4 ⇒ 12√4 = 24`; `x=3 ⇒ 2·3² = 18`); a **numeric** base is concrete (`12√2 ≈ 16.97`, `5² = 25`). Lowering links two *same-exponent* measures as a ratio (the `varⁿ` cancels: `12√x : 3√x = 4:1`, `4x² : x² = 4:1`); *mixed* exponents are nonlinear and stay free labels rather than emit a wrong ratio. The `angle`/`measure-angle` rules also learn the **`∠`** trigger and tolerate a trailing **`°`** (so `∠ABC = 37°` parses like the word). UI: the insert toolbar is now **two labeled rows** — Greek letters (α β γ δ θ) and **Symbols** (√ x² xⁿ ∠ ° ⊥ ∥; ⊥/∥ already parsed as perpendicular/parallel constraints). Also (same session, separate fix): the LLM fallback emits its canonical steps in the **student's language** so escalated steps display in Hebrew. 749 tests green (+7 √, +7 power/glyph). Still out of scope: nested/multi-term radicals, a root/power over a sum, exponents on angles.

**Amendment 2 (2026-06-14) — `π` constant.** `AB = 2π` is a concrete length using π ≈ 3.14159 (a `measurePi` rule before `measureLength`, so π — a Greek letter — isn't read as a free variable). Only the **π glyph** (its toolbar button) is accepted; the word "pi" is deliberately omitted because it collides with a segment named `PI`. 751 green.

## ADR-032 — Triangle congruence (≅) and similarity (~) reshape the figure

**Status:** Accepted (2026-06-14) · realises [FR-EN-12](02-requirements.md); built on the coupled constraint solve of [ADR-030](#adr-030)/[ADR-031](#adr-031) and the composition model of [ADR-013](#adr-013)

**Context.** Bagrut givens often state a *relation between two triangles* — "△ABC ≅ △DEF" (congruent) or "△ABC ∼ △DEF" (similar). The operator confirmed these must be addressable, and chose (over draw-and-annotate) that the figure should **reshape to enforce** the relation, consistent with the tool's "the figure adapts to its givens" philosophy ([ADR-028](#adr-028)). Two blockers stood in the way: (1) the engine placed every disjoint shape at the *same* default template coords, so a second free triangle collided with the first (the ADR-017 coincidence guard rejected it — "A and D would be at the same point"); (2) there was no congruence/similarity vocabulary.

**Decision.** (a) **Place disjoint shapes apart.** `placeBase` (apply.ts) now offsets a shape that shares **no** point with the figure to the right of all existing geometry (max-x + gap), so two independent triangles coexist. Composed shapes (≥1 shared point) are unaffected — stability and all composition behaviour are untouched. (b) **Express each relation as existing constraints — no new engine primitive.** A congruence is **SSS**: three `set-equal` constraints driving the *second* triangle's sides to equal the first's (`|DE|=|AB|`, `|EF|=|BC|`, `|FD|=|CA|`). A similarity is **AA**: two `set-angle-ratio` (k=1) constraints driving the second's angles to equal the first's. These ride the existing coupled solver ([ADR-030](#adr-030)/[ADR-031](#adr-031)), which reshapes the free second triangle. (c) **Parser** (`congruence`, `similarity`, before the shape rules) reads `ABC ≅ DEF` / `triangle ABC congruent to triangle DEF` / `המשולשים ABC ו-DEF חופפים` and the `~`/`similar`/`דומה` forms — `twoTriangles` pulls the first two label-triples from either phrasing order. Using `ParseContext.points`, it emits a `triangle` for whichever isn't already drawn, then the constraints (so a fresh `ABC ≅ DEF` builds both; a relation over two existing triangles only constrains). `≅ ~ ∼ ∽ חופ דומ` join `SHAPE_LEFTOVER` so a shape rule can never half-parse a relation. UI: **≅** and **~** join the symbols toolbar.

**Consequences.** `ABC ≅ DEF` draws both triangles side by side and reshapes DEF to be congruent (verified: corresponding sides equal); `ABC ~ DEF` reshapes DEF to the same angles (verified: angles equal ⇒ sides proportional). All phrasings He/En. Purely additive (the relations desugar to constraints the engine already had; place-apart only affects 0-anchor shapes). 759 tests green (8 new). **Limitations / next:** triangles only (not quad/polygon congruence); the *second*-named triangle is always the one that adapts (no choice of which is fixed); the coupled solve is the heuristic one (robust for a single SSS/AA pair, not proven for a relation tangled with many other constraints); **tick/arc marks** on the corresponding equal sides/angles are still unbuilt (the relation reshapes but isn't yet *marked*) — a natural follow-up. SAS/ASA-style partial givens aren't special-cased (SSS/AA fully determine the shape, which is what a bare ≅/~ asserts).

## ADR-033 — Shapes carry their true degrees of freedom (driveable shape-parameter DOFs)

**Status:** Accepted (2026-06-14) · fixes a systemic template-design flaw; generalises the constraint-driving of [ADR-028](#adr-028)/[ADR-030](#adr-030)/[ADR-031](#adr-031)

**Context.** A reported bug (`BD = 12√2` on a right triangle flagged over-constrained) turned out to be **systemic**: several shape templates *hard-code a dimension* in a derived vertex, so the shape carries one fewer DOF than the real shape and a natural sizing/shaping constraint is wrongly rejected. Audited + verified empirically: **square** (`placeBase rigid` → can't resize), **rectangle** (`perp-offset dist:4` → height frozen), **rhombus** (`rotated angleDeg:60` → angle frozen), **trapezoid** (`scaled-offset k:0.6` → top-base ratio frozen), **right-triangle** (`perp-offset dist:5` → a leg frozen). Fully-flexible shapes (triangle, quadrilateral, parallelogram) were fine — their derived vertices maintain only the *defining* property (`D = A+C−B`) without pinning a free dimension. The operator chose **Approach 1** (make the frozen scalars driveable, preserving the structural shape) over Approach 2 (rebuild shapes from free points + soft constraints, which makes properties drift-prone).

**Decision.** Make the derived-vertex scalars **solver-driveable DOFs**. (a) `perp-offset.dist`, `rotated.angleDeg`, `scaled-offset.k` gain an optional `solve` directive (default unset ⇒ fixed, so every default figure is byte-identical and the corpus is untouched). (b) A **generalized solver** `resolveMixedCarriers` (evaluate.ts) drives a *heterogeneous* DOF vector — free-vertex coords (2), parametric `t`/`θ` (1), and the shape scalars (1) — jointly, each **normalised per-coordinate** by its own magnitude (so a short leg next to a long one keeps fine resolution), with a **degeneracy penalty** in the cost so the solver can't satisfy a length by collapsing the figure. `resolveDriven` routes any case containing a shape scalar here; pure free-point and pure single-parametric cases keep their existing (tested) paths. (c) `driveOrCheck` (apply.ts) drives a referenced shape scalar (a rectangle's height via `BC`); the **recruit** (`freeDrivableAncestors`, step.ts) reaches a scalar behind a derived vertex (a rhombus's angle behind C, a rectangle's height behind D) and marks the figure's reachable DOFs, the joint solver moving only the ones that matter. (d) Template fixes: **square** drops `rigid` (A,B drive; an impossible constraint like a non-90° angle is still rejected by the satisfied/degeneracy guards); **rectangle**'s D becomes a `parallelogram-vertex` so its height is a *single* DOF (BC and AD can't diverge).

**Consequences.** All five shapes now reshape to a sizing/shaping constraint: `square AB=10` → 10×10, `rectangle BC=10` (height, AD follows), `rhombus ∠ABC=80` (sides stay equal), `trapezoid DC=2` (stays parallel), `right-triangle CB=12` (∠C stays 90°) — and a length given like `BD=12√2` sizes the figure *through* a bisector/incenter construction. Impossible constraints (square side=diagonal, non-90° square angle) still reject honestly. Defaults unchanged.

**Amendment 1 (2026-06-14) — relative residuals close the coupled case.** The operator's full figure (`BD=12√2` AND `AC=7k/5`, *both* routed through the incenter `D`) initially landed visually-exact but a hair past the **fixed** `1e-6` tolerance (which is ~7 digits on a figure of size ~20 — unreachable for a derivative-free solve through a construction). Fixed two ways, both **per-constraint-scale-relative**: (1) the length-unit tolerances (distance/equal/ratio) are now `max(1e-6, 2e-4·scale)` where `scale = constraintScale(con)` is the constraint's OWN characteristic length (`|value|`, `|cd|`, `k·|cd|`) — NOT the figure span, which a far-off point could inflate; (2) `resolveMixedCarriers` minimises the sum of squared **relative** residuals (`residual ÷ constraintScale`). The relative cost is *un-gameable by shrinking* — a wrong ratio stays ~1% relative however small you make the constrained part, and a collapse (scale→0) blows the cost up — so the solver finds the genuine spread-out solution instead of a degenerate fake (this also let the per-constraint degeneracy penalty be dropped). Result: the figure now solves to the **real triangle** (CA=5.6, CB=19.2, k=4 — the actual bagrut answer), `AC/AD=1.4000` exact, **green**. A scale-free constraint (angle, ∥/⟂) keeps its fixed tolerance. 770 tests green (9 shape-DOF incl. the full coupled bagrut figure; the old "square is rigid" tests updated to assert sizing). **Remaining limits:** triangles/quads only for the shape set; a *very* tangled system (many constraints sharing DOFs through several constructions) still relies on the heuristic solver converging.

## ADR-034 — `R`/`r` reserved as the radius symbol (a size, not a vertex)

**Status:** Accepted (2026-06-14) · extends the symbolic-measure layer of [ADR-031](#adr-031)

**Context.** A radius is conventionally written `R`, and givens are stated relative to it ("AC = 1.6R", a chord = 1.6 radii). Two bugs surfaced in debug: (1) `circle … radius R` silently dropped the `R` — the radius regex only matched a *number*, so the circle defaulted to radius 5 and `R` was never defined; (2) `AC = 1.6R` mis-parsed to `set-distance AC = 1` — the numeric rule's `\b` after `1.6` failed before the `R`, so it half-read just `1`, producing a tiny segment that over-constrained the figure ("B and C would be at the same point"). The symbolic-measure layer (ADR-031) keys variables to **lowercase** latin/Greek letters, so an **uppercase** `R` wasn't a candidate variable; meanwhile `R` is a legitimate **vertex** label (e.g. `quadrilateral PQRS`).

**Decision.** Reserve `R`/`r` as the radius symbol **in size contexts only** — never globally banned as a vertex, so `PQRS` and `AB = RS`/`AB = AR` (R the 2nd letter of a segment) keep reading R as a point. The distinction is syntactic: `R` is the radius when it follows a number/coefficient or the word "radius", and is *not* followed by another letter (the existing `(?![a-zA-Z])` guard already gates this). Concretely: (a) a shared `parseRadius` helper reads `radius 5` (numeric) **or** `radius R`/`radius r` (symbolic), used by both the `circle` and inscribed-polygon rules; a symbolic radius keeps the circle's concrete default radius (5) and emits a `set-var R = 5` so the variable is **pinned to the circle's radius**. (b) `measureLength`'s RHS variable class gains uppercase `R` (`LVAR`), and both `R`/`r` normalise to the canonical `R` (`RADIUS_VAR` in types.ts). (c) The radius symbol **stays symbolic on the figure** — `measureLabelText` shows "1.6R" even though `R` has a numeric value (it's a size relative to the radius, not a number the student chose). (d) Minor English parity: "around O" now reads O as a centre. The whole change lowers through the existing ADR-031 machinery — `AC = 1.6R` becomes `measure-length` var R, which (R having a value) lowers to `set-distance AC = 1.6·5 = 8`.

**Consequences.** `circle O radius R` + `AC = 1.6R` constrains `|AC| = 1.6·radius` and labels the chord "1.6R"; `AC = 2r` reads the same symbol; `R` remains a vertex inside a letter-run. With no radius-`R` circle present, `R` is an unresolved variable like any other (free representative + ratio), so it degrades gracefully to a label. 795 tests green (+6: parse of `circle … radius R`/Hebrew, `AC = 1.6R`/`2r`, R-stays-vertex, the constrained-and-labelled full flow). **Limits:** one shared radius symbol (multiple circles of different radii would alias `R`); the radius value is the concrete default (5), not itself a free DOF the "show another configuration" sampler resizes.

**Amendment 1 (2026-06-16) — `R` auto-binds to the radius even when not declared.** Originally `R` only got a value when the circle was written `radius R` (which emits `set-var R = 5`); a circle declared `radius 5` (numeric) left `R` unbound, so a later `OC = 0.5R` was a free label and didn't reshape (the operator saw "nothing happened" until a second `R` measure formed a ratio). Since `R` is *reserved* for the radius, it should always mean it: `buildSymTab` now, when a measure uses `RADIUS_VAR` and no explicit value was given, binds `R` to the first numeric-radius circle's radius. So `OC = 0.5R` sizes against the radius (`|OC| = 2.5`) with no `radius R` declaration — and it drives the chord's midpoint via the derived-ancestor recruit (FR-EN-11). An explicit `set-var R` still wins (no change to the `radius R` flow).

## ADR-035 — Relabel a point as a fact-list rewrite, kept out of the engine

**Status:** Accepted (2026-06-14)

**Context.** Textbooks letter their figures in ways the auto-layout doesn't always reproduce: naming order (base-then-counter-clockwise) and the flip/rotate controls cover the corner cases, but **interior / derived points** (an intersection, a midpoint, a foot) get a construction-order auto-name (`M`, `N`, …) the student can't pre-choose. The operator wanted to match the book's exact lettering (e.g. the rectangle's `E F G H O`). Two routes were offered — a rename command, or documenting naming tricks — and the operator chose **both**.

**Decision.** A **rename is a relabel over the ordered fact list, not a geometry command.** A new store action `rename(from, to)` rewrites that one letter across every fact (and its display utterance), so the figure replays geometrically identical under the new name; it's a single undo entry. The rewrite is safe because of a standing invariant: **point ids are always single uppercase letters**, while line ids (`bis-…`) and circle ids (`circle-O`) are multi-character — so an exact single-letter substitution can't touch a line/circle id, a keyword, or a measure variable (the `expr` sub-object is skipped outright). The rename is recognised by a dedicated `parseRename` boundary (He/En: `rename E to G`, `שנה שם E ל-G`, `החלף E ב-G`) that the App intercepts **before** `parse()`, so it never enters the parser's command stream, the engine's `Command` union, or any exhaustive switch — zero blast radius on the construction pipeline. It refuses to relabel onto a letter already in use (that would silently merge two distinct points), reporting `target-taken` / `no-source` / `same` for the UI. The naming-order + orientation levers are documented in [12-letter-placement.md](12-letter-placement.md) (the "both" of the operator's choice).

**Consequences.** Any arrangement is reachable: name + flip for the corners, then rename the interior points to the book's letters. Realises [FR-HS-7](02-requirements.md). 814 tests green (+9: the He/En parse forms, cross-fact rewrite, geometry-preserved, the validation refusals, `expr` left intact, undo). **Limits:** the utterance relabel is a literal uppercase-letter swap (fine for the short canonical phrasings; a freeform LLM utterance keeps its original wording on the row); renaming a circle's centre leaves the circle's opaque `circle-<old>` id unchanged (it still resolves — only cosmetically stale). Shipped alongside two render polish items in the same session: textbook-small vertex dots (4px → 2px) and PNG **save**/**copy-image** from the canvas (realising [FR-HS-5](02-requirements.md)).

## ADR-036 — A drawn line named by two points creates them as fixed markers (`on-line`)

**Status:** Accepted (2026-06-14)

**Context.** A tangent (or any drawn line) is often named by two points — "הישר CD משיק למעגל בנקודה T" / "line CD tangent at T". The `tangentLine` rule read only the circle and the tangency point `T` and **silently dropped the `CD` name**, so C and D were never created; a later step referencing one (`AC ⊥ TC`) failed with "references an unknown point". The engine had no notion of a point *on a line* — points sit on a segment (two endpoints), on a circle, or are a derived intersection/foot/midpoint, but a drawn tangent is an infinite `Line` (anchor + direction) with nothing to ride it. Offered drivable-along-the-line points vs. fixed markers, the operator chose **fixed markers**.

**Decision.** A new 0-DOF point kind **`on-line`** (`{ line, offset }`) positions a point at `anchor(line) + offset·dir(line)` — it rides whatever the line's `LineSpec` resolves to, in the same interleaved point/line/circle sweep as `line-intersection` and `foot`. A tangent named `CD` at `T` emits the `tangent` line plus two `point-on-line` markers at `±TANGENT_MARK` (5) from `T` (the tangent's anchor), so C and D straddle T along the tangent (⟂ the radius) and are immediately referenceable. The plain single-point tangent (`tangent to circle O at A`) is unchanged — the markers appear only when the line carries two extra labels. `on-line` is **fixed** (a derived 0-DOF point), per the operator's choice: a later constraint can reference C/D but cannot slide them along the line (the drivable-`t` variant is deferred — it would need an `on-line` carrier in `solve.ts` like `on-segment-solved`).

**Consequences.** "Name a tangent by two points" works end-to-end: the operator's circle/diameter/`T`/tangent-`CD` figure now creates C and D on the tangent, and a following `segment TC` / `AC` resolves. 820 tests green (+6). The `on-line` primitive is reusable for naming bisector/perpendicular/parallel lines by points.

**Amendment 3 (2026-06-15) — the named-line markers are widened beyond the tangent to perpendicular & parallel lines.** The tangent's marker emission was extracted into a shared `lineMarkers(lineId, labels)` helper (1 label → a single marker at +offset from the line's anchor; 2 → a straddling ±offset pair). A new `lineNameLabels(s, exclude)` reads the 1–2 point labels naming a drawn line (the labels right after the line word — "line PQ …" / "הישר PQ …", anchored on the line word so it can't misfire on a keyword), excluding the points that already define the line. `perpendicularLine`/`parallelLine` now emit a marker for the named far end: "line PQ through P ⟂ AB" creates `Q` on the perpendicular at +offset from the through-point `P` (the line's anchor), referenceable like the tangent's C/D. An unnamed "line through P ⟂ AB" still creates no marker. The **bisector** named by a point is unchanged — it already had its own path (`AD bisects ∠BAC` → a `line-intersection` placing the point). +3 parser tests, 889 green.

**Amendment 4 (2026-06-16) — a named perpendicular REPOSITIONS pre-existing loose endpoints; the cut-point is created on the reference.** Operator built `segment AB`, `segment CD` (a *loose* free segment), then `CD אנך ל-AB בנקודה F` ("CD ⟂ AB at F"). Several arrangements all broke: anchoring the perpendicular on a not-yet-made `F` ("unresolved dependencies"), or re-creating the existing C,D as markers ("'C'/'D' already defined"); a constraint-only attempt (`set-perpendicular CD⟂AB` + `F = CD∩AB`) made CD perpendicular but the **segments didn't visually cross** — F floated off both (the constraint pins the angle, not the position), and five constraint formulations either left F off-segment or over-constrained. **Resolution (operator's choice via AskUserQuestion): an engine change so the construct path can reuse the loose endpoints.** Two parts: (1) **`perpendicularLine` always CONSTRUCTS** — a `perpendicular-line` through the cut-point `F` (created as a `point-on-segment` on the reference AB when new, i.e. the foot) with the named endpoints `lineMarkers` straddling `F`; (2) an **`on-line` marker may REPOSITION a loose free point** — `commandConflict` exempts `on-line` over an existing free-point (mirroring the `on-circle` exemption), and `apply`'s `point-on-line` case **replaces** a free point of that id with the marker (a structural/derived point is left untouched). So a bare `segment CD` followed by `CD ⟂ AB at F` moves C,D onto the perpendicular, centred on `F` (which lands on AB) — a clean centred cross, no redefinition error, no solver fragility. Works for every arrangement (name new/old × cut-point new/old). The constrain-style branch added the prior day is removed for ⟂ (parallel keeps its `set-parallel` branch — parallels have no cut-point). Regression `existing-segment-perpendicular-cuts-at-new-point` now asserts the clean cross (E on AB *and* between C,D). 897 green.

**Amendment 1 (2026-06-14) — the markers are DRIVABLE after all.** The operator clarified that C/D exist "just to create the initial segment but later need to adjust to the constraints" — i.e. the drivable option, not fixed. So `OnLinePoint` gained the standard `solve?: SolveDirective`, making its **offset a 1-DOF the constraint solver drives** (the on-segment analogue for an infinite line). Because the offset is *unbounded*, it can't use the bracketed range-solve (on-segment `[0,1]` / on-circle `[0,2π]`); it routes through the seed/scale optimizer (`resolveMixedCarriers`, the same path as the shape scalars) — `carrierSpec`/`setCarrierVals` gained an `on-line` case. In `driveOrCheck` the on-line carrier is tried **right after on-segment, before on-circle / free-vertex**: a marker on a drawn line is an *explicit slider*, so a constraint referencing both the marker and a structural point (e.g. `AC ⟂ TC`, with `C` on-line and `T` on the circle) moves the **marker C**, leaving the tangency point `T` put. Verified: `C` slides along the tangent to the perpendicular foot, staying on the line. 821 tests green. **Limits:** the default offset (±5) is still a fixed *starting* position (cosmetic — the visible tangent is drawn clipped anyway).

**Amendment 2 (2026-06-15) — a free (un-driven) marker's offset is now sampled by "show another configuration".** Closing the Amendment-1 limit: `applySeed`/`freeDofs` (`sample.ts`, ADR-018 Stage 1) now treat an `on-line` marker with `solve === undefined` as a free DOF. The sampler scales its signed `offset` by 0.4×–2.4× (sign preserved, so a pair straddling the anchor — a tangent's C at +offset, D at −offset — keeps straddling; the segment between them still spans the touch point, just a different length), seeded and deterministic like the other DOFs. A marker the constraint solver has claimed (`solve` set, Amendment 1) is left alone. So an undriven tangent's C/D now slide along the tangent across configurations, and the figure reports its remaining freedom honestly. +1 sample test, 886 green.

## ADR-037 — Two circles tangent to each other (mutual tangency)

**Status:** Accepted (2026-06-14)

**Context.** "מעגל O ומעגל P משיקים זה לזה בנקודה M" / "circle O and circle P are tangent at M" — the textbook two-circles-touching picture (e.g. the bagrut figure with `O₁`, `O₂` side by side, touching at `M` on the centre line). The engine had `circle-circle-intersection` (two circles *crossing* at 0/1/2 points) but no notion of **mutual tangency** (touch at exactly one point). The `משיק` keyword was being grabbed by the tangent-**LINE** rule, which drew a stray tangent at `M` to one circle and left the two circles overlapping at their default (near) positions — a wrong figure.

**Decision.** A new `circles-tangent` command (`{ circle1, circle2, at, external }`), parsed by a rule that fires on **two named circles + a tangent keyword** (a single-circle "tangent to circle X" stays the tangent-line rule) and runs **before** `tangentLine`. Default **external** (`r1+r2`); "internally"/"פנימית" selects internal (`|r1−r2|`). The engine expresses it with **existing primitives**, no new solver math: in `applyCommand` it reads the two circles' (length) radii, places `at` as an **on-segment point** on the centre line at fraction `r1/d` (the touch point), and adds a **distance constraint** `|c1 c2| = d` that the generic `driveOrCheck` uses to **move a free centre** to the touching distance (ADR-014/030). So stating the relation *reshapes* the figure — the circles separate until they kiss at `M`.

**Consequences.** The operator's two-circles figure now draws correctly: equal-radius circles end up centre-to-centre `r1+r2` apart, `M` at the midpoint on both circles, touching at one point. 829 tests green (+4). **Limits:** needs **concrete (length) radii** — a `through`-a-point radius isn't known at apply time, so tangency isn't imposed for those yet; internal tangency with equal radii is degenerate (skipped); the centre that moves is whichever the free-vertex driver picks (usually the later-named one).

**Amendment 1 (2026-06-14) — a radius is a flexible DOF, so internal tangency never "can't be done".** First shipped a rejection ("internal tangency needs different radii") for two equal circles. The operator pushed back: *"radius should be a DOF and not fixed, so there's no reason two circles can't meet the request"* — the same philosophy as [ADR-033](#adr-033) (a stated size is a default, not a hard pin). So instead of rejecting, the apply step **flexes a radius**: for internal tangency of (near-)equal circles it shrinks the **second** circle to half the first's so it sits inside, then places the touch point and the centre-distance as usual. The bigger circle is always the outer one; `M` lands on the ray from the outer centre through the inner, at the outer radius. The only remaining `circles-tangent` rejection is the radius-through-a-point case (its radius isn't known at apply time). **Interim caveat:** the shrink is a hardcoded default (½), and the step row still shows the originally-typed radius — a cosmetic mismatch. The **principled version is queued** (see the radius-as-first-class-solver-DOF note in PROJECT-MEMORY): make a circle's radius a real carrier in `resolveMixedCarriers`/`driveOrCheck` so a tangency (or any relation) sizes it generally and a later "radius = 3" pins it.

**Amendment 2 (2026-06-15) — the inner radius becomes a genuine, honest DOF (replaces the ½ hack).** Amendment 1's ½-shrink was a hidden, frozen number. Made the radius a real DOF, scoped **Light** (operator's choice; the full "radius-aware residual" path was declined since the constraint/residual system is position-only and radii aren't positions, and internal-equal tangency is *underdetermined* anyway — any inner radius ∈ (0, r₁) is valid). For internal tangency of equal circles the **second circle gets a derived radius** — a new `RadiusSpec` variant `{ via: 'tangent-inner', outer }` resolving to `r = r(outer) − |centre − centre(outer)|` (the largest circle inside `outer` and tangent to it). Its **centre stays a free point** (seeded at a gap of r₁/2 ⇒ a default inner radius of r₁/2, byte-identical to the old default), so: the **radius flexes** as the centre moves, **"show another configuration" varies it** (the free centre resamples; the radius adapts and tangency is preserved *structurally*, no baked distance constraint to break), and the **drawn radius is honest** (computed, not a phantom typed value). The touch point `M` is a new 0-DOF `radial-toward` point (on the outer circle, on the ray toward the inner centre) so it tracks the centre under resample. `resolveCircle` is threaded the resolved-circles map (the outer resolves first); `scene.ts` mirrors the derivation when drawing. External tangency and non-equal internal tangency are **unchanged** (typed radii kept — a radius only flexes when the fixed-radius figure is impossible). 836 tests green (+4: derived-radius honesty, resample-varies-radius-while-tangent, external-unchanged, plain-circle-unchanged). **Limits:** the inner radius isn't independently *pinnable* by a `radius = k` on this construct (it's derived from the gap); a general radius-sized-by-relation still wants the full carrier path, left for if a corpus figure needs it.

## ADR-038 — Structural-first theorem detection; geometric analysis deferred to opt-in Reveal

**Status:** Accepted (2026-06-15)

**Context.** Phase 6 ([Pedagogy §3–4](10-pedagogy.md)) surfaces relevant theorems as the figure is built. The defining question: does `detect()` read the **construction facts / dependency graph** (what the student *typed*) or the **computed coordinates** (what the figure numerically *is*)? Settled in the same design conversation: the **surfacing model** (delta-driven, an accumulating feed pinned to facts, with graded confidence) and what to do with the **geometric** layer the structural path leaves uncovered.

**Decision.**

1. **Structural-first detection.** A theorem's hypothesis is matched against the **typed construct and its dependency parents**, not against numeric coordinate measurements — built a diameter + an inscribed point subtending it → raise 103/104, because *that is what was constructed*. Each catalog theorem gets a structural matcher keyed on construct + parent-relationship pattern; the [Pedagogy §4 trigger map](10-pedagogy.md#4-construction--theorem-triggers-the-pedagogical-payload) is the spec for these matchers.
2. **Whole-figure analysis, delta presentation.** Each step the matchers run over the **entire accumulated figure** (all enabled facts), *not* just the last fact — a hypothesis can span several facts and be completed (or change tier) only by a later one, and an already-shown theorem's confidence must update as the figure grows. What *surfaces* is the **diff** (newly-satisfied theorems + tier/relevance changes); results live in a **growing feed beside the canvas**, each entry attributed to the fact that completed/last-changed it, updated in place (not re-listed), and dropped/downgraded when a fact it depended on is removed (FR-TH-1/2).
3. **Graded confidence as ordinal tiers** — *certain / possible / recall* — driving order and colour (FR-TH-3). Not a continuous probability: structural matching yields "hypothesis met / one given away / merely evoked," which maps to tiers, and a fabricated percentage would undercut the catalog's exact-and-citable authority (Pedagogy §5.4).
4. **Geometric (coordinate) detection is deferred and re-homed.** It is *not* auto-fed as theorems — that would violate "no unsolicited clues" (Pedagogy §5.1). The same coordinate analysis instead powers an **opt-in Reveal** feature (FR-RV-\*) in a **separate later phase** ([Plan Phase 9](09-implementation-plan.md#phase-9--reveal--figure-unmasking-deferred)): the student presses a button to unmask equal segments/angles/measures. Theorems (Phase 6) and Reveal (Phase 9) are independent — either ships without the other.

**Why.** (1) Faithful to the pedagogy — the theorem is about *the given the student entered*, not a numeric accident; trace-to-trigger is exact and free (the parent facts are already known). (2) Reuses the dependency graph; no floating-point tolerance tuning in the must-have path. (3) Cheaper to build and test — the Phase 6 gate is symbolic and deterministic. (4) Splitting geometric analysis into opt-in Reveal resolves the tension between "reach your own conclusions unclued" and "it's valuable to see what the shape really is" — the analysis exists, but only on demand.

**Consequences.** A chord that *happens* to pass through the centre but was **not** built as a diameter won't trigger 103 until the geometric layer lands behind Reveal — accepted: coincidental configurations are rarer than named ones, and the structural path covers the corpus. The Phase 6 gate: expected **P/C** IDs surface with correct tier; **O**-tagged items, definitions, and area/perimeter formulas never surface.

## ADR-039 — Inequalities between named measures ("α < β") actively reshape the figure

**Status:** Accepted (2026-06-15) · extends the symbolic-measure layer of [ADR-031](#adr-031); rides the coupled solver of [ADR-030](#adr-030)/[ADR-033](#adr-033)

**Context.** Bagrut problems routinely state an *ordering assumption* — "נסמן ∠BAP = α, ∠ABP = β, **α < β**". This is not a metric given (it fixes no number); it tells the reader which configuration the figure is drawn in. The tool had no notion of it: the parser dropped `α<β` (→ LLM, which can't turn an inequality into a canonical command either), so it errored. And because the figure's residual freedom is sampled by "show another configuration", the rare configurations that *happen* to satisfy α<β were almost never reached — empirically, on the operator's actual Q5 figure (median BD, E on BC, P = AE∩BD, |BP|=3|PD|, AE⊥BD) only **≈3.6 % of seeds** had ∠BAP < ∠ABP (max achievable gap ≈ 21.7°). The operator pressed "another configuration" eight times and never saw it — a misleading figure that contradicts the stated assumption. The operator chose (over selection-only or label-only) that the inequality must **actively reshape** the figure so the relation is visibly true.

**Decision.** Add an **order (inequality) constraint** as a one-sided residual, solved jointly with whatever DOFs are already moving.
- *Parser* — `measureOrder` reads `α < β` / `x > y` / `α ≤ β` (and ascii `<=`/`>=`) between two **bare** single-letter variables → a store-level `measure-order` `SymbolicCommand`. A `<` button joins the symbols toolbar. (Coefficiented/numeric comparisons fall through — a documented limit.)
- *Lowering* ([lower.ts](../src/engine/lower.ts)) resolves each variable to the measure it names (via the symbol table) and emits `set-angle-order` / `set-length-order`, ordering them so the first listed is the smaller. Undefined vars, mixed kinds, or non-bare bindings lower to nothing (harmless no-op).
- *Engine* — new `AngleOrderConstraint` / `LengthOrderConstraint`. The residual is **one-sided**: `max(0, smaller − larger + MARGIN)` — zero across the whole satisfying region, so it has no sign change for the bracketing root-finder and is therefore **pushed as a check**, never given a dedicated carrier; `applyStep`'s `recruitFreeDofs` (or the augmentation below) supplies the DOFs. Two thresholds **decouple "looks clearly smaller" from "is at all smaller"** (types.ts): the solver *aims* for a visible **MARGIN** (8° / 12 % of the longer length) so the figure isn't a misleading near-tie, but *accepts* any config in order by at least **MIN_GAP** (1° / 2 %), so a figure whose geometry only permits a small gap is still accepted rather than wrongly flagged a contradiction.
- *The key fix* — an inequality is satisfied by a **region**, not a point, so it never owns a carrier; when the DOFs it needs are already driving another constraint (here the |BP|=3|PD| recruited A, B, C, E), `recruitFreeDofs` finds nothing un-driven and the joint solver — which only minimised *carrier* constraints — ignored the inequality. Fixed with `withOrderCons` (evaluate.ts): every solver path (`resolveMixedCarriers`, `resolveFreeDriven`, the coupled `resolveDriven`) now **also folds in the construction's order constraints**, so they are minimised *jointly with the already-moving DOFs* — the solver picks the part of the existing solution family where the order holds. Surgical: only figures that contain an order constraint are affected.

**Consequences.** `α<β` on the Q5 figure reshapes it deterministically so ∠BAP ≈ 41° < ∠ABP ≈ 49° (the targeted ~8° gap) while `|BP|=3|PD|` and `AE⊥BD` still hold — every seed, no error. The operator's exact 10-step sequence is a permanent end-to-end scenario (`alpha-less-than-beta-reshapes`). **876 tests green, build clean.** **Limits / next:** only bare single-letter variables compare (no `2α < β`, no numeric/`∠ABC < ∠DEF` direct forms); the order biases toward a fixed visible margin (not student-tunable); if the inequality is geometrically incompatible with the other givens it honestly keeps the prior figure and flags the contradiction.

## ADR-040 — A secant's second crossing is "the OTHER crossing", not a fixed branch index

**Status:** Accepted (2026-06-17) · refines the `line-circle` point of [ADR-020](#adr-020); fixes a class of resample/cycle instability surfaced building the two-circles secant-web figure

**Context.** A secant drawn through a point that already lies on the circle — "the line AC cuts circle O at D" where A is on O, or "from C the line CB cuts O at E" where B is on O — meets the circle at the known point and at one new point. The engine modelled the new point as `line-circle` with a fixed `branch` index. But `lineCircleIntersect` returns its two roots ordered by the line *parameter* `t`, and that order **flips with the line's direction** (the sign of `b = 2·(anchor−centre)·dir`). So as "show another configuration" resamples the free points and the secant turns, the fixed branch intermittently lands on the *known* point, collapsing the new point onto it → "B and E would be at the same point". The figure looked un-resamplable: the operator reported the constraints "weren't kept" across views and it "never looks like the book". A second, compounding defect: the LLM, decomposing "AC cuts the left circle at D", emitted "from A a line cuts circle O at **C and D**", and the parser's existing-point secant branch then **re-placed the existing C onto circle O** — pinning C to *both* circles, so it was dragged to the intersection (or dropped when unsatisfiable).

**Decision.** Two surgical changes.
- *Engine* — `LineCirclePoint` gains an optional `avoid?: Id`. When set, `evaluate` discards every intersection root that coincides (within `LEN_EPS`) with an **already-placed** point — which always includes the secant's known on-circle end — and returns the genuinely new crossing (ties broken deterministically as the root farthest from `avoid`). This is the **"the OTHER crossing"** semantics: stable as the line turns, because it is defined by *non-coincidence with existing geometry*, not by a root index. `branchCount` returns 1 for an `avoid`-pinned point, so it is correctly **not** offered to "show another configuration" (it is determined — [ADR-022](#adr-022)/`cyclableBranch`).
- *Parser* — `secantFromExternal`'s existing-point branch no longer re-places a named crossing that already exists: an existing endpoint is a **direction point** (the line runs through it), never re-pinned onto the circle; only a genuinely new first-crossing is placed on the circle. The new crossing is emitted with `avoid` set to a known endpoint.

**Consequences.** The operator's book figure — two circles meet at A,B; C on the right circle; secant AC cuts the left circle at D; secant CB cuts it at E — now builds with C on the right circle only, D and E genuine second crossings on the left circle, and **holds on every "other view"** (canonical + 8 resamples, all valid — regression `two-circles-secant-web`). **928 tests green, build clean.** **Limit:** if a secant is geometrically tangent (one root) the "other crossing" coincides with the known point — an honest degenerate, surfaced as a coincidence error rather than hidden. Separately, the LLM's "cuts at C and D" labelling (treating an off-circle direction point as a crossing) is a decomposition-quality issue, not a parser defect; the parser now tolerates it correctly.

## ADR-041 — A `concyclic` constraint makes PRE-EXISTING points share a circle (cyclic quad on top of a figure)

**Status:** Accepted (2026-06-17) · a new first-class constraint in the [ADR-021](#adr-021) family; the cyclic-quad analogue of the existing-points circumcircle ([ADR-020](#adr-020))

**Context.** Building a cyclic/inscribed quadrilateral whose four vertices **already exist** — e.g. `משולש CED`, `A על CD`, `B על CE`, then `מרובע ABDE בר חסימה` — was broken. The `inscribedPolygon` rule had an existing-points path only for a *triangle* (three points have a unique circumcircle), so a *quad* fell through to the fresh-circle path and **re-placed A, B, D, E as new on-circle points**, detaching A from segment CD and B from CE (and D, E from the triangle). A second utterance form, "circle through A B E D", hit the `circumcircle` rule, which read only the first **three** of four labels and silently dropped the fourth, so the circle passed through three vertices and missed D. The underlying gap: four arbitrary points are **not** concyclic — being concyclic is a genuine geometric *constraint* (one equation), which the engine had no way to express on existing points.

**Decision.** Add a `ConcyclicConstraint` (`{ type: 'concyclic'; points: Id[] }`) and a `set-concyclic` command, wired through the **generic** constraint machinery — no new point kind, evaluator rule, or solver:
- *Residual* (solve.ts): the signed, length-unit deviation of the points beyond the first three from the **circumcircle of those three** — `0` ⇔ all concyclic, and it sign-changes as a point crosses the circle, so a 1-DOF on-segment carrier solves in closed form (`solveParam`). NaN when the first three are collinear (no stable circle). `constraintScale` = that circle's radius; tolerance is the standard relative length tolerance.
- *Carrier selection* is the existing `driveOrCheck`: it drives whatever free DOF the points expose — an on-segment slide (A on CD), an on-line/on-circle offset, a shape scalar, or a free vertex (`resolveDriven`) — and falls back to a pure **check** (honest over-constraint) when all four are determined. The engine, not the parser, picks the DOF.
- *Parser* (parse.ts): `inscribedPolygon`, when **all** the polygon's vertices already exist, emits the circumcircle through three of them (drawn for "inscribed/חסום", `hidden` for "cyclic/בר-חסימה") + `set-concyclic` over all of them + the polygon edges. The `circumcircle` rule, given **four** existing labels, emits the circumcircle of three + `set-concyclic` over all four (no forced edges — "circle through" asks only for the circle). `circumcircle` gains an optional `hidden` flag.

**Consequences.** `מרובע ABDE בר חסימה` and `circle through A B E D` on the triangle figure now keep A on CD and B on CE, drive a free DOF until **all four are concyclic**, and draw or hide the circle per phrasing — regressions `cyclic-quad-existing-vertices`, `circle-through-four-existing-points`, plus engine tests for the free-vertex carrier path. **933 tests green, build clean.** **Limits / next:** the residual targets exactly the cyclic-**quad** case (four points; >4 sums the deviations, which the optimizer can still descend but won't bracket in closed form); the driven point is whichever DOF `driveOrCheck` reaches first, so the resulting circle is one valid configuration (others via "show another"), not a student-chosen one; if the four are rigidly fixed and not concyclic it honestly flags the contradiction.

## ADR-042 — A FREE point on an arc (`on-circle` with `between`)

**Status:** Accepted (2026-06-17) · distinguishes "a point ON arc BC" (a 1-DOF free point) from `arc-midpoint` (the fixed midpoint)

**Context.** "F is on arc BC" / "F על קשת BC" should give F as a **free, slidable** point on the arc — a real degree of freedom the student can position and a later constraint can drive (e.g. "∠FBC = 30°"). The only arc construct was `arc-midpoint`, the *fixed* midpoint; the parser also required the word *midpoint*, so "F on arc BC" matched no rule, escalated, and was either dropped or placed by the generic on-circle rule on the wrong circle. Modelling F as a plain `on-circle` point (an absolute `theta`) has two problems: the parser can't compute an on-arc angle (it has no positions), and a full-circle θ lets the sampler/solver slide F onto the *far* arc.

**Decision.** `OnCirclePoint` gains `between?: [Id, Id]`. When set, `theta` is reinterpreted as a **fraction in [−1, 1] of the (minor) half-arc** from the arc's midpoint — not an absolute angle:
- *evaluate* computes F at `baseAngle + clamp(theta, −1, 1)·0.92·halfArc`, where `baseAngle` is the midpoint direction of the arc from→to and `halfArc` is half the subtended angle. So `theta = 0` (the canonical seed-0 default) puts F at the arc midpoint, and any sampled/driven value keeps F **strictly on arc from→to** (the 0.92 keeps it off the endpoints). F depends on from/to, resolved by the normal fixed-point sweep (`pending` until they're placed).
- *sampler* slides a `between` point by drawing `theta` uniformly in [−1, 1] (a fraction of the arc) instead of the full-circle spin — so "show another configuration" varies F across the arc, never around the whole circle.
- *parser*: "F **on** arc BC" → `point-on-circle` with `between:[B,C]` (free); "F **midpoint of** arc BC" → `arc-midpoint` (fixed). The circle is resolved by membership (the circle holding both B and C — ADR earlier this session).

**Consequences.** "F על קשת BC" builds a free point that starts at the arc midpoint and slides within arc BC on resample, on the circle that actually contains B and C — engine tests `free-arc-point.test.ts` (canonical = midpoint; resampled = varied, always on circle P and within the arc) + scenario `point-on-arc-no-midpoint-word`. **938 tests green, build clean.** **Limits / next:** a constraint that *drives* a `between` point goes through the generic on-circle carrier path, whose seed/range still assume an absolute θ — so a driven (vs free) on-arc point isn't yet arc-bounded by the solver; the arc taken is always the minor arc from→to (no "major arc" selector yet).

## ADR-043 — Collapse the hand-synced enumerations into single sources of truth (carrier descriptor, SHAPES/reuse registry, branchable source, compiler-checked kinds)

**Status:** Proposed (2026-06-17) · from the [design audit §3 items 1–2, R2/R3/R4](13-design-audit-2026-06-17.md)

**Context.** The audit's named root cause of the "case-by-case patching" feeling: the same concept is **hand-enumerated across 5–8 sites with no compiler link, and a missing copy fails silently** (a dropped DOF, a false conflict — not a type error). Three concrete enumerations: (1) "which point kinds carry a DOF" is re-typed in `driveOrCheck` (`apply.ts:44–108`), the four `resolveDriven` filters (`evaluate.ts:86–101`), `carrierSpec`/`setCarrierVals`, `sample.ts` `freeDofs`/`rawMovableDof`, `step.ts` `freeDrivableAncestors`/`markDriven`; and `POINT_KINDS` (`types.ts:327`) is a hand-typed `ReadonlySet<string>` parallel to the 21-member `GeoPoint` union with no compiler reconciliation. (2) "which commands reuse-or-create base points" lives in `isShape` (`step.ts:64`), `DERIVED_SLOTS`, `POINT_PLACEMENTS`, `shapeKinds`, `mirrorComposition` — restating the real authority `placeBase` (`apply.ts:306`); this list already drifted in production (the circumcircle false-conflict, git `1fdd6a0`). (3) "which kinds have cyclable branches" is enumerated 3× with mismatched lists (`step.ts:613` 5 kinds vs `App.tsx:264`/`scenarios.test.ts:654` 4 kinds).

**Decision (proposed).**
- **Carrier descriptor (R3):** a single `carrierOf(o): Carrier | null` (`carriers.ts`) = `{ kind, dofCount, isParametric, preferenceRank, eligible(o,pinned), seed(), scale(span), jitter(), read(), write(o,vals) }`, seeded *verbatim* from the existing `carrierSpec`/`setCarrierVals`/`sample.ts` tables (figure-tuned magnitudes — copy, don't flatten). All readers route through it. **Scope limit:** `driveOrCheck` stays a thin ladder that *consults* `preferenceRank`/`eligible` but keeps the on-segment→`on-segment-solved` kind mutation and the load-bearing preference order (on-line beats on-circle, `apply.ts:51–54`).
- **Compiler-checked kinds (R3 Piece 1, free):** `type GeoPointKind = GeoPoint['kind']`; build `POINT_KINDS` from a `const … as const satisfies readonly GeoPointKind[]` + a `Record<GeoPointKind, true>` exhaustiveness object, so a forgotten kind is a **compile error**. Collapse the two `solve?` shapes into the one named `SolveDirective`.
- **SHAPES/reuse registry (R4 Stage 1):** replace the `isShape` literal with a structural `reusesBase(cmd)` derived from apply's own `placeBase` output, so `commandConflict` consumes apply's output instead of a parallel list; derive `DERIVED_SLOTS`/`POINT_PLACEMENTS`/`shapeKinds` from one `SHAPES` registry. (Stage 2 — folding the five 0-DOF vertex kinds into one `DerivedVertex` carrying a drivable scalar — is deferred behind corpus tests; **not** a bare `Mat2`.)
- **Branchable source (R2):** export one `firstCyclableBranch(c)` from the engine; `App.tsx`/`scenarios.test.ts` call it. The `on-segment-solved` branch is **not** persistable through replay today (`apply.ts:48` synthesizes `branch:0` fresh, the command carries no `branch` field) — so either keep it out of the user-facing set with a comment, or deliberately add `branch?` to `point-on-segment` + a post-replay regression test. Do not bill the latter as free.

**Consequences (expected).** "Add a kind / add a reuse-command / add a branchable kind, forget one of N copies" becomes a compile error (membership) or a single edit point (behavior). Risk is confined to apply-time/conflict-time classification and the carrier read/write table — no change to the solving math; gate with a before/after corpus coordinate snapshot (determinism makes this a clean diff).

**Resolved (2026-06-17 discussion).** on-segment-solved cycling **IS a feature** — implement option (b): add `branch?: number` to the `point-on-segment` command, thread `cmd.branch ?? 0` through `apply.ts:48`, and add a post-replay regression test (build a two-root figure, assert `t` flips after replay). This follows the operator's general principle: **everything movable should be able to move** — via *cycle* ("show another configuration") now, and via *drag* later (Phase 8 interaction). The two mechanisms are distinct work.

**Implemented (2026-06-17, Wave 1).** *Piece 1* shipped: `GeoPointKind = GeoPoint['kind']`, and `POINT_KINDS` is now derived from a `POINT_KIND_FLAGS: Record<GeoPointKind, true>` (keys must exactly match the union — a forgotten kind is a compile error; this proved cleaner than a `satisfies` list + `AssertNever`, which the strict config flagged as an unused type). The two inline `solve?: { constraint; branch }` shapes are folded into the named `SolveDirective`. *R2 (the feature)* shipped: the `point-on-segment` command carries `branch?`, threaded onto the `OnSegmentPoint` as `solveBranch?` (named apart from `branch` so it doesn't join the `'branch' in o` set of *materialised* branchable points) and read in `driveOrCheck` when it upgrades to `on-segment-solved`; the store's `cycleAlt` branchable set gains `point-on-segment`; and a single engine-owned `firstCyclableBranch(c)` replaces the drifted `BRANCHABLE_KINDS` literals in `App.tsx` and `scenarios.test.ts`. Regression: a 2-root driven on-segment point cycles to its other root and the choice survives `replay` (`phase3.test.ts`). The `carrierOf` descriptor + SHAPES/reuse registry (Pieces 2 / R4) remain Wave 2. **941 tests green, build clean.**

## ADR-044 — The engine owns resolved geometry; the renderer consumes it (no re-derivation)

**Status:** Proposed (2026-06-17) · from the [design audit R1](13-design-audit-2026-06-17.md) · reinforces [ADR-004](#adr-004)

**Context.** The renderer is meant to be a pure consumer ([ADR-004](#adr-004)), but `scene.ts:117` `lineGeometry` verbatim re-implements `evaluate.ts:696` `resolveLine` (its comment admits it "mirrors the engine's `resolveLine` … because the engine doesn't expose its internal resolution"), and `scene.ts:209–221` re-derives circle radius including the tangent-inner formula. They have **already diverged**: a tangent-inner circle with a `via:'through'` outer renders nothing. The data is already computed and discarded — `evaluateCore` holds populated `lines`/`circles` maps (`evaluate.ts:586–587`) but `EvalOk` (`evaluate.ts:39–42`) returns only `{ positions }`.

**Decision (proposed).** Add `lines: Map<Id, ResolvedLine>` and `circles: Map<Id, ResolvedCircle>` to `EvalOk`; export the two interfaces; populate both `ok:true` returns; thread through `Derived` (`geoStore.ts`) into `buildScene`; **delete** `lineGeometry` and the radius re-derivation. The renderer must `orient()` the resolved geometry the same way it orients positions (`Figure.tsx:138–141`) — orient `anchor`/`center`, rotate + component-flip `dir`, `r` invariant. Genuinely-presentational parts stay in the renderer (arc sweep/largeArc, line-trim-to-extent, autoCenter/hidden draw-gating). Add a guard test: scene geometry == `evaluate()`'s resolved values (modulo orientation).

**Consequences (expected).** One source of truth for line/circle resolution; the standing renderer-vs-engine divergence is eliminated; future `Line.via`/`RadiusSpec` modes are added once. Purely additive — positions unchanged, determinism/stability untouched. **Do this first:** highest value-to-risk ratio, and it establishes the "engine owns geometry, view consumes it" pattern other items lean on.

**Implemented (2026-06-17, Wave 1) — refined mechanism.** Rather than thread cached world-coordinate maps through `EvalOk` → `Derived` → `buildScene` (which changes `buildScene`'s signature, forces re-orienting the maps in `Figure.tsx`, and churns ~12 test call sites), the engine now **exports `resolveLine` / `resolveCircle` (+ the `ResolvedLine` / `ResolvedCircle` types)** and the renderer **calls them** on the (already-oriented) positions it holds. Same single-source-of-truth outcome — `scene.ts`'s `lineGeometry` and the tangent-inner radius re-derivation are **deleted**, so there is no second implementation to diverge — but lower risk: `buildScene`'s signature is unchanged (zero test churn) and orientation is automatic (the resolver is a pure function of whatever positions it's given). It also fixes the live bug the divergence caused (a `tangent-inner` circle whose outer was `via:'through'` now renders, because the engine resolver reads the *resolved* outer radius). Exposing the maps in `EvalOk` is deferred until a consumer (e.g. Phase 6 theorem detection) actually wants world-coordinate resolved geometry — then it's a one-line addition. **941 tests green, build clean.**

## ADR-045 — One driven-DOF solver, one residual/degeneracy policy; binding decided once (capability-preserving)

**Status:** Proposed (2026-06-17) · from the [design audit R5/R7/R8](13-design-audit-2026-06-17.md) · refines [ADR-014](#adr-014)/[ADR-030](#adr-030)/[ADR-033](#adr-033)

**Context.** The DOF re-solver fractured into 3 near-duplicate numeric bodies + a 6-way router (`evaluate.ts:106` → coupled `139–224`, `resolveFreeDriven` `235–306`, `resolveMixedCarriers` `381–454`), with **three** residual conventions (coupled absolute+soft-barrier; free absolute+hard-reject; mixed relative+hard-reject), degeneracy thresholds ~40× apart, and a byte-identical "is satisfied?" gate copied at four sites (192/302/450/665). Separately, carrier→DOF binding is split across two phases that override each other (greedy `driveOrCheck` at apply time vs after-failure `recruitFreeDofs`, `step.ts:365`, whose own comment admits the greedy pick can be wrong), with three near-identical ancestor walkers and two bespoke diameter siblings. Branch identity is a position in a numerically-ordered list whose order flips as the figure flexes.

**Decision (proposed), strictly staged by risk.**
- **Cleanups (do now, no behavior change):** one exported `isSatisfied(con, get)` replacing the four copies; extract the shared scaffold (dedup + `withOrderCons` + Nelder-Mead/polish/seed-fallback) so the three bodies become thin configs; pick **one residual convention** (the relative one — [ADR-033](#adr-033) Am.1 declares it un-gameable) and apply it to `resolveFreeDriven`; pick **one degeneracy policy** (hard `degenerateSpread` + seed fallback, exempting `coincidePairs`).
- **Merge (gated, NOT a deletion):** the coupled block runs a full-range grid-scan coordinate-descent start (`evaluate.ts:207–222`, scanning `[0,1]`/`[0,2π]`) that `resolveMixedCarriers` lacks (it perturbs θ by only ±2 rad and **cannot reach a far-side branch**). So *first* port that grid-scan seeding into `resolveMixedCarriers`, *then* route pure-parametric multi-carrier cases through it. Keep the single-1-D `drivenRoots` fast path (`117–130`) — it is the only clean discrete-root cycling for "show another configuration."
- **Binding (R7, deepest, gated):** collapse the three ancestor walkers into one parametrized `ancestors(...)`; fold `reinterpretDiameter` into `reinterpretAsConstraint`; unify the apply-time pick and recruit by keeping `driveOrCheck` as a deterministic **tie-break weight** (it encodes same-residual disambiguation the joint solver cannot recover) + a real per-DOF stay-put penalty (the current `λ=1e-3` regulariser does not hold over-recruited DOFs).
- **Branch identity (R8):** extract a shared `otherCrossing(sols, pos, referenceId)` (retiring the line-circle-only `avoid` and the `step.ts:606` special case); where it pays, carry a signed-side geometric key so `branch` selects "the + side."
- **Hard constraint:** any new ordering/branch key **must reuse** `circleCircleIntersect`'s centre-axis sense and `solveParam`'s fixed grid — never invent a new ordering. This is the cheap insurance against silently regressing the alternatives feature.

**Consequences (expected).** Collapses ~5 of 6 solver duplications and the binding split. **Refuted sub-claim to respect:** `replaceCyclicForDiameter` cannot be deleted wholesale — its θ-spread can go, but it also converts D to a structural `antipode` (`step.ts:242`) so a later `∠BDA=24°` can't scramble the diameter (verified: without the pin, `scenarios.test.ts:293` bagrut-4d and `cyclic-quad.test.ts:150` fail). The antipode pin must remain or migrate to a first-class persistent relation first. **Gate:** a driven-solver stability harness asserting `maxDelta ≈ 0` on pre-existing vertices across adr028/cyclic-quad/shape-dof figures, before vs after.

**Resolved (2026-06-17 discussion).** The "reuse `circleCircleIntersect`/`solveParam` ordering" hard rule is **accepted** as a binding constraint on this work. The anti-collapse threshold question: **figures stay small**, so a small fixed threshold is fine — do **not** chase large-span relativization; instead, when the three solvers are consolidated (the cleanup step above), settle on **one consistent small threshold** across all paths. Consistency between the three solvers is the goal, not scale-relativity.

**Implemented (2026-06-17, Wave 1) — cleanup (1) only.** The single exported `isSatisfied(con, get)` now lives in `solve.ts` and replaces the four byte-identical `|residual| ≤ residualTolerance(constraintScale)` gates in `evaluate.ts` (the over-constraint check + the three driven-solver accept tests). The shared Nelder-Mead **scaffold extraction** (cleanup 2), the **one-residual / one-degeneracy** unification, the capability-preserving **merge** (with the grid-scan seeding port), the **binding** rework (R7), and the **branch-identity** generalisation (R8) all remain **Wave 2/3**, each behind the `maxDelta` stability harness — they touch the hot solver path and must not land without it. **941 tests green, build clean.**

## ADR-046 — Parser: one `=`-RHS rule; construct-vs-constrain folds into the engine's existing reinterpretation

**Status:** Proposed (2026-06-17) · from the [design audit R6/R9](13-design-audit-2026-06-17.md) · refines [ADR-002](#adr-002)/[ADR-024](#adr-024)/[ADR-026](#adr-026)

**Context.** The parser re-implements construct-vs-constrain in ~8 rules, each open-coding its own existence check, and ~20 of 62 rules carry "must run before X" comments with no ordering-invariant test. Eight `=`-RHS rules match the same `XY =` prefix and **none return `'stop'` on a partial match** — they return `null` and depend entirely on RULES-list position to avoid a silent half-parse (the documented [ADR-024](#adr-024)/[ADR-026](#adr-026) `"AB = 12√x"` → `set-distance 12` bug). Meanwhile the engine *already* has the generic construct-vs-constrain home: `reinterpretAsConstraint` + `POINT_PLACEMENTS` (`step.ts:464–482`) auto-lowers a re-definition into a `coincide` constraint driving a free DOF.

**Decision (proposed).**
- **Part (a), first — highest value / lowest risk:** fold the 8 `=`-RHS rules into **one** `XY = <rhs>` rule backed by `parseLengthRHS(expr)` returning a typed value (`number | π·k | k√r | k·varⁿ | ratio | equal-ref`) with an "unreadable" discriminant mapped to `'stop'`. Converts an ordering accident into a structural property; makes the half-parse class impossible. Add the ordering-invariant test + the missing √/sqrt coverage case.
- **Part (b), incremental:** stop pre-deciding existence in the parser; have the point-placement forks (`perpBisector`, `perpendicularLine` foot, `circumcircle`, `inscribedPolygon`, `ensureTriangles`) emit always-construct and let the engine's reinterpretation be the single home. The topology-divergent forks (`secantFromExternal`, `tangentFromExternal`) emit different segment topology per branch — treat as a second, smaller family with a richer intent tag. **Fold the parser into the reinterpret chain; do not delete it.**
- **LLM context (R9):** `absorb` (`llm.ts:34`) registers only `circle`/`circle-through`, not `circumcircle` — so a plan `["circle through A B C", "midpoint of arc BC"]` drops step 2. Add the missing circle-introducing types; make `circleMembers` a mutable local that accumulates on-circle outputs across re-parsed steps.

**Consequences (expected).** The half-parse class becomes structurally impossible; the construct-vs-constrain duality (and its "two pre-existence arrangements" that kept generating bugs) collapses onto one engine mechanism; LLM multi-step circle plans stop dropping steps. **Correction:** the audit's "parser reads coordinates / doc-11 boundary violation" framing is **dropped** — `App.tsx:147–151` feeds the parser declared *structure* (`circleMembers`, computed from kinds/parents), never coordinates; the accurate critique is "duplicates existence logic the engine owns." Do it rule-family by rule-family with `scenarios.test.ts` as the gate.

## ADR-047 — Test strategy: a property/invariant/differential layer; demote (don't delete) the per-figure scenario mandate

**Status:** Proposed (2026-06-17) · from the [design audit §5](13-design-audit-2026-06-17.md) · refines [ADR-008](#adr-008) and the [testing strategy](08-testing-strategy.md)

**Context.** The current methodology **amplifies** the patch loop: the NON-NEGOTIABLE "every reported bug becomes an end-to-end scenario" rule produces a monotonically growing example suite (24 additive commits, 0 removals; ~26 scenarios), while the one general asset — the 343-case campaign — is **positive-only by construction** (two `.toBe(true)` assertions, zero rejection assertions). `fast-check`/Playwright were specified in [ADR-008](#adr-008) and **never adopted**. Universal promises (stability, determinism, distinctness, replay-equivalence) are each pinned by a few hardcoded fixtures and tested on no generated figure — which is why bug *classes* surface one figure at a time.

**Decision (proposed).** Add a property layer over the existing campaign generators + `_invariants.ts`, in three tiers:
- **Tier A (now, free):** determinism (`build(cmds)` twice → deep-equal); blanket distinctness post-check; **replay-equivalence** (`build()` vs `replay()` of the same commands — currently untested entirely, and they are independent folds that could diverge).
- **Tier B (negative space):** an algebraic over-constraint generator (measure a true length/angle, append a contradicting one, assert `evaluate().ok === false` + prior-figure preserved — guaranteed by construction); a threshold-agreement probe across coordinate spans (≈1, 100, 1e4) routed through the three anti-collapse paths.
- **Tier C (scope honestly):** stability as a generated property needs an engine-reported `movedAncestors` diagnostic (else a naive "all prior ids frozen" false-fails on recruited/mirrored/reinterpreted branches); then `fast-check` with the seeded shrinker, driven off the single `firstCyclableBranch` ([ADR-043](#adr-043)).
- **Demote the scenario rule:** the *first* response to a bug becomes "extend a campaign generator / add an `_invariants.ts` predicate so the suite turns red"; add a scenario only for what the engine campaign can't reach (parser ordering, parse-with-context, LLM decomposition, store/resample). Optionally a meta-test that fails if `scenarios.test.ts` grows without a paired campaign/invariant change.

**Consequences (expected).** Whole bug *classes* are caught up front; the scenario suite stops being the only safety net and can stop growing monotonically. The property infrastructure **already exists** (`campaign.test.ts` + `_invariants.ts`, built 2026-06-12) — this is not a new suite, it is turning the existing one from positive-only into invariant + negative-space. The pure-geometry invariant each scenario asserts migrates into a campaign family; scenarios with `{llm:[...]}` steps or store-driven resample stay as pipeline coverage.

**Resolved (2026-06-17 discussion).** The scenario-growth meta-test is **accepted** — build it once the Tier-A/B property layer exists for bug-fixes to redirect toward (a gate with no alternative is just friction). Until then, the `CLAUDE.md` rule stands as written.

The equivalence check passed across the whole corpus on first run — closing a class that was previously **untested entirely** (the two are independent folds). ## ADR-048 — Dragging is a soft reseed (not a pin); "where can it go" is the alternatives mechanism scoped to one point

**Status:** Accepted (2026-06-17) · design; **implementation deferred to Phase 8 (interaction)** · refines [ADR-011](#adr-011)/[ADR-018](#adr-018); satisfies [FR-RN-5](02-requirements.md), [FR-RN-9](02-requirements.md), US-9

**Context.** Phase 8 will let a student drag a point on the canvas. The question was what a drag *means* in a constructive, constraint-driven engine — and a second, related idea the operator raised: when selecting a point to reposition, **show where it is allowed to go**. Two ways a drag could be modelled: (a) it **pins** the point at the drop location (a fixed coordinate), or (b) it is a **hint** — re-solve the figure with the point preferring that spot, but leave it free to move under later constraints. (a) collides with the product's defining interaction (a dragged point would stop participating in the figure's residual freedom and couldn't be re-driven), and it duplicates the *typed* pin (`A = (x,y)`, [ADR-011](#adr-011)).

**Decision.**
- **A drag is a soft reseed, not a pin.** Dragging sets the point's degree of freedom to the dropped position and re-evaluates, but the point **stays free** — future constraints can still drive it ([ADR-014](#adr-014)/[ADR-030](#adr-030)), "show another configuration" still samples it ([ADR-018](#adr-018)), and it can be dragged again. This is distinct from typing `A = (x,y)`, which **pins** ([ADR-011](#adr-011) — `pinned: true`, removed from sampling). A **free** point drops at the literal location; an **on-object** point projects onto its host (segment/circle/line) and sets `t`/θ; a **derived** point (0 DOF) is not directly draggable (its position follows its parents).
- **Unsolvable ⇒ snap back.** If `evaluate` cannot satisfy the figure with the point at the drop, the drag is discarded and the figure re-derives from the prior seed — the existing **keep-prior** contract ([FR-EN-8](02-requirements.md)), no new error path. So the point visibly returns to where it was.
- **"Where can it go" (FR-RN-9) is the alternatives mechanism, scoped to one point, shown all-at-once.** Selecting a point surfaces a small set of valid candidate positions: for a parametric point, samples along its host curve or — when constraint-driven — the discrete `solveParam` roots the engine already enumerates; for a free point, the [ADR-018](#adr-018) resample restricted to that point; for a derived point, none. Candidates are **thinned to ~10 well-separated positions** with the existing spread / min-separation heuristics (golden-angle on-circle spread; the distinctness guard) so they don't blob. It is the same residual-freedom machinery as "show another configuration" ([FR-ALT-2](02-requirements.md)) viewed per-point and laid out rather than cycled.

**Consequences.** Drag stays inside the constructive model — a hint that reseeds a DOF, never a new fixed object — so it composes with constraints, sampling, and undo without special cases, and reuses the keep-prior failure handling. The locus preview is a *view* over machinery that already exists, not new solving. **Staging:** the easy case (free and unconstrained-parametric points) is reachable first; the constrained case — "where can it go **while keeping every other given satisfied**" — is a joint solve and so depends on the consolidated solver ([ADR-045](#adr-045)). Drag itself reads each point's freedom from the carrier descriptor ([ADR-043](#adr-043)), which is one more reason the carrier/solver rework precedes the interaction work. Not built yet (Phase 8).

**Amendment (2026-06-20) — a playable DOF can't be moved into an IMPOSSIBLE figure (the radius slider, built).** The first shipped playable DOF (the free-circle-radius slider) applies the same "unsolvable ⇒ snap back" rule above: `setRadius` dry-runs `replay` with the candidate value and **only commits if the figure still builds** (`lastError === null`); a value that breaks it is rejected, so the slider STOPS at the boundary of the constructible range instead of letting the student dial into a broken/empty drawing (operator requirement — a DOF the engine exposes must not be draggable into an invalid state). This surfaced and fixed a latent bug: `replay`'s `lastError` was **build-only**, so a radius OVERRIDE (or a seed) that made the *final* `evaluate` fail left `lastError` null with the figure silently gone; `replay` now also reports the override-evaluate failure. The same guard will extend to drag/locus once Phase 8 lands.

## ADR-049 — LLM as strategist + seed for figures the engine can't solve alone (engine stays the arithmetic + verifier); harvest failures into the corpus

**Status:** Proposed (2026-06-17) · design only, not built · extends [ADR-023](#adr-023) (LLM fallback) · relates to [ADR-045](#adr-045) (one solver/seeding), [ADR-014](#adr-014) (generic constraints), the [compiler lens](11-architecture-as-compiler.md), and the "reported bugs become regression scenarios" rule (CLAUDE.md). Satisfies a future FR (TBD on acceptance).

**Context.** The engine occasionally fails to produce a figure for an input that is *not* contradictory: a construct or binding strategy it lacks, or — more often — a numerical solver that lands in the wrong basin / misses a far branch (the audit's own caveat: "port the grid-scan seeding or far-branch parametric figures regress"). We already have a server-side LLM path ([ADR-023](#adr-023)). The operator asked whether, in these rare cases, we could send all constraints to the LLM, get coordinates back, draw the figure, and use a feedback loop to "teach the engine."

**The naive form is rejected.** Asking the LLM to *return coordinates* makes the LLM do numerical constraint-satisfaction — exactly what LLMs are worst at; it produces plausible-but-wrong numbers (angles off by degrees, points not on their lines). Worse, it risks the cardinal sin of this tool: **displaying a figure that does not satisfy the givens**, off which a student would reason falsely. And the engine is not a learned model — it is deterministic symbolic/numerical code with no weights — so there is nothing to "update" at runtime, and runtime self-modification of the solver would be unsafe and untestable.

**Decision (the sound form — LLM owns *structure*, the engine owns *arithmetic + verification*).** When `evaluate` fails on a non-contradictory figure, escalate — but never let LLM numbers be truth:
- **(a) LLM as re-decomposer.** Ask the LLM for a *different construction recipe* — a sequence of primitives the engine already solves exactly (drop this ⟂, intersect that circle, take the far branch) — not for an answer. The engine executes it and stays exact. This is the same "LLM → canonical commands" contract as [ADR-023](#adr-023), applied to the solve-failure case rather than the parse-failure case.
- **(b) LLM as seed, engine as refiner.** For basin/branch failures, the LLM proposes a *rough layout / which branch / which DOF to drive*; the engine's numerical solver refines that guess to exactness. The LLM supplies the basin; the engine guarantees correctness. This is the highest-value variant because most non-contradiction failures are seeding failures.
- **(c) Verification is mandatory and non-negotiable.** Anything the LLM yields — coordinates or commands — passes through the engine's existing `isSatisfied`/residual gate ([ADR-045](#adr-045)) before anything is drawn. Residuals out of tolerance ⇒ reject and keep the prior figure ([FR-EN-8](02-requirements.md), no new error path). This is what makes the whole mechanism safe regardless of variant.
- **(d) Contradictions are NOT "solved."** When the real cause is over-constraint, the LLM must not paper over it — the correct behaviour stays "flag the conflict, keep the prior figure." The escalation is only for figures that *have* a valid drawing the engine merely failed to reach.

**The learning loop (offline + supervised, not runtime).** The engine "learns" by **capability accretion through the corpus and new constructs**, not weight updates. Every case where an LLM/seed path succeeds where the engine alone failed is **auto-harvested** into (1) a candidate corpus/regression fixture (the `logs/debug-log.jsonl` → scenario pipeline, partly automated) and (2) a "missing construct / weak basin" queue for a developer (+ assistant) to fix at root. So the rare-failure path doubles as a discovery mechanism for what the engine should learn to do natively — the project's existing "reported bugs become regression scenarios" rule, turned into an automatic harvester.

**Consequences.** The exactness and pedagogical-safety guarantees never leave the engine; the LLM only ever supplies structure or a starting guess, both verified before display. It slots onto the existing parser-first / LLM-fallback architecture with no new trust surface. Cost/latency: the seed/decompose call likely needs a stronger model than the haiku parser-fallback and only fires on genuine solve-failures, so it is rare-path — keep the [ADR-023](#adr-023) cost controls (gated proxy, low `max_tokens`, per-IP limit). **Open questions:** how the engine exposes a "seedable" hook to the solver (depends on the [ADR-045](#adr-045) consolidation — do that first); the exact harvest-to-corpus automation; whether to surface "found via assisted solve" to the student or keep it invisible; and the FR number once accepted. **Sequencing:** depends on the [ADR-045](#adr-045) solver/seeding work and the production proxy deploy (a parked thread); not before. Proposed, not built.

## ADR-050 — Collinearity constraint: a point onto a line named by two others (drives a free DOF; the redefine becomes a constraint)

**Status:** Accepted (2026-06-17) · built · 974 tests green. Extends [ADR-014](#adr-014) (generic constraints — a new `case` per function, no new point kind) and [ADR-028](#adr-028)/[ADR-046](#adr-046) (a redefining placement reinterpreted as a constraint). Satisfies the "two circles meet at A,B; line through one intersection point" construction unit (a common bagrut circle figure).

**Context.** An operator built two circles meeting at A,B, placed C on one and E on the other, then wanted line CE to pass through A — the classic secant-through-an-intersection-point figure. The tool had no way to express it (diagnosed from `logs/debug-log.jsonl`, session `de88adm7`): "ישר CE עובר בנקודה A" was **silently dropped** (the LLM modelled it as "A on line CE", which matched no parser rule), and the retry "E על המשך הצלע AC" hit **"'E' is already defined"** (a `point-on-segment` redefining the existing on-circle E). The real need: constrain an **already-placed** point onto a line through two others, driving its existing DOF — not redefine it, not coincide it with a fixed `t`-point.

**Decision.** Add a `collinear` constraint (points a,b,c) — the engine's first non-metric *incidence* constraint, modelled exactly like `parallel`:
- **Residual** = sin∠(b·a·c) (unit cross of the two rays from a) — scale-free, ∈[−1,1], 0 ⇔ collinear and sign-changing as the third point crosses the line, so a 1-DOF on-segment carrier brackets in closed form and an on-circle carrier descends it numerically. A collapsed ray ⇒ NaN (skip), as in `parallel`. Tolerance 1e-6.
- **Routing** is the existing `driveOrCheck`: it drives the first drivable referenced point (an on-circle/on-segment slides onto the line; a free vertex moves) and is a pure **check** (over-constraint detection) when all three are fixed. The point listed FIRST is preferred as the carrier, so "E on line AC" slides E. The trivial collapse onto A is rejected by the solver's existing **degeneracy gate** (two referenced points coinciding), so the solve finds the OTHER crossing of line AC with E's circle.
- **Two entry points.** (1) A parser rule (`collinearConstraint`) for "E on line AC" / "line CE passes through A" / "A, B, C collinear" (He+En); the line-named forms also DRAW the segment (idempotent, FR-IN-7). (2) `step.ts` `reinterpretAsCollinear`: a redefining "P on segment a→b" of an existing **free carrier** P becomes `collinear(P,a,b)` instead of an "already defined" error — the on-line analogue of the [ADR-028](#adr-028) coincidence reinterpretation. A catalog entry exposes the phrasing to the LLM fallback.

**Consequences.** No new point kind, evaluator rule, or solver — one residual case + one command + one parser rule + one reinterpretation, all on existing machinery. The exact operator sequence is locked as an end-to-end regression scenario (`line-through-intersection-collinear`). **Follow-ups:** the bare 3-point "collinear" form drives a free vertex, which on a rigid shape flattens it (rejected by the satisfied/degeneracy guards, kept-prior) — acceptable for v1; a dedicated incidence mark (showing the three are on a line) is deferred. A `point-on-line` of an existing **named line** object already had its own path (ADR-036); this complements it for the line-through-two-points case.

### ADR-050 Amendment 1 — chained collinearity exposed a driven-solver bug (binding-aware seed + keep an accepted candidate)

**2026-06-17 · built · 976 green.** Manual testing of the new constraint immediately found a chain that wouldn't solve (operator session `kd24do14`): two circles meet at A,B; C on O, D on P; **A,D,C collinear** (drives D); then E on O; **D,B,E collinear** (drives E). This is a *triangular* system — D is fixed by its own constraint, E then by D — but it failed with a false `over-constrained: A, D, C collinear cannot hold`. Root cause was **two** defects in the driven solver (`resolveMixedCarriers`/`multiStartSolve`):

1. **The joint solver minimised the SUM of all constraint residuals over all carriers.** The shared carrier D appears in *both* constraints, so the sum pulled D toward satisfying DBE as well as ADC and satisfied neither — losing the triangular binding (the deferred R7 "decide binding once" issue, [ADR-045](#adr-045)). **Fix:** a **binding-aware seed** — a Gauss-Seidel sweep solving each bounded carrier against *the constraint it drives* (others held), `argMin` on its own residual. For a triangular/sequential system this lands the exact solution; for a genuinely coupled one it's just one more restart the joint search vets. (The degenerate root — the driven point collapsing onto a referenced one, e.g. D=A — returns NaN from the collinear residual and is skipped by `argMin`.)
2. **`multiStartSolve` could DISCARD a solution it had already found.** Even though the grid-scan/binding seeds reached cost≈0 and passed the accept gate, the final polish (Nelder–Mead on the joint cost) wandered OFF the accepted point into a degenerate same-cost basin (the second collinear root), so the function returned the *seed* and reported a false over-constraint. **Fix:** track the best **accepted** candidate seen across all restarts and the polish, and return it when the polished point isn't accepted — never throw away a valid solution. This is general (it protects every driven solve, not just collinearity).

Both fixes are gated by the stability snapshot (unchanged) and the full suite; the chain is locked as engine test (`collinear.test.ts`) + end-to-end scenario `two-collinear-chain-solves`. The binding-aware seed is a small, local down-payment on the R7 binding consolidation, not a replacement for it.

### ADR-050 Amendment 2 — the "second intersection" pattern: a collinearity onto a circle becomes a line∩circle (avoid the shared point)

**2026-06-17 · built · 979 green.** More manual testing (operator session `uln4fwow`) showed the driven-collinear model is wrong for a *very common* circle construction: "E on line DB" where **E is on circle O and B is ALSO on circle O**. There, "E on line DB" means *the second intersection of line DB with circle O* — line DB meets O at exactly B and E. Driving E's angle by a generic collinearity let the numeric solve land on the **degenerate crossing E = B**, or on the wrong side, **seed-dependently** (the operator saw both, and only got the figure he wanted by cycling). The collinearity residual is zero at *both* crossings, so the solver has no principled reason to prefer E over B.

**Decision.** In the `set-collinear` handler, recognise the pattern and model it as a **line∩circle that AVOIDS the shared point** instead of a driven collinearity: when the point to drive is on a circle K and one of the other two (line) points is structurally also on K (`pointOnCircle`, a per-point view of `circleMembers`), replace it with `line-circle(line(other two), K, avoid = the co-circular point)`. `avoid` deterministically picks the crossing farthest from the shared point — so it is the OTHER crossing, **never** the degenerate one, and **seed-independent**. This covers both halves of the operator's figure (C on line AD with A on O; E on line DB with B on O), and composes with the parser rule AND the redefine reinterpretation (both funnel through `applyCommand(set-collinear)`). A generic collinearity (the driven point not on a circle, or no co-circular line point) still uses the driven solver from Amendment 1.

**Consequence.** The two most common collinearity figures (a point on a circle, on a line through another point of the same circle) are now exact, deterministic, and degeneracy-free — reusing the existing `line-circle` + `avoid` machinery ([ADR-022](#adr-022)) rather than a numeric DOF solve. The point becomes a 0-DOF derived crossing that tracks the remaining free point (e.g. D), so "show another configuration" still varies the figure by resampling D. Locked as engine tests (`collinear.test.ts`, second-intersection block) + scenario `second-intersection-avoids-shared-point`.

### ADR-050 Amendment 3 — ordered multi-point line "line ABE" (collinear AND in the named order)

**2026-06-17 · built · 981 green.** Operator asked whether "line ABE" could mean "a line starting at A, through B, then E" — i.e. the *order* of the named points should pin the side/sequence (B between A and E). This is the natural way to name a line through ≥3 collinear points and, crucially, it resolves the side ambiguity from Amendment 2 (which crossing / which way the figure folds).

**Decision.** `line ABE` / `ישר ABE` (and 4+: `line ABEF`) → a `set-line` command carrying the ordered point list. Its `apply`:
- **Collinearity** — each point after the first two is made collinear with the first two via `addCollinear` (the same helper `set-collinear` uses, so the second-intersection→line∩circle conversion of Amendment 2 still applies for circle points).
- **Order** — a new one-sided `collinear-order` constraint (the sum of "backwards" overlaps of the points' projections onto the line P0→Pn-1; 0 ⇔ strictly increasing). It mirrors the existing inequality constraints ([ADR-039](#adr-039)): no sign change, so it rides the optimizer, joins the joint solve via `withOrderCons`, and removes 0 DOF in the sampler's count. To fix the side it **drives the free PARAMETRIC carriers among the named points directly** (an on-circle / on-segment anchor slides until the order holds) rather than via `recruitFreeDofs` — which would reach a fixed intersection point's parent CIRCLE CENTRES and distort the circles. When no point is movable it's a pure check.
- Also draws the spanning segment.

Parsing is uppercase-labels-only after the keyword (so a lowercase word like "through" isn't read as a label run) and requires ≥3 labels (`line AB` falls through to the segment/other rules).

**Consequence.** Naming points in order selects the configuration deterministically: the operator's `line DBE` now places E beyond B (B between D and E) on circle O — the "continuation" he wanted — without cycling. Reuses the order-constraint machinery and the Amendment-2 conversion; the only new surface is the `collinear-order` residual + the `set-line` command/rule. Locked as parser + engine tests (`collinear.test.ts`, ordered-line block). **Limit:** a brand-new point named only inside `line ABE` that must MOVE has to be introduced on a host (circle/segment) first — a `point E` is pinned and so can't be slid onto the line; creating a fresh free point from the line name is a possible later refinement.

## ADR-051 — A circle's radius can be a free DOF (solver-sized), for circles with no stated size

**Status:** Accepted (2026-06-17) · built · 986 tests green. Extends the shape-scalar carrier framework ([ADR-033](#adr-033)) and the carrier-descriptor single source of truth ([ADR-043](#adr-043)). Satisfies the operator need: "the radii need to be DOFs — there is no chance the fixed values will hold for any question."

**Context.** "two circles intersect at A and B" states no radii, but the parser froze them at 5 and 3.6 (a fixed 0.72 ratio). For any real problem with givens (a length, an angle, equal chords…), frozen radii can't adapt — the figure over-constrains or draws wrong. The radii must be degrees of freedom the solver sizes.

**Decision.** A circle whose size is not stated gets a `radius: { via: 'free', value }` — `value` is the seed, but the radius is a **driveable shape scalar** (the circle analogue of a perp-offset `dist` / rotated angle). It flows through the EXISTING carrier machinery:
- `carrierOf` classifies a `via:'free'` circle as `family:'shape', dof:1` (so it's counted in the DOF cue and gathered by the joint solver). `carrierSpec`/`setCarrierVals` read/write the radius (clamped > 0).
- A constraint reaches it through `freeDrivableAncestors`: a point on a free-radius circle surfaces that circle's radius as a recruitable DOF (`circlesOfPoint`), so e.g. `|OC| = 9` (C on circle O) **sizes circle O to radius 9** — the radius is recruited and the joint solver sets it. A STATED radius ("circle O radius 5") stays `via:'length'` and fixed.
- The driven radius is baked into `positions` (the circle's points sit at the solved size) but NOT the stored seed, so the RENDERER recovers it as the distance from the centre to a point on the circle (`scene.ts`), drawing the circle to match its points.

**Deliberately NOT sampled.** A free radius is driveable but the sampler does **not** jitter it: varying radii on "show another configuration" produced near-tangent secants (a second-intersection point landing on another), regressing the secant-web scenario. Radius exploration is left to constraints; the centres are free points and still resample, so the two-circle overlap already varies between views.

**Scope.** Only `twoCirclesMeet` emits free radii for now (the reported case), so every existing fixed-radius circle (inscribed, circumscribed, stated-radius, tangent) is untouched — bounded blast radius. **Consequence / follow-ups:** extend free radii to other no-stated-size circles ("circle O" alone) once validated; the `RADIUS_VAR` (R) binding still reads the seed from the circle COMMAND (a free radius + an explicit `R` measure is a corner case to revisit); a guarded radius-resample (reject near-degenerate draws) could re-enable size variety in "show another configuration".

## ADR-052 — No fixed assumptions: every unstated magnitude is a free DOF (a default value, never a fixed value)

**Status:** Accepted (2026-06-17) · a GUIDING PRINCIPLE (partly built, audit ongoing). Generalises [ADR-018](#adr-018) (pinned-vs-free points), [ADR-033](#adr-033) (shapes carry true DOF), and [ADR-051](#adr-051) (free circle radius) into one rule that governs ALL constructs.

**The principle (operator, 2026-06-17).** A student enters what they SEE in the question — the relations and givens — nothing more. The tool must therefore make **no assumption about any size, angle, position, or proportion unless the student stated it** (a number, an angle, or a relation that forces it). A default is fine as a *starting* value so the figure can be drawn, but it must be a **free degree of freedom, not a fixed value**: it changes the moment the student asks for an alternative ("show another configuration") OR a later constraint forces it. Drawing a circle is not stating its radius; placing a point on a segment is not stating where; naming a quadrilateral is not stating its side lengths or angles.

**Why it matters (pedagogy).** A geometry figure must show ONLY what is given, or a student reasons falsely from an accidental property (a circle that looks equal to another, a point that looks like a midpoint, a quad that looks like a rectangle). A fixed default silently asserts a fact the question never gave. This is the same cardinal sin as drawing a figure that violates the givens — here it's drawing one that *adds* a given.

**Consequences / how it's enforced.**
- **Points:** an engine-defaulted point is free (sampler may redraw it); only a student-pinned `point A at (x,y)` is fixed ([ADR-018](#adr-018)).
- **Shapes:** a generic shape's vertices and its scalars (a rectangle's height, a rhombus's angle, a trapezoid's top) are DOFs the sampler varies; only *definitional* properties (a square's right angles / equal sides) are fixed — those ARE the given ("it's a square"), not an assumption ([ADR-033](#adr-033)).
- **Circle radius:** a circle with no stated radius has a free radius ([ADR-051](#adr-051)); a stated one is fixed.
- **Point on a segment/line/circle with no stated ratio/angle:** the parameter is a free DOF the sampler slides — the point isn't assumed to be the midpoint/a particular spot. (Being closed out under this ADR; on-circle already free, on-segment now too.)
- **General test of conformance:** every magnitude the renderer shows should trace back to a stated given OR be varied by "show another configuration." A value counted as a DOF (`rawMovableDof`) but NOT sampled (`freeDofs`) is a smell — a default masquerading as fixed.

**Audit (living).** Known instances brought into conformance: free points (ADR-018), shape scalars (ADR-033), circle radius (ADR-051, all unstated-radius circles). Closed under this ADR: a free on-segment point's position. **Open:** sweep for any other counted-but-unsampled DOF; confirm no rule bakes a fixed angle/length a student didn't give.

## ADR-053 — "No error" ≠ "correct": re-definitions become relations, and the figure is verified against the original givens

**Status:** Accepted (2026-06-18). Motivated by a trust question from the operator after two bugs slipped past green tests. Extends [ADR-050](#adr-050) (a redefinition becomes a relation, not a silent overwrite) and adds a general output-verification net.

**The two failures.** Reproducing a bagrut figure (two circles meeting at A,B; tangents; two secants), two issues passed every test and showed all-green in the app yet drew a wrong figure:
1. A natural Hebrew verb (**פוגש**, "meets") was absent from the shared `INTERSECT_KW`, so the operator's phrasing fell through to `circlesTangent` and was misread as mutual tangency. **Why it escaped:** the tests used the author's own phrasings (`meets`/`חותך`), not the synonym a real user typed — tests and code shared one blind spot.
2. The operator's `המשך AC חותך את מעגל P בנקודה E` had no rule, escalated to the LLM, which split it into `E על המשך AC` + `E על מעגל P`. The second command (`point-on-circle` for the ALREADY-EXISTING E) hit `addObj`, **which no-ops on an existing id** — so the on-circle fact was silently dropped: every step `ok`, `lastError` null, yet E sat far off the circle.

**Decision.**
- **A re-definition of an existing point is a RELATION, never a silent no-op.** `point-on-circle` for an existing point now: (a) idempotent if already on that circle; (b) if the point sits on a segment/line one of whose ends is also on the circle, it becomes the SECOND crossing (`line-circle` avoiding the shared end) — the same reinterpretation as [ADR-050](#adr-050)'s `addCollinear`; (c) otherwise it is left for the verifier to flag rather than dropped. (Generalising this to all `point-on-X` redefinitions, and adding a true "lies-on-circle" driving constraint for the free-DOF case, is follow-up.)
- **The output is verified against the original givens.** After evaluate, `checkGivens` ([src/engine/verify.ts](../src/engine/verify.ts)) re-derives the relations the COMMANDS assert — independent of how each object was constructed — and checks them against the final coordinates. On-circle membership and a tangent's tangency point are covered first (the classes that bit us); constraint residuals and collinearity are the next slice. Violations are exposed on `Derived.violations` and shown as an amber "the figure may not match what you described" cue. **"Green" now requires `violations` empty, not merely no error.**
- **Process (durable, in [08-testing-strategy.md](08-testing-strategy.md)):** a construct is not covered until several natural He/En phrasings parse; drive the real app (or replay the user's exact input) before calling a figure done — unit tests prove the code does what it was told, not that the figure matches the problem.

**Consequences.** `evaluate` now also returns the resolved `circles` map (centre + radius) so the verifier needs no re-resolution. The verifier is the standing net for the whole "looks fine, isn't" class — including future silent drops — because it checks the *stated intent*, not the (possibly lossy) constructed model.

## ADR-054 — `המשך XY` is DIRECTIONAL: a directed extension onto a circle that adapts the figure (`extend-onto-circle`)

**Status:** Accepted (2026-06-18). The resume task parked in the 2026-06-18 PROJECT-MEMORY ★ NEXT STEP note. Refines [ADR-050](#adr-050) (collinearity / ordered lines) and [ADR-052](#adr-052) (no fixed assumptions) for the circle case.

**The convention (operator-confirmed).** `המשך AC` ("the extension of AC") is **directional**: the new point lands **beyond the 2nd named letter** — `המשך AC` → past C (order A→C→D), `המשך CA` → past A. The same holds for English "AC extended" / "the extension of AC". This **changes** the prior reading: `lineMeetsCircle` ([ADR-053](#adr-053)) treated `המשך AC חותך מעגל P` as an order-agnostic *chord* (the crossing that avoids a shared on-circle end). Under strict semantics the **direction owns the meaning**, so a plain "line AC meets circle P" (no extension word) keeps the order-agnostic chord, while any extension word routes to the new directed construct. (The bagrut figure that motivated `lineMeetsCircle` is reworded accordingly: its `המשך AC`/`המשך BD` became `המשך CA`/`המשך DB`, since its E/F are past A/B.)

**The geometric crux.** With **default radii a line often has NO extension crossing at all** — line AC extended beyond C simply misses circle P. Honouring the extension therefore genuinely REQUIRES *resizing* the circle (an unstated radius is a free DOF, [ADR-051](#adr-051)/[ADR-052](#adr-052)), not merely picking a root. So the construct must **adapt the figure**, not just select a branch.

**Decision — a new `extend-onto-circle` command.** Two structurally different cases:

**(0) Shared endpoint — a named endpoint is ALREADY on the target circle** (e.g. A is an O∩P crossing, so it's on circle O). The line then meets the circle at that endpoint and at exactly ONE other point, so the directional extension IS that second crossing — a **deterministic `line∩circle` that AVOIDS the shared endpoint** (the same second-intersection pattern as `addCollinear` / [ADR-050](#adr-050) Am.2 / `lineMeetsCircle`). No driven solve, no radius change. *(This case was added after the first build: the operator hit "A and F would be at the same point" because the lone driven-θ solve collapsed F onto the degenerate F=A root — the touch-zero fragility below. When the line is genuinely **tangent** at the shared point (no second crossing exists — e.g. C was defined on the tangent to O at A, so line CA is that tangent), the `line∩circle` resolution now returns a clear "line is tangent … no second crossing to extend onto" error and the prior figure is kept, instead of the opaque coincidence crash.)*

**(1+2) Neither endpoint on the circle — the genuinely-directional case.** D is a fresh **on-circle point driven by `collinear(A,C,D)`** (slides onto line AC) plus a one-sided **`collinear-order [A,C,D]`** that pins it past the 2nd letter (the existing order residual, [solve.ts](../src/engine/solve.ts), [ADR-050](#adr-050) Am.3). Two regimes, reusing existing machinery:
- **A root exists at the current radius** → the **single-DOF driven solve picks the root that satisfies the order** (the FAR crossing), so the circle is left UNTOUCHED — no collapse onto the near crossing. (This is a small order-awareness added to `resolveDriven`'s 1-DOF path: a one-sided order constraint owns no carrier of its own, so when one references the driven carrier, the roots are sorted by order residual and `branch` cycles them.)
- **No root exists** (the line misses the circle) → the order check fails, `recruitFreeDofs` grabs the circle's **free radius** (reached via `circlesOfPoint`, [ADR-051](#adr-051)), and the mixed solver — which minimises the order jointly (`withOrderCons`) — **grows the radius** until an extension root appears.

**Why not mark the radius unconditionally.** An early version marked D *and* the free radius as carriers up front. With a root already available, the under-determined radius then drifted to the clamp floor (a degenerate dot) — a default masquerading as movable, the very smell [ADR-052](#adr-052) warns of. Recruiting the radius *only on failure* keeps it put when a valid configuration already exists.

**Limits / follow-ups.** (1) The 1-DOF order-aware pick depends on `drivenRoots` returning BOTH crossings; for a *pathologically axis-aligned* line (a crossing exactly at θ=0/π, a touch-zero of `|sin∠|`) it can return one, and the figure then falls back to the recruit+resize path (still valid, but it resizes when it needn't). A general `drivenRoots` touch-zero fix is deferred (broad blast radius). (2) When the target circle's radius is **fixed** (a stated size) and no extension root exists, the construct honestly cannot honour the order — an over-constraint, as it should be. (3) Folding `collinear-order` into the givens verifier ([ADR-053](#adr-053)) is the next verifier slice.

**Amendment (2026-06-19/20) — directional `המשך` extends to line∩line.** The same beyond-the-2nd-letter rule applies when two *extended* lines cross: "המשך BD חותך את המשך OC בנקודה A" means A is where the ray **beyond D** meets the ray **beyond C**. A `המשך`/extension operand sets `dir1`/`dir2` on `line-line-intersection` (detected per operand by which side of the cut verb the word falls on); `evaluate` requires the crossing to be beyond the named 2nd point (proj > 1 along that segment). Plain "BD cuts OC at A" (no `המשך`) stays direction-agnostic.

*The diverge case is CONFIGURATION-dependent, not impossible — and a free DOF must be SOLVED by the engine, not the user (operator requirement).* An early diagnosis of the operator's tangents-from-D figure wrongly concluded "by symmetry these extensions can never meet." They can: it depends on the **apex distance**. For tangents from an external point D to a circle of radius R, "המשך BD חותך את המשך OC" meets beyond D and beyond C only when D is **close** (≈ D < 1.4R; verified: D=1.2R → A=(10.7,−7.1) clean like the textbook, D=2.4R → crosses on the wrong side, with a parallel singularity at ≈1.4R between the two basins). **Shipped fix (two parts):** (1) the directional operand makes the command emit a `collinear-order` so `recruitFreeDofs` **drives the free apex** until the extensions reach A — the engine solves the DOF, the student never repositions a point; (2) the two-tangent construct (`tangentsFromExternal`) now **seeds the apex CLOSE** (≈1.2R, `x:6` for the default r5 circle, like a textbook sketch) instead of far (was 2.4R) — so the normal path satisfies the order at the seed with a clean crossing (no driving needed), and only a deliberately far-seeded apex falls back to driving. **Honest limit:** driving from a FAR seed, past the parallel singularity, lands a valid-but-ugly near-parallel config (A flung far out) — the close default avoids it for the real figure; a compactness-preferring driven solve (reject the near-parallel basin) is the follow-up. The absolute `x:6` seed assumes the default r5 origin circle; a radius-relative apex seed is also a follow-up.

**Amendment 2 (2026-06-20) — an extension-meet DRAWS both lines through to the meeting point.** Operator: "המשך CA ו-BD נפגשים בנקודה G — should also draw the lines up to G." The crossing G was placed, but `lineLineIntersection` drew the bare operand segments (CA, BD), which stop at the inner points and don't visually reach G (the operator drew CG/BG by hand). Fix: when an extension word is present, draw each line from its **base through to G** (`C→G`, `B→G`) — the inner points (A, D) then lie *on* those segments, so the extension is visible — and emit the `line-line-intersection` (which DEFINES G) **before** the segments, since a segment to a not-yet-defined G would create G as a stray free point and conflict ("'G' is already defined"). A plain diagonals crossing without an extension word ("M = intersection of AC and BD", M *between* the endpoints) is untouched — drawing only to the crossing would hide half of each diagonal. Regression `scenarios.test.ts` `extension-meet-draws-lines-to-G`.

## ADR-055 — A parse that builds nothing gets a SECOND try (LLM) and then an honest problem — never a silent no-op

**Status:** Accepted (2026-06-18). Operator request after a typo (`שנקודה` for `בנקודה`) caused a tangent-meets-circle phrasing to fall through to `circles-tangent`, which silently repositioned the circles and **drew no tangent line** — "a silent fail with no indication of error".

**The failure class.** Geo Builder is **parser-first, LLM-fallback** ([ADR-023](#adr-023)): the deterministic grammar runs first, and only `not-handled` (no rule matched) escalates to the LLM. The hole: a too-greedy rule can **match** malformed input and produce a *confident but wrong/empty* parse — so it "succeeds", never escalates, and the LLM that would have understood the typo is never consulted. Same shape as the [ADR-053](#adr-053) "no error ≠ correct" problem, one layer up (at input routing, not output verification).

**Two fixes.**
- **Structural (parser):** `circlesTangent` no longer fires when a cuts/meets keyword (`INTERSECT_KW`: חותך/פוגש/cuts/meets) is present — mutual tangency is a STATE ("tangent to each other"), never a crossing EVENT. A near-miss of `tangentMeetsOtherCircle` (e.g. the typo) can no longer be misread as the two circles touching.
- **Routing (input layer):** a deterministic parse is now **dry-run before it commits** (`dryRunOutcome`, [src/store/geoStore.ts](../src/store/geoStore.ts)): it replays the candidate commands on top of the current facts and asks whether they actually BUILT something. "Produced nothing" = a step that **errored** (kept-prior) or **changed nothing at all** (no new object / constraint / label; a bare `x=4` is exempt as legit data). Such a step is **not committed** — it gets a **second attempt through the LLM**, exactly as `not-handled` does. The LLM's decomposition is itself dry-run; if neither grammar nor LLM builds anything, the input layer shows an explicit **"I understood that but it didn't build anything"** message ([i18n](../src/i18n/locales/en.json) `input.producedNothing`) instead of a silent success.

**Deliberately NOT a trigger: a givens *violation*.** A step that applies but contradicts the stated givens is already surfaced by the [ADR-053](#adr-053) verifier's amber "may not match" cue *with the figure still shown* — that's an indication, not a silent fail — so it does **not** force an LLM retry (which would suppress the amber and cost a call for no gain). Only *error* and *no-change* escalate (operator's chosen policy).

**Consequences.** A re-stated-verbatim construct (idempotent, no growth) now escalates to the LLM — a rare, cheap edge. The verifier ([ADR-053](#adr-053)) remains the net for "built something, but the wrong figure"; this ADR is the net for "built nothing".

## ADR-056 — A symmetric driven constraint nudges its DOF to the NEAREST root (stability), not `roots[0]`

**Status:** Accepted (2026-06-20). Operator report: a cyclic quad ABCD was correct until the last step `OD⊥AC` — which "messed the shape up". The constraint applied with no error, yet vertex D jumped half a circle and the quad became **crossed**.

**Root cause.** The 1-DOF driven solve ([ADR-028](#adr-028) base case, `resolveDriven` in [src/engine/evaluate.ts](../src/engine/evaluate.ts)) finds the roots of a constraint's residual along the carrier's parameter and returns `roots[branch]` (branch 0 by default). A **symmetric** constraint like `OD⊥AC` has two roots — the two arc-midpoints of AC, half a circle apart. D already sat at ≈330° (essentially the near arc-midpoint, residual ≈0), but `roots[0]` was the FAR root at ≈148°, which lands *between* A(30°) and B(210°) and re-orders the vertices into a self-intersecting quad. The solve had **no stability preference**, so it could fling a point clear across the circle to satisfy a constraint the nearby root already satisfied.

**Decision.** When **no order constraint** (`collinear-order`/`angle-order`/`length-order`) rides the carrier — i.e. there is no stated reason to prefer a side — order the roots by **nearness to the carrier's current parameter value** (circular distance for an on-circle θ, linear for an on-segment t). Branch 0 is then the *smallest move*: a symmetric constraint nudges its point to the nearest satisfying spot rather than the antipodal one. "Show another configuration" still cycles outward to the far root, so no configuration is lost — only the *default* changes, from arbitrary to stable.

**Why this is the right layer.** This is the structural-stability principle ([ADR-028](#adr-028): "adding a constraint re-evaluates downstream objects without perturbing earlier choices — the figure doesn't jump") applied to the driven-root choice, which previously honoured it only by accident of root ordering. The order-constraint path is untouched: when an order *is* stated (e.g. an `extend-onto-circle`'s far crossing), that preference still wins over nearness. The `POLYGON_SHAPES` convex/cyclic check used by resampling is a *rejection* filter; this is the *prevention* — keep the move small so the polygon never leaves its valid order in the first place.

## ADR-057 — A circle tangent to two GIVEN sides (inscribed-corner circle), composed from primitives

**Status:** Accepted (2026-06-20). Operator entered, on a rectangle ABCD, "AB ו-AD משיקים למעגל O" ("AB and AD are tangent to circle O") — it escalated to the LLM and **built nothing**. The operator asked, reasonably, whether the LLM should decompose such a sentence into a construction.

**Root cause — a missing primitive, not an LLM failure.** The LLM is constrained to emit only canonical commands the parser re-parses ([ADR-023](#adr-023)); it cannot invent geometry. Every "tangent" the engine knew went **circle → tangent** (a tangent *line to* a given circle at a point, two tangents *from* an external point, two circles mutually tangent). The operator's sentence is the **inverse**: the *sides* AB, AD are given and the **circle must be constrained tangent to them**. With no command expressing "tangent to a given line", neither the parser nor the LLM could land it, and building nothing was the honest outcome ([ADR-055](#adr-055)). So the fix belongs at the **vocabulary layer**, not the LLM.

**Decision — compose from existing primitives (no new engine type), like the incircle.** A circle tangent to two sides that meet at a shared vertex (a corner) has its centre on the **angle bisector** at that vertex — the locus equidistant from both sides — with **one free DOF**: how far along the bisector, i.e. how big the circle is. A new parser rule `cornerTangentCircle` emits, all from primitives that already existed:
- a `bisector` Line of ∠(arm1–vertex–arm2);
- a **free** `point-on-line` on that bisector as the centre O (a sampled DOF — "show another configuration" grows/shrinks the circle; [ADR-052](#adr-052): an unstated size is never frozen);
- two `foot` points — the ⟂ feet from O onto each side — the tangency points E, K (named if the student gave them, else auto-named like the incircle's foot);
- a `circle-through` O via the first foot, so **r = distance(O, side)** ⇒ tangent to that side; tangency to the *other* side is **automatic** because O is equidistant (on the bisector).

**Consequences.** No new `Command`/`RadiusSpec`/object kind — the construct is purely a parser composition, so the engine, evaluator, renderer, sampler and undo all carry it for free (the centre is an ordinary free on-line DOF the [ADR-036](#adr-036) sampler already varies). Tangency is **structural** (radius literally *is* the distance to the side, and the second side is equidistant by construction), so it cannot drift and needs no givens-verifier check — "green = verified" holds trivially. **Scope (v1):** the two sides must share a vertex (a corner); two parallel/opposite sides (no shared vertex — centre on a midline, not a bisector) fall through to the LLM. **Refinement noted:** the free DOF is sampled by scaling the offset (0.4×–2.4×), so a large sample can push a tangency point *past* the end of a short side (still tangent to the side's *line*, but poking past the corner); bounding the offset to keep both feet within their segments — the [ADR-048](#adr-048) "a DOF must not reach an invalid figure" principle, applied to this DOF — is deferred.

**Amendment 1 (2026-06-20) — putting an EXISTING point on the corner circle grows it.** Operator next added "C נמצאת על המעגל" ("vertex C is on the circle") and it built nothing ("why isn't C adjusted to be on the circle?"). C is a *derived* rectangle vertex — it can't itself slide onto the circle, so the `point-on-circle` apply hit its give-up branch (case c). But the corner circle has a **free size DOF** (the centre's slide), so the circle should GROW to reach C. Fix: in that branch, when the circle's radius is set by a point T on it (`circle-through`, which the corner circle is), "P on circle" ⟺ `|centre·P| = |centre·T|` is pushed as an `equal` constraint; `driveOrCheck` routes it to the centre's free on-line offset and grows the circle until P lands on it — **tangency preserved** (the centre stays on its bisector, only the size changes). Reuses the existing equal-distance residual and the on-line driving path; no new mechanism. Also a parser broadening: `pointOnCircle` now resolves a **definite/unnamed** circle ("על המעגל" / "is on the circle") through the single circle in context (via `resolveCenter`), so the phrasing parses deterministically instead of escalating. (General case — a `free`-radius circle with no point on it — would drive the radius DOF directly; deferred, as the corner circle is always `circle-through`.)

**Amendment 2 (2026-06-20) — the corner circle needs no pre-named circle; spacing was a red herring.** Operator: "AB וAD משיקים למעגל" failed, "only after adding a space it worked — shouldn't the LLM be called?" Two findings. (i) The LLM **is** called on `not-handled` ([ADR-023](#adr-023)) — it was, and it built the figure; the perceived "failure" was its latency/nondeterminism, not a missing fallback. (ii) The deterministic rule failed *regardless of spacing*: it required `resolveCenter` to find a circle, and "למעגל" names none (and none existed yet). Fix: `cornerTangentCircle` now **auto-names** a fresh centre when none is given (`circleCenter(s) ?? freeLabel(...)`, dodging the figure's labels — the incircle pattern), so the construct builds offline with or without a named circle, and the "ו" spacing is irrelevant. (The auto-picked tangency points are the rule's fixed defaults — first choice **E** then **F/G**, and **K** then **M/N** — *not* remembered across runs; there is no cross-run memory.)

## ADR-058 — A segment ratio may carry a √ value; a ratio LHS bars the length rules from fragment-misparsing

**Status:** Accepted (2026-06-20). Operator typed `EB/AE=√2/2` (the ratio EB/AE = √2/2 ≈ 0.707) and "it didn't work as expected — does the √ need parentheses?" It silently parsed as **`AE = √2`** — a wrong *length* on the middle two letters, dropping both the `EB/` numerator and the `/2` denominator.

**Two root causes.** (1) `segmentRatio`'s right-hand side accepted only a numeric fraction (`2/3`), so a √ value didn't match and the rule fell through. (2) With it fell through, the measure-VALUE rules (`measureSqrt`, `measureLength`, …) — which match a single `XY = value` anywhere in the string — grabbed the **fragment** `AE=√2` out of `EB/AE=√2/2`. This is the [ADR-024](#adr-024)/[ADR-026](#adr-026) "wrong partial parse beats honest failure" class, one rule reaching into another rule's input.

**Decision.** (a) Extend `segmentRatio`'s value to a `RATVAL` that allows a `√` on the numerator and/or denominator — `√2/2`, `√2`, `1/√3`, `1/√2` — computing `k` accordingly (plain fractions unchanged). (b) Add a shared `SEG_RATIO_LHS` guard (the shape `XY/ZW =`) to every measure-value rule (`measurePi`/`measureSqrt`/`measurePower`/`measureLength`/`distanceConstraint`): when the input *is* a ratio, only `segmentRatio` (which runs first) may claim it — so an RHS it still can't read (e.g. the parenthesised `(√2)/2`) **escalates honestly** to the LLM instead of fragment-misparsing to a length.

**Consequences.** No parentheses are needed — `√2/2` reads directly; parentheses are in fact *not* parsed and now fail cleanly rather than misparsing. The guard is the general fix (it covers the whole length-rule family, not just the √ case), so any unreadable ratio RHS fails honestly. A `√` in a ratio is exact-valued (`Math.sqrt`), consistent with how `measureSqrt` keeps "12√2" exact for lengths.

## ADR-059 — A "show circle centres" view toggle (telling unnamed circles apart)

**Status:** Accepted (2026-06-20). Operator: "when working with two circles, unless we have the centres like O and P, it's impossible to know how to address each circle — we should be able to show and hide the centres."

**The tension.** FR-RN-8 made a circle's centre show **only when named or used** (an unused auto-centre — a circumcentre, an incentre, a defaulted "two circles" centre — is hidden, so the canvas isn't littered with helper dots). That default is right for a single tidy figure, but it backfires with **two unnamed circles**: both centres are auto-hidden, so the student can't see that one circle is O and the other P, and can't reference them ("tangent to circle O…").

**Decision.** Add a **view-level toggle** (default off) that reveals *every* circle's centre with its label, auto ones included. It is a pure *display* preference — `buildScene(…, { showCenters })` simply skips the unused-auto-centre suppression — so it touches no engine state, no facts, no undo history; it lives in the renderer's local `view` (beside rotate/flip/align) as a toolbar button (⊙), not in the fact list. Auto-centres already carry real labels (O, P, … via `freeLabel`), so flipping it on immediately names the circles on the canvas.

**Why a global toggle, not per-circle.** The stated need is "tell the circles apart / know how to address them" — a single switch solves that with the least UI. Per-circle show/hide (click a circle to toggle its centre) is a finer-grained follow-up if it's ever wanted; the global toggle is the 80% solution and is trivially reversible. The default stays off so the clean FR-RN-8 behaviour is unchanged until the student asks for centres.

## ADR-060 — A second free point on a segment seeds away from the first (and a "two points on AC" rule)

**Status:** Accepted (2026-06-20). Operator: "why can't I add 2 points on a segment? I tried in 2 ways and both failed." Way 1, "L ו-K נקודות על AC" (both at once), escalated to the LLM and built nothing; way 2, one at a time, the *second* point "K על AC" **errored** — "L and K would be at the same point".

**Root cause.** A free `point-on-segment` with no stated ratio always seeded `t = 0.5` (the midpoint, [ADR-052](#adr-052)). A second point on the same segment therefore landed exactly on the first and tripped the [ADR-017](#adr-017) no-two-nodes-coincide guard. (The combined phrasing additionally had no deterministic rule, and the single-point rule misparsed it — so it fell to the LLM, whose two points then hit the *same* collision.)

**Decision.** (a) Seed a new free on-segment point in the **middle of the largest open gap** among the parameters of points already on that segment (`freeSegT` in [apply.ts](../src/engine/apply.ts), normalised to the a→b orientation): the first lands at 0.5, the second at 0.25, the third at 0.75, … so any number of points spread out instead of stacking. The "show another configuration" sampler still slides each independently. (b) Add a `pointsOnSegment` parser rule for "L and K are points on AC" / "L ו-K נקודות על AC" / "L ו-K על AC" → two `point-on-segment` commands, deferring circle phrasings ("A and B on circle O") and requiring four distinct labels.

**A JS-regex gotcha worth recording.** The Hebrew "points" word matched `נקוד\w*` — but **`\w` is ASCII-only** in JavaScript, so it stopped after "נקוד" and the suffix of "נקודות" broke the whole match. Hebrew word-fragments in a regex need an explicit Hebrew-letter class (`[א-ת]*`), never `\w`. (Likely lurking in other rules; flagged for an audit.)

**Consequences.** Adding any number of points to a segment "just works" — they're placed distinctly and remain free DOFs. The fix is at the seed layer, so it also covers points placed by other constructs that land on a shared segment.

## ADR-061 — A drawn perpendicular that "cuts AB at E" creates the crossing point (and draws the segment)

**Status:** Accepted (2026-06-20). Operator tried several ways to create a perpendicular segment EK and "it just drew a line." The phrasing that got closest — "האנך ל-AC בנקודה K חותך את AB בנקודה E" ("the perpendicular to AC at K cuts AB at E") — parsed to a **single** `perpendicular-line` command: the `perpendicularLine` rule built the line through K but **dropped the "cuts AB at E" clause**, so E was never placed and no segment was drawn.

**Root cause.** `perpendicularLine` only ever emitted the drawn line (+ optional name markers). It had no notion of the perpendicular *meeting another segment at a new point* — a real construction ("erect a perpendicular at K, where it meets AB is E"), distinct from merely drawing a perpendicular.

**Decision.** When a **cut clause** is present (a cut verb — `INTERSECT_KW` — then a segment then a result point), the rule now builds the perpendicular as **scaffolding** (`visible:false`, not a long drawn line — the student wanted the segment, not an infinite line), crosses it with the named segment via `line-through` + `line-intersection` to place the result point E, and draws the perpendicular **segment** K–E. The cut verb anchors the match, so the *second* "בנקודה"/"at" is read as the result point, not the perpendicular's through-point. Mirrors the existing `tangentLineIntersection` pattern (tangent line ∩ a segment → a named crossing). With no cut clause the rule is unchanged (a plain drawn perpendicular with markers).

**Consequences.** "The perpendicular to AC at K cuts AB at E" now places E on AB with EK ⟂ AC and draws EK — a one-line way to build a perpendicular segment between two sides. The companion phrasing "from E on AB drop a perpendicular to K" (the inverse direction) still escalates to the LLM — a follow-up if it recurs.

## ADR-062 — Coupled chained equalities (AL=LK=KC) joint-solve instead of deadlocking

**Status:** Accepted (2026-06-20). Operator: "support a case such as AL=LK=KC — multiple equalities." The parser already chains it into `AL=LK` + `LK=KC` (the `chainedEquality` rule), but the figure **errored** "unresolved dependencies for: L, K".

**Root cause.** `driveOrCheck` upgrades a free on-segment point pinned by an equality to a **closed-form `on-segment-solved`** (its `t` placed analytically — fast and exact for the common case "E on AC with AE=3"). With a chain, `AL=LK` drives L and `LK=KC` drives K — but **each constraint references the OTHER driven point**, so L's closed form needs K's position and K's needs L's: a cycle the topological evaluator can't break, leaving both "unresolved". The numeric joint solver (`resolveMixedCarriers`, [ADR-045](#adr-045)) *could* solve them together, but `resolveDriven` only routes plain `on-segment` carriers to it — never `on-segment-solved`.

**Decision.** In `resolveDriven`, detect **coupled** solved-on-segment points — those whose constraint references another solved-on-segment — and **promote that group back to numeric `on-segment` carriers** (kind `on-segment` + a `solve` directive, seeded at the closed-form `t0`), then re-enter. They now fall into the coupled numeric path and solve **jointly**: `AL=LK=KC` drives L and K together so they trisect AC (all three parts equal). The fast closed-form path is untouched for the uncoupled common case — only a genuine cycle pays the numeric cost.

**Consequences.** Chained equalities of any length on shared free points now work (`AL=LK=KC`, `AC=CD=DB`, …) — equal division/`n`-section falls out of the general solver, no special-casing. The coupling test is purely structural (does a solved point's constraint name another solved point), so it generalises beyond equalities to any constraints that drive mutually-referencing on-segment DOFs.

## ADR-063 — Spelled-out Greek letter names normalise to symbols (alpha → α)

**Status:** Accepted (2026-06-20). Operator: "I enter alpha for one angle then try 2alpha to another and the result is wrong." Spelled-out `alpha` (not the `α` glyph) was the trap.

**Root cause.** A symbolic variable is a *single* Greek letter (`[α-ω]` in the var regex), so `alpha` (five letters) never matched the symbolic-measure rule. `∠BAC=alpha` fell through to `not-handled`; worse, `∠ABC=2alpha` was then caught by the numeric `angle` rule, which read the leading `2` as **2 degrees** and silently dropped `alpha` — so the second angle became a 2° sliver, not 2α (the [ADR-024](#adr-024)/[ADR-026](#adr-026) numeric-prefix half-parse, again).

**Decision.** Normalise spelled-out Greek names to their symbols at the parse entry point (`normalizeGreek` in `parse()`), before any rule runs — `alpha→α`, `beta→β`, … `omega→ω` — so the existing single-letter variable machinery handles them unchanged. Two guards: (1) **lowercase-only** keys, so an uppercase point pair (`MU`, `XI`) is never read as μ/ξ; (2) bounded by **"not a letter"** (lookarounds, not `\b`) on each side, so a *digit* prefix counts (`2alpha`→`2α`, where `\b` fails because digit↔letter is no boundary) while a letter neighbour does not (`alphabet` stays a word). `pi` is deliberately omitted (it collides with a segment `PI`; only the π glyph is accepted, per [measurePi]).

**Consequences.** Students can spell out angle variables (`alpha`, `2theta`) or use the glyphs (`α`, `2θ`) interchangeably. The fix is at the entry layer, so it covers every rule (lengths, ratios, inequalities) at once — and the inequality `alpha<beta` now reaches its rule as `α<β` too. (A wider audit for other `\w`-vs-Hebrew / numeric-prefix half-parse traps remains worthwhile — see [ADR-060](#adr-060).) **Note:** this was *not* the operator's actual α/2α bug — they used the glyph — see [ADR-064](#adr-064) for that root cause; this fix stands on its own (the spelled form was genuinely broken).

## ADR-064 — Only a FREE on-segment point is driveable; a stated-ratio/extension point is a given

**Status:** Accepted (2026-06-20). The operator's real "α then 2α is wrong" report (with the α glyph). Figure: isosceles △ABC (AB=AC) in its circumcircle (centre O), **D placed on the extension of BC** (`t = 1.3`), then `∠CAD = α` and a central angle `∠BOC = 2α`. It **errored** — "cannot place D on segment BC so that ∠BOC = 2·∠CAD".

**Root cause.** `driveOrCheck` (apply.ts) picks a DOF for a relation to drive, preferring an on-segment ref first (its `t` is solved in closed form). It picked **D** — but D's position was *stated* by the student ("on the extension", `t = 1.3`), not a free DOF. So an unrelated relation (a central angle that doesn't even depend on D) tried to satisfy itself by sliding D, which either fails (no D makes a central angle = 2× an inscribed one) or "succeeds" by dragging D off where the student put it. Either way the figure is wrong. The step (1) filter selected *any* `on-segment` kind, ignoring the `free` flag the parser sets.

**Decision.** Step (1) now drives only a **free** on-segment point (`free === true` — the parser's mark for "no stated ratio", e.g. "G on AB"). A point the student positioned explicitly — a stated ratio ("E on AC at 40%") or an extension point ("D on the extension of BC", `t>1`) — is a **given**, not a DOF, so the relation falls through to drive the figure's genuine freedom (a free vertex / shape scalar) instead. With D left put, `∠BOC=2α` correctly reshapes the *triangle* so the central angle is twice ∠CAD, and D stays at `t=1.3`.

**Consequences.** A relation never silently relocates a point the student pinned by position; it drives the actual free shape, matching intent (and "no fixed assumptions" in reverse — an explicitly *stated* value is equally inviolable). One store test that drove an on-segment point constructed with an explicit `t` (a non-parser representation) was realigned to the free representation the parser emits — its behaviour (a branchable driven on-segment point, [ADR-043](#adr-043)) is unchanged. General: the driveability test is now "is this a free DOF?", not "is this a parametric kind?".

## ADR-065 — "Show another configuration" reports when there is no different drawing

**Status:** Accepted (2026-06-20). Operator: "the image says 5 DOF but when I request a different view I get the same one — we need an on-screen indication of whether something is or isn't happening." On a figure whose *shape* is determined by its constraints (an isosceles triangle in a circle with `∠BAC=2∠CAD` fixing the apex angle), the only remaining freedom is similarity (size / rotation), so every resample looked identical and the button felt dead.

**Root cause.** `resample` advanced the seed to the first *valid* sample — never checking it was a **visually different** drawing. With only similarity DOFs left, all samples render the same figure, and the student got no signal that the engine had searched and found nothing new.

**Decision.** `resample` now compares each candidate to the current drawing with a **similarity-invariant shape fingerprint** (every pairwise distance between named points, normalised by their mean — translation/rotation/scale/reflection don't change it) and accepts a sample only if the shape genuinely differs (>3% mean change in the distance ratios). It returns `true` when it lands a different drawing and `false` when 24 attempts find none. The UI shows a transient note on `false` — "No other configuration — the shape is determined (only size/position can change)" — so the button always gives feedback. When a different drawing exists, the visible change is the feedback (no note).

**Why the fingerprint, not the DOF count.** The "N DOF" cue counts *all* residual freedom, including similarity transforms that don't yield a different *configuration*. Distinguishing "shape DOF" from "similarity DOF" in the count is a harder, separate problem (deferred); the fingerprint sidesteps it by asking the only question the student cares about — "is this a different drawing?" — directly. A side benefit: resample no longer jitters to a same-looking view, so when variety *does* exist it reliably surfaces it. (A scoped attempt this session to also stop the count itself from inflating — excluding a stated-position parametric point from `rawMovableDof`/`recruitFreeDofs` — was reverted: it over-constrained on-circle figures that legitimately recruit such a point's freedom, and the targeted figure's extension point is in fact free, not stated. The DOF-count honesty pass is left as future work.)

## ADR-066 — "Triangle circumscribes a circle" is the incircle; two tangents can meet at a point

**Status:** Accepted (2026-06-20). Two operator gaps in one figure (inscribed triangle in a circle).

**(1) "משולש DEF חוסם את המעגל" / "triangle DEF circumscribes the circle".** This was misparsed to a **circumcircle** (a circle *through* D,E,F) — backwards. "A triangle circumscribes a circle" is the same figure as "a circle inscribed in the triangle" (the **incircle**, tangent to the three sides). Fix: the `incircle` rule now also matches the triangle-first phrasing, with an **ordered** pattern (triangle-labels … `circumscrib`/`חוסם` … circle) so the *circle-first* "מעגל חוסם משולש" (a genuine circumcircle, circle as subject) is **not** captured — the subject that "circumscribes" is the outer shape, and word order disambiguates it. (Limit: it builds the incircle as a fresh circle of triangle DEF; tying it to a *named existing* circle — a tangential triangle around a fixed circle — is a follow-up.)

**(2) "המשיק מנקודה A והמשיק מנקודה C נפגשים בנקודה D" — two tangents meeting at a point.** No rule existed for tangent ∩ tangent (only the tangent ∩ *segment* compound), so it escalated to the LLM and built nothing. Fix: a `twoTangentsMeet` rule emits the `tangent` line spec at each on-circle point plus a `line-intersection` — D is the pole of chord AC, where the two tangents cross (each ⟂ its radius). Tolerates the `מנקדה` typo and both "מנקודה"/"בנקודה" forms; runs before the tangent ∩ segment rule (which needs exactly one tangent).

**Amendment (2026-06-20) — the LLM can now compose the tangential triangle.** Operator asked whether the LLM could break down "a tangent through *each* vertex of triangle ABC, the tangents meeting at D, E, F" (the tangential triangle). It can — and this is the intended division of labour ([ADR-023](#adr-023)): the LLM does the natural-language *understanding* (expand the "each vertex" quantifier; pair the three tangents) and emits only *canonical* lines the deterministic parser guarantees. Because the catalog now contains the two-tangents-meet form (above), it is in the LLM's vocabulary, so the long sentence decomposes into **three** "tangent at X and tangent at Y meet at Z" lines that build the tangential triangle DEF (verified end-to-end: each of the six tangent segments is ⟂ its radius). A prompt example was added to make Haiku reliable at this specific expand-and-pair step. General lesson: extending the deterministic vocabulary *automatically* extends what the LLM can compose — the two layers compound.

## ADR-067 — A perpendicular operand is never silently read as a plain line; ⟂-cut accepts an extension target

**Status:** Accepted (2026-06-20). Operator: "המשך DB והאנך לישר AD נפגשים בנקודה G" produced a wrong/degenerate figure (and the next step "DG" then errored). Root cause: the generic line∩line rule grabbed the four labels (D,B and A,D) and **silently dropped "אנך"** — reading "the perpendicular to AD" as just "line AD". Since line AD and line DB share endpoint D, that crossing collapses **onto D**, so G can't be built. A second, deeper issue: "the perpendicular to AD" gives **no through-point**, so it's underspecified — the figure only works with the perpendicular **at A** (a vertical), the one non-degenerate choice.

**Decision.** (1) `lineLineIntersection` now **defers** (escalates) when a perpendicular/parallel modifier (`אנך`/`מאונך`/`מקביל`/`⊥`/`⟂`/`∥`/`perpendicular`/`parallel`) is present — it cannot represent a ⟂/∥ operand, so it must not mangle it into a plain line. (2) The `perpendicular … cuts … at` form ([ADR-061](#adr-061)) now accepts a **"המשך"/extension** cut target (`חותך את המשך DB`), so the explicit, well-specified phrasing **"האנך ל-AD בנקודה A חותך את המשך DB בנקודה G"** builds correctly: G = (⟂ to AD at A) ∩ line DB (verified — GA ⟂ AD, G on line DB).

**Consequences.** The ambiguous one-liner no longer silently builds a degenerate point — it escalates, and the LLM (which can infer the missing through-point from the figure) can now emit the cut form, which parses. The robust deterministic path is to **name the perpendicular's point** ("…בנקודה A…"). General principle reinforced: a rule that *can't* represent a modifier must defer, not drop it (the [ADR-024](#adr-024)/[ADR-026](#adr-026) class, applied to ⟂/∥ operands).

## ADR-068 — A reference to the circle's centre isn't a circle definition; a named line can cut the circle twice

**Status:** Accepted (2026-06-20). Two gaps in a tangent-secant figure (circle O, tangent from external A, a line from A through the centre).

**(1) "ישר AD עובר דרך מרכז המעגל" built a PHANTOM circle P.** The `circle` rule's `centred` trigger matched `מרכז` (centre) even in "מרכז המעגל" ("the centre of the circle" — a *reference* to the existing circle, not a new circle), so it auto-created a stray circle. Fix: `centred` counts as a circle *definition* only when a centre is actually **named** (`מעגל שמרכזו O`); a bare reference no longer fabricates a circle (it defers, and the line-through-centre meaning can be expressed otherwise). All real circle definitions (named centre / radius / through / standalone "circle") are unchanged.

**(2) "AO חותך את המעגל בנקודות C ו-D" — a NAMED line cutting the circle at TWO points — had no rule.** `lineMeetsCircle` finds ONE new crossing (the other endpoint already on the circle); `secantFromExternal` needs "from a point …". Neither fits a line given by two points (an external point + the centre) crossing at *both* roots. Fix: a `lineCutsCircleTwice` rule (before `lineMeetsCircle`) emits `line-through` + a `line-circle-intersection` for each branch (0 and 1) + the drawn secant — so "the line AO cuts the circle at C and D" builds C, D on the circle, collinear with A–O (a secant through the centre). Resolves the circle by name **or** the figure's single circle.

## ADR-069 — The external tangent apex is a free DOF; a real bagrut figure reproduces with its SYMBOLIC given

**Status:** Accepted (2026-06-20). Operator built the actual bagrut Q4 figure (circle R, external A; tangent AB at B; AD through the centre O cutting at C,D; AG ⟂ AD; D,B,G collinear; **∠ADB = α**), then tried adding a numeric size (`AG=8`) and a proportion (`AC=0.5DC`), which **over-constrained**. They showed the textbook page: "it is supposed to be solvable."

**Two findings.** (1) The `tangentFromExternal` rule **pinned** the external apex A — but A's distance from O is *unstated*, so it should be a **free DOF** ([ADR-052](#adr-052)); pinning it removed the very freedom the problem parametrises. Fix: the single-tangent apex is now `free` (matching the already-free two-tangent apex) — safe (no test regressions), and it lets a *length* given like `AG=8` flex A. (2) The figure is **shape-determined**: with the construction's structural constraints (AG⟂AD, the collinearity) only the scale is free. The book's given is the **symbolic** `∠ADB = α` — a *label*, not a numeric constraint — so the figure builds cleanly (verified end-to-end: D,B,G collinear, AG⟂AD, C,D on the secant through O, matching the drawing — now scenario `bagrut-q4-tangent-secant-perpendicular`). The operator's failures were from stacking *numeric* givens (`AG=8` **and** `AC=0.5DC`) onto a figure with too little residual freedom to hold them both.

**The honest limit.** Setting `∠ADB` to a *number* still over-constrains / can't converge: the angle depends on A only *indirectly* (through the tangent point B and the secant end D), and the constraint solver can't currently flex A to hit a target angle through that chain. Driving *whichever* free DOF actually satisfies each constraint (a joint solve / carrier-fallback over all DOFs) is the real enhancement — deferred. For now the figure reproduces with the symbolic α (the book's own form), and a single length given works. (An attempt this session to also free the EXTENSION point G was reverted — it re-broke [ADR-064](#adr-064)'s case where a relation that *can't* be satisfied by sliding the extension point must drive the shape instead; the two need the same carrier-fallback.)
