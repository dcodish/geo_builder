## ADR-1xx — Evaluating advanced solvers without risking the engine: a frozen baseline + a pluggable solver seam + a differential harness

**Status.** Proposed (2026-07-02) · design only, no code. Sibling to — and reuses the infrastructure of — the **coordinate-validation campaign** ([ADR-109](#adr-109)) and the **givens verifier** ([ADR-053](#adr-053)); its correctness metric is theirs. Motivated by the paper's method-lineage work ([`paper/01-methods-and-mathematical-lineage.md`](paper/01-methods-and-mathematical-lineage.md)).

**Context — why, and the hard constraint.** The engine's numeric core is a deliberately **derivative-free** stack: bisection with grid bracketing for a single driven DOF (`solveParam`, `geometry.ts`), and a Nelder–Mead + coordinate-descent + Gauss–Seidel joint solve with Tikhonov regularisation for the coupled case (`evaluate.ts`). It is **correct** — it matches an independent closed-form oracle to ~machine epsilon over a 13,760-figure sweep (ADR-109) — but it has documented cost/robustness soft spots: ~7 s on the reflection figure, ~1.5 s coupled replays, and the genuinely under-determined ~8-DOF case where a Halton global multi-start was tried and reverted (it didn't converge). We want to evaluate **better-fitting** methods (Brent / TOMS 748 for 1-D; automatic differentiation → Gauss–Newton / Levenberg–Marquardt; CMA-ES for the under-determined case; continuation / interval / graph-decomposition as research directions — see [`paper/01`](paper/01-methods-and-mathematical-lineage.md) §2–4). **Operator's hard constraint: the working engine must not be risked in any way, and we must be able to run the whole test corpus through the old solver vs. a new one and see whether anything improves.** This ADR fixes *how* we do that.

**Decision — one repo, a frozen baseline, a solver seam whose default is the untouched code, and a differential harness.**

1. **No repo/branch fork.** Two copies drift and — fatally for this goal — cannot be compared in a single run. One repo; many solvers behind one seam.
2. **Frozen baseline (the safety net).** Tag today's HEAD `solver-baseline`. It is the immutable reference the harness measures against and the parity guard compares to.
3. **Solver seam (strategy pattern) at the two numeric entry points.** Put a thin `Solver` interface in front of `solveParam` (1-D) and the multivariate joint solve. The **`classic`** implementation *is the current code, called verbatim*, and is the **default** — when selected, behaviour is byte-identical to `solver-baseline`. Experimental solvers (`brent`, `newton-ad`, `cma-es`, …) live under a new `src/engine/solvers/` and are **never imported by any production path**; only the harness selects a non-default one. The seam scales to *N* solvers for free (this is why it beats "two versions").
4. **Parity guard.** A test asserts `classic`-mode output equals `solver-baseline`, and the full suite (~1,700) + the ADR-109 oracle campaign must stay green with the default. This is what makes "zero risk to production" *provable*, not merely asserted.
5. **Differential harness — extend `src/validation/`, don't rebuild.** The ADR-109 campaign already builds figures, owns the independent oracle, and sweeps 13,760 figures; extend it to run the corpus + scenarios + sweep under **each registered solver** and emit a comparison report.
6. **Correctness is measured against ground truth, never as a coord-diff old-vs-new.** The engine emits *one model from a space of valid models* (ADR-018), so a new solver may land on a **different but equally correct** configuration — diffing its coordinates against `classic` is meaningless. The metrics are: **correctness** = givens-verifier-green **+** oracle-agreement on the 0-shape-DOF slice (ADR-109), a **hard gate — a new solver must be no worse than `classic` on every figure**; **speed** = function-evaluations + wall-clock (the improvement signal); **robustness** = convergence on the hard/slow/under-determined set; **stability** = the additive-stability property (ADR-047 Tier) must not regress. Note which tests carry which signal: the exact-command / scenario-coordinate tests are **parity guards** (must stay green in `classic`); the **improvement** signal lives in the sweep + timing under an experimental solver.
7. **Apparatus before verdicts (de-risking order).** Build the seam + harness with **`classic` only first**, and prove the harness reports `classic ≡ classic` at machine-ε — a differential rig that can't show "new == old when new *is* old" is worthless (the ADR-109 load-bearing-test principle). *Then* plug in the first experimental solver (`brent` / TOMS 748 in `solveParam`: same roots, fewer evals, clearest metric, lowest risk), read the report, and only then escalate to the AD + Gauss–Newton/LM track.

**Why this is additive and zero-risk (the ADR-109 argument, applied).** Production's default path does not change behaviour and is guarded by the parity test + full suite + oracle campaign. Experimental solvers are not in the production bundle and are imported only by the harness (a dev/CI tool, like a test). Building and running it cannot break anything; only *acting on an improvement it proves* would touch the production default — and that step is itself gated by the same suite (CLAUDE.md rule 4). The independent oracle and generator are exactly what cannot live in production (no ground truth for arbitrary under-determined student input), so this is a dev/CI tool by construction.

**Alternatives considered.** (a) *Fork the repo / long-lived branch* — rejected: drift, and it can't run old-vs-new in one comparison. (b) *A parallel `evaluateExperimental` module that duplicates the orchestration and swaps only the numeric core* — kept as a fallback if the operator wants literally zero edits to production files, but **not preferred**: duplicating orchestration means a measured difference could come from orchestration drift rather than the solver, muddying the science; the seam keeps the solver the *only* variable. (c) *Edit the solver in place behind a flag with no baseline tag* — rejected: no immutable reference to prove parity against.

**Methodology & record-keeping.** *How* we run these comparisons, define metrics, version the benchmark, and record every A-vs-B run for paper claims is specified in [`paper/experiments/PROTOCOL.md`](paper/experiments/PROTOCOL.md) (+ its `LEDGER.md` and `results/` schema). This ADR is the *harness architecture*; that protocol is the *experimental method* the harness serves. Both are cross-referenced from the testing strategy ([08](08-testing-strategy.md#comparative--experimental-testing-method-a-vs-b-vs-c)).

**Scope (v1) and relationship to the paper.** First experimental solver: Brent / TOMS 748 in `solveParam`. AD + Gauss–Newton/LM is a second, heavier R&D track (caveat: residuals are non-smooth at intersection branch points / `abs`/`min`/guards, so AD gradients need care across branch switches). CMA-ES targets the under-determined case Halton missed. Continuation / interval methods / graph decomposition stay **paper future-work** unless the harness shows a pain point that demands them. This ADR *is* the paper's evaluation methodology (§ "Correctness / verification" and "Limitations & future methods" in [`paper/outline.md`](paper/outline.md)); a positive result (e.g. "Brent cuts 1-D solver evals X% with identical roots and zero verifier regressions over the corpus") is a citable empirical claim.
